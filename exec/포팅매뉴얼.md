| 항목 | 내용 |
|---|---|
| 프로젝트 | DUO (Coding Agent를 위한 Decision compliance 도구) |
| 팀 저장소 | GitLab `https://lab.ssafy.com/s15-final/S15P31A106.git` (GitHub `https://github.com/kanghyunsoon/duo`의 mirror) |
| 기준 브랜치 | `main`: stable 0.3.5(npm `latest`), `next`: 0.4 개발선(npm `next` = 0.4.0-rc.2) |
| 공개 패키지 | npm `@duo-director/cli` |

## 1. 배포 형태 요약

DUO는 웹 서비스가 아니라 **npm으로 배포하는 명령줄 도구(`duoctl`)**다. 사용자의 PC에서 사용자의 Git 저장소를 대상으로 실행된다.

- 서버를 띄우거나 호스팅할 곳이 없다. 클라우드 배포, 도메인, 인증서, Docker, Nginx가 필요 없다.
- Coding Agent(Codex, Claude Code)는 `duoctl mcp`를 **표준 입출력(stdio) MCP 서버**로 실행해 DUO를 쓴다. 네트워크 포트를 열지 않는다.
- 선택 기능인 로컬 UI(`duoctl ui`)만 `127.0.0.1`에 HTTP 서버를 연다. 외부 접속은 받지 않는다.
- 데이터는 대상 저장소 안의 `.duo-project/` 폴더에 파일로 저장된다. 별도 DB 서버가 없다(내장 SQLite, 8장).

따라서 포팅은 **소스 빌드 → 배포 패키지(tarball) 생성 → 설치 → 대상 저장소에 적용** 순서다.

## 2. 기술 스택과 버전

### 2.1 실행·빌드 환경

| 구분 | 사용 제품·버전 | 비고 |

Windows 11, Node.js v24.18.0, pnpm 11.25.0, Git 2.55.0. CI는 같은 커밋을 Ubuntu·macOS에서도 검증한다.

## 4. 소스에서 빌드

```bash
git clone https://lab.ssafy.com/s15-final/S15P31A106.git duo
cd duo                                 # 기본 브랜치 main (0.3.5)
pnpm install --frozen-lockfile         # 검증 환경 약 16초
pnpm build                             # tsc -b + UI 번들, 약 40초
node apps/cli/dist/main.js --version   # → duoctl 0.3.5
```

- pnpm이 없다면 Node.js에 포함된 Corepack으로 `corepack enable` 후 실행하거나 pnpm 11을 설치한다.
- 저장소 루트에서 `pnpm duoctl <명령>`으로 빌드한 CLI를 바로 실행할 수 있다.
- 0.4 개발선을 빌드하려면 `git checkout next` 후 같은 명령을 실행한다.

### 4.1 테스트(선택)

```bash
pnpm verify   # check:boundaries → lint → typecheck → build → test → docs:validate
```

전체 테스트는 Windows에서 수십 분 걸리고, UI E2E에는 `pnpm exec playwright-core install chromium`이 먼저 필요하다. CPU가 바쁜 PC에서는 `VITEST_MAX_WORKERS=3`처럼 병렬 수를 줄이면 시간 초과가 줄어든다(테스트 내용은 같다).

## 5. 배포 패키지 생성과 설치

### 5.1 패키지(tarball) 생성

```bash
pnpm release:pack
# 결과: .dist/duo-director-cli-<version>.tgz, .dist/release-candidate.json
```

- 작업 트리에 commit하지 않은 변경이 있으면 거부한다(배포물과 커밋을 일치시키기 위해).
- **Windows 주의(main/0.3.5):** pnpm을 standalone 실행 파일로 설치한 PC에서는 `pnpm release:pack`이 `ERR_UNKNOWN_FILE_EXTENSION`으로 실패한다(Issue #90, next에서 #93으로 수정). 같은 스크립트를 직접 실행하면 결과물은 같다.

  ```bash
  node scripts/release/pack.mjs
  ```

- **재현성 확인 결과(2026-11-13):** GitLab main에서 새로 clone해 만든 tarball이 npm에 공개된 0.3.5와 동일했다.

### 5.2 설치

| 방법 | 명령 |
|---|---|
| npm 공개 패키지(stable) | `npm install -g @duo-director/cli` |
| npm 공개 패키지(RC) | `npm install -g @duo-director/cli@next` |

## 6. 대상 저장소에 적용

### 6.1 0.3.5(main, npm `latest`)

```bash
cd <첫 commit이 있는 Git 저장소>
duoctl init                 # Truth 질문 → .duo-project 생성 → 첫 index → adoption baseline
duoctl install codex        # 또는: duoctl install claude-code
duoctl doctor               # 전체 점검, "ready"면 정상
```

비대화형(스크립트·CI)에서는 질문 답을 JSON으로 넘기고 확인을 `--yes`로 준다.

```bash
echo '[{"question":"project_goal","value":"Sample app."},{"question":"current_milestone","title":"MVP"}]' \
  | duoctl init --non-interactive --answers -
duoctl install codex --yes
```

commit하지 않은 변경이 있는 저장소라면 `--baseline-policy head`(현재 HEAD를 기준으로 기록) 또는 `abort`를 골라야 한다.

### 6.2 0.4.0-rc.2(next, npm `next`): 한 번에 설정

```bash
duoctl setup --agent codex   # 질문 → 계획 출력 → 한 번 확인 → Truth·index·baseline·Agent 연결 → doctor
```

비대화형에서는 `--yes`가 없으면 계획만 보이고 아무것도 쓰지 않은 채 종료 코드 6으로 멈춘다. `--yes`는 파일 변경만 승인하며 Truth 질문에 대신 답하지 않는다. `init`, `install`, `doctor`는 0.4에서도 그대로 동작한다.

### 6.3 사용

```bash
duoctl index                    # 코드를 바꾼 뒤
duoctl review                   # 변경을 Decision과 대조. CI에서는 --fail-on block(BLOCK이면 종료 코드 4)
duoctl ui [--port N] [--open]   # 선택: 127.0.0.1 로컬 UI. 포트를 생략하면 빈 포트를 고른다
```

`duoctl ui`가 출력하는 URL에는 실행마다 새로 만드는 세션 값(`?session=...`)이 들어 있다. 공유하지 않는다. Ctrl+C로 종료한다.

### 6.4 DUO 밖에서 사람이 해야 하는 한 단계

DUO는 Agent의 신뢰·승인 설정을 바꾸지 않는다.

- **Codex:** 저장소를 처음 열 때 나오는 trust 질문에서 신뢰하거나, `~/.codex/config.toml`에 `[projects."<저장소 경로>"]`와 `trust_level = "trusted"`를 추가한다. 그다음 Codex의 `/mcp`에 `duo-director`가 보인다.
- **Claude Code:** 저장소에서 `claude`를 실행해 workspace trust와 `duo-director` 서버를 승인한다. 승인 전 `claude mcp get duo-director`는 `Pending approval`을 보인다.

DUO는 commit하지 않는다. 생성된 파일(7.2)을 확인한 뒤 직접 commit하고, commit 뒤에는 `duoctl index`를 다시 실행한다.

## 7. 환경 변수와 설정 파일

### 7.1 환경 변수

빌드와 기본 실행에 **필수 환경 변수는 없다.** `.env` 파일을 쓰지 않으며 `.gitignore`가 `.env`, `.env.*`를 제외한다.

| 변수 | 쓰임 | 필수 |
|---|---|---|
| `DUO_LOCALE` | 출력 언어 `en`(기본) 또는 `ko`. `--locale`과 같다 | 아니오 |
| `OPENAI_API_KEY` | 선택 LLM 보조(`duoctl review --semantic`)에서 `llm.provider: openai-responses`일 때 API key | LLM을 켤 때만 |
| `llm.api_key_env`에 적은 변수 | `openai-compatible` provider의 API key를 담는 변수 이름(기본 `OPENAI_API_KEY`) | LLM을 켤 때만 |
| `DUO_RELEASE_ALLOW_DIRTY=1` | `release:pack`을 commit하지 않은 상태로 시험할 때(`clean: false`로 기록) | 아니오 |
| `VITEST_MAX_WORKERS` | 테스트 병렬 수 제한 | 아니오 |

API key는 파일에 저장하지 않고 환경 변수로만 받는다. `duoctl status`·`doctor`는 key 값을 보이지 않는다.

### 7.2 설정·데이터 파일 (대상 저장소에 생성)

| 경로 | 내용 | commit |
|---|---|---|
| `.duo-project/project.yaml` | 프로젝트 이름, 현재 milestone, 선택 `llm` 설정 | 예 |
| `.duo-project/intent/`, `milestones/`, `decisions/`, `specs/` | 사람이 확정한 Project Truth(Requirement, Decision, Constraint 등) | 예 |
| `.duo-project/reviews/adoption-*.json` | Adoption Baseline 기록 | 예 |
| `.duo-project/generated/graph.db` 등 | Project Graph(SQLite), `index-state.json`, `fingerprints.json` | 아니오(`.duo-project/.gitignore`) |
| `.duo-project/cache/`, `runtime/` | 분석 캐시, 실행 기록, Agent 연결 소유권 기록 | 아니오 |
| `.codex/config.toml` + `AGENTS.md` | Codex용 MCP 서버 항목과 안내 블록 | 예 |
| `.mcp.json` + `CLAUDE.md` | Claude Code용 MCP 서버 항목과 안내 블록 | 예 |

Codex에 생성되는 MCP 항목(관리 블록 안에서만 DUO가 수정·삭제한다):

```toml
[mcp_servers.duo-director]
command = "duoctl"
args = ["mcp", "--root-from", "git-cwd", "--agent", "codex"]
```

DB 접속 정보, 계정, 비밀번호 같은 프로퍼티 파일은 **없다.**

## 8. DB와 데이터 백업

DUO에는 DB 서버와 덤프 대상이 없다.

- 원본 데이터는 `.duo-project/`의 Truth 파일이다. Git에 commit되므로 저장소가 곧 백업이다.
- `graph.db`(SQLite)는 소스와 Truth로부터 다시 만들 수 있는 색인이다. 지우거나 옮긴 뒤 `duoctl index --full`로 처음부터 다시 만든다.
- 다른 PC로 옮길 때는 저장소를 clone하고 `duoctl index`만 실행하면 된다.

## 9. 외부 서비스

| 서비스 | 쓰임 | 계정·비용 |
|---|---|---|
| npm registry | 패키지 배포·설치 | 설치는 계정 불필요. 게시는 maintainer 계정과 2FA |
| GitHub | 원본 저장소, Issue, Actions CI, Release | 공개 저장소 기본 제공 |
| SSAFY GitLab | 제출용 mirror | — |
| OpenAI API (선택) | `review --semantic` 의미 보조. 기본값 `llm.provider: none`이면 네트워크 호출 없음 | 사용 시 사용자 API key와 비용 |
| Codex, Claude Code (선택) | DUO MCP 서버를 쓰는 Coding Agent | 각 Agent 계정 |

소셜 로그인, 결제, 클라우드 스토리지 같은 다른 외부 서비스는 쓰지 않는다.

## 10. 배포(릴리스) 시 특이사항

일반 사용자와 평가자는 4~6장만 하면 된다. npm 게시는 maintainer만 하고, 다음 조건을 모두 지킨다(`docs/release/checklist.md`).

1. `main`·`next`는 보호 브랜치다. PR, 작성자가 아닌 사람의 승인, 3 OS CI 통과가 있어야 병합된다.
2. 게시할 정확한 커밋과 tarball 해시를 Human Decision(`docs/conflicts.md`의 H-번호)으로 기록한다.
3. 같은 커밋에서 `pnpm release:preflight`(전체 검증·감사·재현성·npm dry-run)가 READY여야 한다.
4. 검증한 바로 그 tarball을 게시한다. stable은 `latest`, RC는 `next` dist-tag이며 npm 2FA가 필요하다.
5. 게시 뒤 `v<version>` tag와 GitHub Release를 만들고 `pnpm release:verify-published`로 registry 설치본을 다시 확인한다.

## 11. 문제 해결

| 증상 | 원인과 조치 |
|---|---|
| `pnpm install`이 engine 오류로 실패 | Node.js가 24.15.0 미만이다. Node 24 최신으로 올린다 |
| Windows에서 `pnpm release:pack`이 `ERR_UNKNOWN_FILE_EXTENSION` | standalone pnpm 문제(#90). `node scripts/release/pack.mjs`로 실행한다 |
| `duoctl init`이 `ADOPTION_HEAD_REQUIRED` | 대상 저장소에 commit이 없다. 첫 commit을 만든다 |
| `duoctl init`이 종료 코드 6, `ADOPTION_DIRTY_POLICY_REQUIRED` | commit하지 않은 변경이 있다. `--baseline-policy head`를 주거나 정리한 뒤 실행한다 |
| Windows에서 `init`/`index`가 `Debug Failure. Expected C:/… === C:\…`로 실패 | 가장 가까운 `tsconfig.json`·`jsconfig.json`에 JSON 문법 오류가 있다(#205). JSON을 고친 뒤 다시 실행한다. next에서는 #219로 수정되어 `TSCONFIG_INVALID` 경고만 남긴다 |
| `duoctl install`이 종료 코드 6, launcher를 찾지 못함(0.4.0-rc.1 이상) | Agent가 쓰는 PATH에 `duoctl`이 없다. 전역 설치를 확인하거나 `--launcher npx`로 다시 설치한다 |
| `review`·`context`가 `index-required` | `duoctl index`를 실행한다 |
| Codex `/mcp`에 `duo-director`가 없음 | 저장소를 Codex에서 trust하지 않았다(6.4) |
| 처음 실행이 느림 | Windows에서 설치 직후 첫 명령은 오래 걸릴 수 있다(기준 PC 약 18초, 이후 약 1.5초) |
