# T24.1 Overload evidence completeness (C217)

0.2.0 Milestone C(L1 Correctness)의 첫 task다. 결정: H-51. 이 문서는 [0.2.0 audit §15](0.2.0-audit.md#15-t24-첫-task-제안-c217-overload-safe-symbol-identity-구현하지-않음)의 제안(overload set 크기가 2 이상일 때만 signature를 Symbol ID에 붙임)을 대신한다.

## 1. 결과

Java·C#·C++ overload는 계속 Symbol 하나다(identity 불변). 그 Symbol이 가진 모든 위치(primary `source`와 `additionalLocations`)를 Context, Evidence, Review diff seed가 읽는다. 그래서 overload 본문이 조용히 빠지지 않는다. analyzer 출력, Graph, Symbol ID, 공개 형식, Truth와 baseline 해석은 그대로이고 migration이 없다. overload마다 따로 구별하는 member identity는 T24.2(C224)로 넘긴다.

## 3. Repository evolution 실험

`bench/experiments/overload-evolution.mjs`: 언어마다 임시 Git 저장소에서 case마다 before를 commit·index하고 after를 써서 incremental index, clean full rebuild, Context(과제 `Svc foo count` 등), Review(HEAD → WORKTREE)를 본다. 형태는 Java, C#, C++ class 안 정의, C++ `.h` 선언 + `.cpp` 정의 4가지다.

| case | Symbol ID | Graph | Context, 수정 전 | Review seed, 수정 전 | 수정 후 |
|---|---|---|---|---|---|
| 1. `foo()` → `foo()` + `foo(int)` | 그대로 | `additionalLocations` 생김 | `foo()` 본문만 | class(C++ `.cpp`: file) | 두 본문, seed는 method |
| 2. `foo()` + `foo(int)` → `foo()` | 그대로 | `additionalLocations` 사라짐 | `foo()` | method | 같음 |
| 3. `foo(int)` → `foo(String)` | 그대로 | 위치 그대로 | `foo()`만 | class·file | 두 본문, method |
| 4. `foo(int)` 본문 수정 | 그대로 | 행 그대로(파일 hash만) | `foo()`만, Evidence hash 불변 | class·file | 두 본문, method, hash 바뀜 |
| 5. 순서 변경 | 그대로 | primary가 바뀜 | `foo(int)`만(이번엔 `foo()`가 빠짐) | class(C#: class + method) | 두 본문, class + method(사이 빈 줄도 바뀜) |

20개 경우 모두 incremental = clean full이다. 지금 모델에서 Symbol ID는 overload를 더하고, 빼고, 바꾸고, 순서를 바꿔도 변하지 않는다. 이 성질은 지켜야 할 장점이다.

## 4. 두 층의 문제

**A. Evidence completeness.** C217에서 사용자가 보는 문제는 이것이다: Graph가 이미 가진 overload 위치를 Context, Evidence, Review가 읽지 않아 본문이 조용히 빠지고, 그 줄의 변경이 class나 file로 귀속된다. identity를 바꾸지 않고 고칠 수 있다.

**B. Overload member identity.** `foo()`, `foo(int)`, `foo(String)`을 따로 가리키는 일은 L2 call resolution(어느 overload를 부르는가)과 overload 하나를 지정하는 Truth 참조에 필요하다. 지금 이를 쓰는 곳이 없다: Java·C#은 CALLS가 없고(`calls-unresolved`), C++·Python의 same-file CALLS는 overload set을 추측하지 않는다(C174). A를 고친 뒤 설계해도 잃는 것이 없다.

## 5. 설계안 비교

| 기준 | A. set Symbol 유지 + 위치 소비 | B. set Symbol 유지 + member identity 추가 | C. overload만 signature Symbol로 분리 | D. 모든 callable을 signature identity로 |
|---|---|---|---|---|
| 기존 Symbol ID | 모두 그대로 | 그대로(set = 지금 ID) | overload 없는 것만 그대로 | 모든 callable이 한 번 바뀜 |

| overload 제거 | 그대로 | set 그대로, member가 사라짐 | 남은 `foo()`의 ID가 바뀜(churn) | 그대로 |
| signature 변경 | set 내용만 바뀜 | 그 member ID만 바뀜(다른 callable이므로 맞음) | ID 바뀜 | parameter 수정마다 삭제 + 추가 |
| incremental, clean full | 그대로(검증함) | 결정적이면 같음 | 같음 | 같음 |
| GraphStore | 변경 없음 | member 행(node 종류나 payload), `graph_schema_version`과 analyzer version | analyzer version | 모든 Symbol 행 |
| Context 품질 | set 전체가 한 item(본문 누락 없음, 하나만 고를 수 없음) | 하나 또는 전체 | 하나 | 하나 |
| Evidence 참조 | set 단위 hash가 모든 본문을 덮음 | member 단위 가능 | 개수가 바뀌면 옛 기록이 고아 | 옛 기록 전부 고아 |
| adoption baseline | 그대로 | offending을 set ID로 두면 그대로 | overload가 생기면 key가 바뀌어 pre-existing이 introduced로(BLOCK 가능) | 모든 Symbol key 변경, 형식 version 필요 |
| Decision·Truth 참조 | 그대로 | qualifiedName → set(그대로), member 문법은 선택 | qualifiedName이 여럿과 일치 → unresolved | 해석 규칙 전면 변경 |
| cache 무효화 | packet·LLM은 text hash로 자연 miss | 재분석 | 재분석 | 재분석 |
| 공개 계약 | 형식 불변 | 새 ID가 trace·impact·MCP에 나타남, version 판단 필요 | ID 집합이 시간에 따라 흔들림 | ID 형식 전면 변경 |
| 향후 L2 | 막지 않음(set을 anchor로 member를 아래에 둘 수 있음) | 가장 잘 맞음(못 고르면 set으로 fallback) | 가능하나 anchor 불안정 | type 해석 없이 signature text가 불안정 |

C는 정적 snapshot에서만 그럴듯하다. 저장소가 `foo()`에서 `foo()` + `foo(int)`로 바뀌는 순간 기존 `foo()`의 ID가 바뀌고, 그 ID를 가진 Review Record, baseline offending, impact 결과가 끊긴다. D는 그 churn을 처음 한 번에 모든 callable에 일으키고 이후 parameter 수정마다 다시 일으킨다.

## 6. 선택: T24.1은 Option A

우선순위(silent source omission 제거 → 기존 identity 보존 → clean full equivalence → 공개 계약 → L2를 막지 않음)를 모두 만족하는 가장 작은 변경이 A다. §3에서 A만으로 C217의 사용자 문제(Context 누락, Review 귀속, Evidence hash)가 모두 사라졌다. member identity는 B를 후보로 T24.2에서 설계한다.

## 7. 위치 규칙 (`nodeLocations`, graph package)

- **순서**: core `compareSourceLocations`의 source 순서. primary가 어느 것인지, analyzer가 어떤 순서로 만났는지와 무관하다.
- **중복**: 같은 범위가 두 번이거나 additional이 primary와 같으면 하나만 남긴다.
- **포함**: 같은 node의 다른 위치 안에 들어가는 위치는 새 text가 없으므로 뺀다. 한 줄에 선언이 둘이면(column이 다름) 둘 다 남는다.
- **범위**: node 자신의 파일 위치만. 형식이 맞지 않는 payload 항목은 무시한다. `source`가 없는 node는 위치가 없다.
- **LF, CRLF, BOM**: 위치는 canonical text(BOM 제거, CRLF → LF)의 줄과 column이다. `SourceReader`가 같은 canonical text를 읽으므로 slice에 `\r`이나 BOM이 없다(C# test는 BOM + CRLF 파일). C223의 raw fingerprint 규칙은 건드리지 않는다.
- **Context 표현**: L1 머리줄에 범위를 모두 쓴다(`Svc.java:4-6,8-10`). L2는 위치마다 선언 첫 줄과 주석 첫 줄, L3는 위치마다 범위와 바로 위 주석이고, 둘 다 source 순서로 빈 줄을 두고 잇는다. 본문 없는 선언만 여럿인 Symbol(C++ header)은 L2와 L3 text가 같아 위치가 하나일 때처럼 L2 하나만 남는다. 한 줄이 두 번 나오지 않게, 앞 부분이 보여 준 줄에서 시작하는 위치는 leading context 없이 정확히 자르고 겹치는 leading 줄은 뺀다. 공개 item의 `source`는 primary 하나 그대로다.
- **token budget**: item 단위다. pack이 tier 몫 안에서 item 전체의 level을 고르고, 파일당 L3 2개 상한은 그대로다. overload 일부만 L3로 넣는 일은 없다(budget이 모자라면 item 전체가 L2나 L1이 된다). 멤버가 후보인 class의 L3 제거는 Symbol의 모든 위치에 적용한다.
- **위치 무효화**: 위치는 node.source와 같은 index state에서 온다. index가 stale이면 freshness가 지금처럼 알린다. 위치 하나라도 slice되지 않으면(`SOURCE_LOCATION_INVALID`) item은 L1(범위 전체를 적은 머리줄)만 남고 diagnostic이 나간다. 일부 본문만 보여 주지 않는다.
- **삭제된 source**: 파일이 지워지면 derived node가 없어지고 위치도 없다. Review의 deleted-unresolved limitation은 그대로다.
- **이름이 바뀐 source**: 경로가 ID의 일부이므로 새 경로의 새 Symbol이 된다(T24.1 이전과 같음). 위치는 새 파일을 따른다.
- **Evidence**: Symbol text는 위치별 정확한 slice를 source 순서로 `\n`으로 이은 것이고 contentHash는 그 hash다. pointer의 `lines`는 primary 범위다(형식 불변). 위치가 하나인 Symbol은 text와 hash가 이전과 같다.
- **Review diff seed**: hunk가 Symbol의 어느 위치와 겹치면 그 Symbol이 seed다. 가장 안쪽 규칙은 겹친 위치의 폭으로 비교한다.

## 8. Contract와 migration gate (Phase 11)

| 질문 | 답 | 근거 |
|---|---|---|
| Graph persisted state migration | 필요 없음 | analyzer 출력과 Graph 행이 그대로다. real-world 3개 저장소의 Graph SHA-256이 수정 전후 같다(§9) |
| 기존 `.duo-project` index 재생성 | 필요 없음 | analyzer version, `graph_schema_version`, index state 형식 불변 |
| format·schema version bump | 필요 없음 | `duo.context-packet/1` item 필드, evidence pointer, `duo.review/1`, `duo.review-record/1`, adoption baseline 형식 그대로 |
| old cache 잘못 재사용 | 없음 | packet cache key(dependency digest)에 각 level text의 hash가 있어 text가 바뀐 Packet은 miss, 나머지는 같은 Packet이라 hit이 맞다. analysis cache는 analyzer 출력이 같다. LLM cache는 redacted request hash라 바뀐 요청은 miss |

`CONTEXT_POLICY_VERSION`은 올리지 않았다(2 유지). `policy.ts`는 표현이 바뀌면 version을 올려 옛 cached Packet을 맞지 않게 하라고 하지만, 이번 변경은 Symbol 위치가 둘 이상인 item의 level text만 바꾸고 그 text가 digest에 들어간다. version을 올리면 overload와 무관한 모든 Packet의 `dependencyDigest`가 바뀌어 "overload 없는 Packet 불변" 조건을 깨뜨린다(C225).

**보이는 동작 변화(형식은 그대로).** 위치가 둘 이상인 Symbol에서만: Context item text와 L1 범위, 그 Symbol의 Evidence contentHash, 비 primary 위치를 고친 hunk의 Review seed(class·file → Symbol). seed가 바뀌면 그 Symbol을 다스리는 Decision이 claim으로 잡히므로 verdict가 달라질 수 있고, 이것이 의도한 수정이다. 언어와 무관한 Graph 규칙이라 TypeScript overload signature·getter/setter 쌍, Python 같은 이름 재정의에도 적용된다. T23 저장소의 TypeScript·Python 쪽에는 그런 Symbol이 0개다.

## 10. Signature 설계 조사 (Phase 6, T24.2 입력)

`bench/experiments/signature-probe.mjs`로 고정된 grammar가 syntax로 주는 것을 확인했다. 아무것도 구현하지 않았다. 원칙: 이름 + 인자 수로 identity를 만들지 않고, AST가 주지 않는 semantic type을 추측해 canonicalize하지 않는다. L1에서는 UNKNOWN·partial을 허용한다.

| 언어 | 요소 | grammar가 주는 것 | identity 후보 |
|---|---|---|---|
| Java | owner, nested type | 지금 identity의 `Type`(nested는 `Outer.Inner`) | set identity 그대로 |
| | name, constructor | `method_declaration` name, `constructor_declaration`(이름 = class) | set identity 그대로 |
| | parameter type | `formal_parameters`의 `formal_parameter` `type` field(`integral_type`, `type_identifier`, `generic_type`, `scoped_type_identifier`) | type text(공백 정규화). `List<String>`과 `java.util.List<String>`은 다르다(type 해석 없음) |
| | array | `array_type` + `dimensions`, 또는 이름 쪽 `dimensions`(`int a[]`) | 두 형태를 같은 `int[]`로 접는 것은 syntax 규칙이라 허용 |
| | varargs | `spread_parameter`(type field 이름 없음) | `T...` |
| | generic | method `type_parameters`(`<U>`) | type parameter 이름은 identity에서 빼고 개수만(erasure에 맞춤) 검토 |
| | 제외 | `modifiers`(final, annotation), parameter 이름 | — |
| C# | namespace/type | 지금 identity(`Game.Player`) | set identity 그대로 |
| | parameter type | `parameter_list`의 `parameter` `type` field(`predefined_type`, `nullable_type`, `generic_name`, `array_type`) | type text. `int?`와 `Nullable<int>`는 다르다 |

| | params | `params int[] d`는 `parameter` node 없이 `parameter_list`에 type·name field로 바로 붙는다 | grammar 특이점. 별도 처리 필요 |
| | 기본값 | `parameter` 안 literal | 제외 |
| | generic arity | `type_parameter_list` | 개수 포함(C#은 arity로 overload 가능) |
| | constructor, destructor | `constructor_declaration`, `destructor_declaration`(지금 Symbol, destructor는 `~P`) | set identity 그대로 |
| | operator | `operator_declaration`, `conversion_operator_declaration`: name field 없음, 연산자 token은 이름 없는 child | 지금 Symbol이 아님. 연산자 text로 이름을 만들지 별도 결정 |
| | explicit interface | `explicit_interface_specifier`(`I.`). extractor는 name field만 읽으므로 지금 `void I.Move()`와 `void Move()`는 같은 identity로 합쳐진다 | 포함(`I.Move`와 `Move`는 다른 member) |
| | indexer | `indexer_declaration`, `bracketed_parameter_list` | 지금 Symbol이 아님 |

| | static·member | `storage_class_specifier`(선언에만) | 정의 쪽에 없으므로 identity에 넣지 않음 |
| | constructor, destructor | 이름 = class, `destructor_name` | set identity 그대로 |
| | operator | `operator_name`(지금 Symbol 이름, 예: `A.operator=`) | set identity 그대로, parameter로 구별 |

## 11. T24.2 제안: overload member identity (설계와 ADR)

Option B 방향. set Symbol(지금 ID)을 anchor로 두고, 그 아래에 overload member를 syntax signature로 구별한다.

- 결정할 것: member를 Graph node로 둘지(새 entity type이나 Symbol kind, `graph_schema_version`) payload로 둘지, member ID 문법, 같은 signature 충돌 diagnostic, member를 보여 줄 surface(trace, impact, MCP)와 각 형식 version, Truth의 member 참조 문법(선택), baseline offending은 set ID 유지.
- 안정성 조건: overload 추가·제거에 set ID와 다른 member ID가 변하지 않는다. member ID는 위치·순서가 아니라 syntax signature만으로 정한다.
- 구현 시점: member identity를 쓰는 첫 기능(L2 call resolution이나 member 단위 Truth 참조)과 함께. 그 전에는 ADR까지만.
- C218(C++ 선언·정의)과 C219(Python source root)는 member identity와 독립이다. 사용자가 보는 정확성 문제라 먼저 진행할 수 있다.
