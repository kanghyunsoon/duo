# Safe index refresh (T179)

Related: [#4](https://github.com/kanghyunsoon/duo/issues/4), Jira S15P31A106-255 and S15P31A106-321.

The baseline is `next` `5e220bf`. [PR #125](https://github.com/kanghyunsoon/duo/pull/125)
already established concurrent cold and incremental index correctness, explicit write refusal and
independent worktree state, with Windows, Ubuntu and macOS verification. Its oracle is reused here.

## Recovery contract

`refreshIndexIfSafe(root, { registry?, historyWindow?, lockTimeoutMs? })` is an opt-in Graph API.
Success returns `{ refreshed: true }` after recovery, or `{ refreshed: false }` when another writer
already made the index current. Failure returns diagnostics and no value. The MCP caller must keep
`index-required`, include the reason, and never proceed using a failed refresh. On successful refresh
it must include both a structured refresh field and a human-readable note in its answer.

Recovery requires complete Project Truth and an existing, compatible index. Missing and incompatible
indexes require an explicit `duoctl index`; recovery never bootstraps a full index or recreates an
incompatible database. Freshness is checked after acquiring the lock, using content hashes and the
existing inspection rules. There is no TTL or mtime shortcut.

Every loaded Truth file must be observed by the current index scan. Git-ignored or
index-excluded Truth can be loaded directly by the Truth loader while ordinary freshness inspection
misses its edits. Recovery conservatively refuses these unobserved inputs, even on an apparently
current index, and asks the caller to check the ignore/include rules and explicitly index again.
Newly added Truth that the current scan observes can be incrementally refreshed as usual.

All index writers share `.duo-project/generated/index-writer.lock`, including CLI `index`, `init`,
and context/review `--refresh`. CLI writer wrappers acquire it before opening the writable database,
so schema recreation is also serialized. The lock covers analysis cache writes and pruning, graph
transactions, `index-state.json`, fingerprints, and recovery's post-write inspection. Direct `indexRepository`
calls acquire it as well. Worktrees have separate generated state and separate locks.

Timeout uses `GRAPH_WRITE_REFUSED` with an explicit `Index lock timeout` message. The default wait
is 5 seconds. The lock is an operating-system file lock held through an otherwise empty SQLite
database (T180). It belongs to the holding process: when that process exits for any reason (crash,
Ctrl+C, kill), the operating system releases it, so no stale lock remains and no lock is ever taken
over by age. A writer killed after its graph commit but before its state file leaves a token
mismatch, which the next explicit index rebuilds as before; recovery refuses that state. The lock
directory `.duo-project/generated/index-write.lock` written by #143 is no longer used and can be
deleted.

The stability guard uses the run's own facts as its snapshot: the loaded Project Truth (also files Git
ignores), the fingerprints of the configured scan (`index.include`/`exclude`), the Git state read
before the scan, and the configuration files the resolver reads (including lookups of files that do
not exist yet). Source text is checked against its fingerprint whenever it is read. A run that writes
to the graph scans again once right before its transaction and then, synchronously up to the commit,
checks the configuration reads, recorded configurations, Truth and database identity; any difference,
or a Git state that cannot be read, refuses with `Index inputs changed`. An explicit `duoctl index`
that writes nothing needs no second read, and a change that lands after its pre-commit check is seen
as stale by the next run, as before #143.

This is the intended consistency scope of an explicit `duoctl index` (F3, maintainer decision T182).
It keeps the CLI contract from before #143 and claims nothing stronger: such a run can report success
while a file changed during a run that wrote nothing, or after its pre-commit check. What it does
guarantee is that the database token, `index-state.json` and the fingerprint file always describe the
same run, so the next run or inspection sees the change as stale and indexes it. A mismatch between
them is a defect, not part of this scope; a new integrity defect or user-visible harm gets its own Issue.
Regression: "keeps DB token, index state and fingerprints consistent ... (F3)" in
`packages/graph/src/incremental/refresh.e2e.test.ts`.

Recovery is stricter: `refreshIndexIfSafe` takes the scan, Git state, recorded configurations and
Truth at the start and compares them again before it reports success, on both the "already current"
and the "refreshed" path, and it also inspects freshness after its write. A change at any point of
the call is never reported as a successful refresh. An interruption after the graph commit can leave
regenerable state requiring an explicit rebuild; it is never reported as a successful refresh. Files
can still change after a call returns; this is a bounded operation, not a background watcher or a
lock on user edits. (T180 replaced #143's three full-repository snapshots per run, which made a no-op
`duoctl index` several times slower; T181 kept the whole-call check for recovery only.)

Only regenerable state is written. CLI defaults and exit contracts remain explicit. Decision
authority, Truth formats and verdict semantics are unchanged.
Explicit CLI indexing retains its existing sidecar-write warning behavior; automatic recovery
requires successful sidecar writes and returns failure for those same errors.
