# 0.2.1 Product Thesis Review (T32.5)

날짜: 2026-10-04. 기준: main `8559913`, 공개 `@duo-director/cli@0.2.1`(`v0.2.1` = `1316bdf`). 결정: H-66.

구현 task가 아니다. production code, test, package, version, dependency, release tooling, README positioning을 바꾸지 않았다. 질문은 하나다. **DUO를 지금 형태의 standalone product로 계속 적극 개발할 근거가 있는가.**

판정 어휘:

- thesis 항목: **Validated technically**(구현이 의도대로 동작함을 확인), **Partially supported**(일부만 근거가 있음), **Weakened**(시험했고 대체재가 같은 결과를 냄), **Untested**(시험한 적 없음), **Not implemented**, **Contradicted**(시험 결과가 주장과 반대).
- option 평가: **Strong**(그 기준에서 이 option에 유리), **Moderate**, **Weak**(불리), **Unknown**. 숫자 점수와 총점은 쓰지 않는다.

"아직 시험하지 않았다"는 "DUO가 낫다"는 뜻이 아니다. 반대로 두 fixture에서 대체재가 따라왔다는 사실이 제품 전체가 무가치하다는 뜻도 아니다. 이미 쓴 개발 비용은 앞으로의 전략 근거로 쓰지 않는다.

## 1. Executive decision

| 항목 | 결정 |
|---|---|
| Primary | **Option C — Validation-only maintenance mode** |
| Fallback | **Option E — Maintenance-only OSS / portfolio** |
| Feature 개발 | 0.2.1 이후 새 product feature 개발을 동결한다. security, correctness, compatibility, packaging maintenance만 허용한다 |
| Thesis 상태 | Standalone product thesis는 **Unproven**. T32 checkpoint **C. Thesis materially weakened**를 그대로 유지한다 |
| 재개 조건 | §14 External Validation Gate를 통과하고 새 Human Decision을 기록한 뒤에만 feature roadmap을 다시 연다 |
| 전환 조건 | Gate 결과가 kill 쪽이거나 독립 참여자를 모으지 못하면 E로 전환한다 |
| 다음 task | T33을 Contributor Surface가 아니라 **External Validation**(protocol과 모집 준비)으로 재정의한다. 이 문서에서는 시작하지 않는다 |

이유를 줄이면 이렇다. DUO는 기술적으로 동작한다(§7 질문 1, 긍정). 그러나 두 공개 benchmark에서 50~70줄대 bespoke gate와 문서를 읽은 Codex가 DUO와 같은 판정을 냈다(질문 2, 약화). 실제 사용자가 그 차이 때문에 DUO를 설치하고 유지한다는 evidence는 하나도 없다(질문 3, 미지). 남은 차별화 후보는 모두 Decision 수, 시간, 사람 수, agent 수가 늘어날 때만 드러나는 성격이어서 작성자가 만드는 fixture를 더 늘려도 답이 나오지 않는다. 기능을 더 만드는 것도 이 질문에 답하지 않는다. 반대로 지금 E로 가면 한 번도 시험하지 않은 가설을 시험 없이 버리게 된다. C는 이미 공개된 0.2.1로 그 가설을 시험할 수 있고 새 개발이 필요 없다.

## 3. What T31 falsified

Benchmark 1(Legacy + New Violation, 한 고정 규칙, TypeScript)에서 published DUO 0.2.0은 다음을 했다.

- 새 위반(introduced)을 BLOCK했다(10/10).
- 건드린 기존 위반(pre-existing-touched)과 건드리지 않은 기존 위반을 구분했다.
- 10/10 같은 결과를 냈다(raw output 차이는 시간 값뿐).
- claim에 Decision ID, 파일·symbol·diff 범위, content hash를 붙였다.

그러나 같은 fixture에서 두 대조군이 같은 핵심 분류를 냈다.

- 57 code line DIY gate가 같은 네 갈래 분류와 blocking 종료 코드를 냈다.
- Codex review + `AGENTS.md`가 5/5 같은 핵심 위반을 같은 우선순위로 판정했다.

따라서 다음 주장은 더 이상 DUO의 차별점으로 쓸 수 없다.

- "fixed architectural rule violation detection에서 DUO가 native AI review보다 우월하다."
- "legacy/new 분류는 DUO만 가능하다."
- "이 정도 Decision compliance를 위해 DUO가 필수다."

추가로, 위반이 없는 정상 변경(control-only)에서 DUO만 knowledge gap 때문에 WARN을 냈다(C239). DIY는 PASS, Codex는 3회 중 2회 finding 없음이었다.

## 4. What T32 falsified

Benchmark 2(Adoption Provenance + Supersession)에서 DUO는 다음을 했다.

- adoption 뒤에 들어온 위반을 기존 부채로 면책하지 않았다. adoption baseline과 diff base가 달라도 그랬다.
- supersede된 D-001을 current rule로 적용하지 않았다.
- current인 D-002를 집행했다.
- 10/10 같은 결과를 냈다.

그러나 대조군이 같은 핵심 판정을 재현했다.

- DIY-1: 54 code lines + 7줄 adoption state로 Scenario A를 재현했다.
- DIY-2: 73 code lines + 16줄 registry로 Scenario A와 B를 재현하고 supersession link를 검증했다. 출력이 current authority를 DUO review보다 직접 보여 줬다.
- Codex + 사람이 관리한 versioned docs: Scenario A 5/5, B 5/5 같은 결론이었고 control 6회에서 잘못된 finding이 0이었다.

DUO만 한 일(사람 확정 강제, adoption·supersede 기록 자동 생성, evidence hash, account·model 불필요)은 이 benchmark에서 다른 판정을 하나도 만들지 않았다.

이 review의 출발점은 T32 checkpoint **C. Thesis materially weakened**다. 이 결론을 완화하려고 benchmark의 의미를 사후에 바꾸지 않는다. 두 benchmark는 DUO가 틀렸다는 증거가 아니다(판정은 모두 맞았다). DUO만 맞힌 경우가 없었다는 증거다.

## 7. Technical merit, differentiation, value, moat

세 질문을 따로 답한다.

1. **DUO는 기술적으로 제대로 동작하는가?** 대체로 **예**. T31·T32에서 모든 판정이 맞았고 10/10 재현됐다. 3 OS CI와 installed conformance가 통과했다. 0.2.1에서는 published artifact의 설치 트리가 기록된 트리와 같음을 npm 10/11/12에서 확인했다.
2. **DUO가 하는 일을 다른 방식보다 쉽게·안정적으로 제공하는가?** **약화**. 시험한 시나리오에서 판정 차이가 없었다. 운영 차이는 있다(DUO는 rule별 custom code 0줄, account·network·model 불필요, 기록 자동 생성, hash). 반대 방향의 운영 차이도 있다(설치, init, 대화형 확정, 수동 index, C239 WARN). 안정성에서도 DIY gate 역시 결정적이어서 우위가 관찰되지 않았다.
3. **그 차이가 사용자가 새 tool을 설치하고 유지할 만큼 중요한가?** **Unknown**. 외부 사용 evidence가 없다.

차별점 후보마다 네 개념을 섞지 않는다.

## 10. Substitute analysis

T31·T32에서 실제로 돌린 대조군을 그대로 쓴다. 대체재를 약하게 만들지 않는다.

| 축 | A. Docs + `AGENTS.md`·`CLAUDE.md` + Codex | B. Docs + 작은 결정적 gate + CI | C. Native review·rules 제품(Copilot, Bugbot, Qodo) |
|---|---|---|---|
| 시험 여부 | 실제 실행(T31 5+3회, T32 5×2+3×2회) | 실제 실행(DIY-0/1/2 각 10회) | NOT RUN. T27.5 공식 자료만 |
| 판정 | DUO와 같음(T31 5/5, T32 A·B 5/5, control 잘못된 finding 0/6) | DUO와 같음(DIY-1: A, DIY-2: A·B) | 알 수 없음 |
| 비용 | account, hosted model, review당 34~82 s, 사람이 문서 5개를 손으로 갱신, 출력은 prose(고정 필드·hash 없음) | 54~73 code lines, JSON state·registry(registry는 손으로 편집), review 1 s 미만 | 각 platform 계정. rules-aware review는 존재(T27.5) |
| 강점 | 이미 쓰는 도구, 설치 없음, 넓은 문제 인식 | 결정적, 빠름, 정확히 원하는 규칙, 의존성 없음 | PR 흐름에 내장, 조직 정책 |
| 관찰된 약점 | 문구가 매번 다름, 1/3 run에서 관계없는 P1, harness(checkout)에 민감 | fixture를 알고 작성됨, 규칙 하나씩 코드로 표현, link 검증 외에는 기록 검증 없음 | Decision lifecycle·adoption baseline은 Unverified |

**어떤 규모·복잡도부터 general tool이 bespoke solution보다 유리해지는가?** **Unknown**. 가설로는 Decision 수 × rule 종류 × 언어 × 사람 수가 커지면 bespoke gate와 손으로 쓴 docs의 유지 비용이 DUO의 Decision 하나당 YAML 비용보다 빨리 늘 수 있다. 그러나 이를 지지하는 측정이 없다. DIY-2는 오히려 규칙을 data로 옮기면서 작은 rule engine 쪽으로 일반화될 수 있음을 보였다.

## 11. Strategic options A–E

| Option | 내용 |
|---|---|
| A. Continue standalone unchanged | broad Project Direction Layer thesis와 feature roadmap(C229, 언어, provider 등)을 계속 추진 |
| B. Narrow standalone product | 핵심을 repository 소유·사람 확정 engineering Decision + 결정적 provenance·compliance로 좁히고 Context·LLM·UI는 supporting capability로 둠 |
| C. Validation-only maintenance | 0.2.1을 유지보수하고 새 feature를 동결, 외부 실사용 evidence를 먼저 수집 |
| D. Toolkit / reference pivot | end-user product 대신 Decision provenance primitive나 reference implementation으로 좁힘(코드 재구성은 하지 않음) |
| E. Maintenance-only OSS / portfolio | 제품 성장 목표를 멈추고 security·correctness·compatibility·packaging만 유지 |

| 기준 | A | B | C | D | E |
|---|---|---|---|---|---|
| Current evidence support | Weak | Weak | Strong | Weak | Moderate |
| User pain clarity | Weak | Moderate | Moderate | Weak | Weak |
| Substitute pressure | Weak | Weak | Moderate | Weak | Strong |
| Adoption friction | Weak | Moderate | Moderate | Weak | Strong |
| Maintenance burden | Weak | Moderate | Strong | Weak | Strong |
| Technical leverage already built | Strong | Strong | Strong | Moderate | Moderate |
| Speculative new work required | Weak | Moderate | Strong | Weak | Strong |
| Ability to falsify cheaply | Weak | Moderate | Strong | Weak | Weak |
| External validation path | Weak | Moderate | Strong | Weak | Weak |
| OSS contributor potential | Unknown | Unknown | Weak | Unknown | Weak |
| Future feature pressure | Weak | Moderate | Strong | Weak | Strong |
| Risk of building without demand | Weak | Moderate | Strong | Weak | Strong |

읽는 법: Strong은 그 기준에서 option에 유리하다는 뜻이다. 예를 들어 maintenance burden이 Strong이면 부담이 작고, substitute pressure가 Strong이면 대체재 압력이 그 option의 목표를 위협하지 않는다는 뜻이다. "Technical leverage already built"는 새 작업 없이 재사용할 수 있는 정도이며, 이미 쓴 비용을 계속할 이유로 쓰지 않는다.

- **A**: evidence가 지지하지 않는다. 검증되지 않은 수요를 전제로 가장 많은 새 작업을 요구한다.
- **B**: 좁힌 핵심이 바로 T31·T32에서 DIY가 재현한 부분이다. 좁히는 것만으로는 evidence가 생기지 않는다. 다만 B의 narrow claim은 C가 시험할 가설로 쓸 수 있다.
- **C**: evidence 상태(Unproven)와 맞는다. 새 개발 없이 0.2.1로 시험할 수 있고, 결과가 어느 쪽이든 다음 결정을 내릴 수 있다. 약점은 frozen roadmap이 contributor를 모으지 못한다는 점과, 참여자를 못 모으면 시간만 쓴다는 점이다.
- **D**: primitive에 대한 수요 evidence가 없고 restructuring과 API 안정화라는 새 작업이 필요하다.
- **E**: 유지 부담이 가장 작고 약화된 evidence와 맞는다. 하지만 아직 한 번도 외부에서 시험하지 않은 longitudinal 가설을 시험 없이 닫는다.

## 12. Recommended path

### 판단 질문

| 질문 | 답 |
|---|---|
| Q1. DUO 없이 docs + Codex + 50~100줄 gate로 현재 핵심 사용 사례의 대부분을 처리할 수 있는가? | **예, 시험한 범위에서는.** 한 규칙 탐지, adoption provenance, supersession 모두 54~73줄 + 작은 JSON, 또는 Codex + 손으로 쓴 docs로 같은 판정이 나왔다. 시험하지 않은 규모에서는 모른다 |
| Q2. DIY가 프로젝트가 커지면 복잡해진다는 evidence가 있는가? | **아직 가정뿐이다.** 관찰된 것은 57 → 54 → 73줄의 작은 증가와 DIY-1이 두 번째 규칙을 표현하지 못한 점이다. DIY-2는 규칙을 data로 옮겨 일반화했다 |
| Q3. 사람 확정 강제는 painkiller인가, ceremony인가? | **Unknown, 현재 evidence로는 ceremony 쪽.** benchmark에서 확정 강제는 다른 판정을 만들지 않았고 Decision마다 대화형 단계를 더했다. agent가 스스로 규칙을 확정하지 못하게 하는 무결성 성질은 있지만, 사용자가 그것을 원한다는 근거가 없다 |
| Q4. model 독립적 결정적 review를 사용자가 원한다는 evidence가 있는가? | **없다.** Codex도 같은 판정을 반복했고 차이는 문구, 시간, account였다. CI gate가 필요한 사용자에게는 DIY gate도 결정적이다 |
| Q5. Context Compiler가 실제 workflow에서 채택 이유가 된다는 evidence가 있는가? | **없다.** 저장소 전체 대비로는 작지만 관련 파일만 읽는 경우보다 크다(합성 fixture). 실제 agent 사용은 측정하지 않았다 |
| Q6. agent 중립성이 두 agent 이상을 병행하는 사용자에게 충분한 가치가 있는가? | **Unknown.** 그런 사용자 evidence가 없고, `AGENTS.md`도 여러 agent가 읽는다 |
| Q7. 사용자 acquisition 없이 C229·언어·provider·enterprise 기능을 더 만드는 것이 합리적인가? | **아니다.** checkpoint C와 T32 규칙(새 feature 전에 thesis review)에 어긋난다. T00 roadmap도 v0.2 integration의 착수 조건을 "실제 프로젝트 2개 이상에서 사용"으로 두었다([12-roadmap.md](../12-roadmap.md#v01-이후-별도-spec-작성-후-착수)) |
| Q8. 가장 싸게 틀렸음을 확인할 next experiment는? | 새 코드 없이 0.2.1로 독립 외부 maintainer가 자기 저장소에서 쓰게 하는 §14 gate다. 가장 빠른 부정 신호는 모집 자체다. 독립 maintainer가 시도할 의사가 없으면 그것도 evidence다. 작성자가 만드는 규모 fixture(Benchmark 3)는 더 싸지만 Q2만 다루고 편향이 있어 gate를 대신하지 않는다 |

### 결정

**Primary: Option C — Validation-only maintenance mode.**

- 0.2.1 이후 새 product feature 개발을 동결한다.
- 허용: security, correctness, compatibility, packaging maintenance와 외부 검증에 필요한 문서·protocol·release.
- validation 기간에 참여자가 찾은 correctness bug는 고칠 수 있다. 의미가 바뀌는 수정(C239 같은 verdict 의미)은 Human Decision이 필요하다.
- 공개 positioning은 바꾸지 않는다(§17, §18, T32.6 후보).

**Fallback: Option E — Maintenance-only OSS / portfolio.** Gate가 kill 쪽으로 나오거나, inconclusive가 두 번이거나, 모집 기간 안에 독립 참여자를 모으지 못하면 E로 전환한다.

**정확한 이유.** feature를 더 만들 근거를 입증해야 하는 쪽은 개발 재개다(checkpoint C). 현재 evidence는 그 입증을 하지 못한다. 시험한 핵심 시나리오에서 대체재가 같은 판정을 냈고, 실사용 evidence가 0이다. 남은 차별화 후보(규모, 기록 drift, 사람·agent 여럿, 장기 history)는 실제 사용으로만 시험된다. C는 그 시험을 새 개발 없이 하는 가장 작은 option이고, 결과가 continue든 kill이든 다음 결정을 바로 내릴 수 있다. E는 시험 기회 없이 가설을 닫으므로 C의 실패 뒤에 둔다.

## 13. Why alternatives were rejected

- **A**: 원래 thesis의 넓은 범위(A~G)를 유지하려면 아직 시험하지 않은 가치에 가장 많은 개발을 걸어야 한다. checkpoint C에서 default가 될 수 없다.
- **B**: 좁히는 방향 자체는 맞다. 그러나 좁힌 핵심(Decision provenance·compliance)이 정확히 benchmark에서 대체재가 따라온 부분이다. B를 지금 product decision으로 택하면 검증되지 않은 positioning에 커밋하게 된다. B의 narrow claim은 C가 시험할 가설로 들어간다.
- **D**: end-user 수요가 불확실한데 개발자 primitive 수요는 더 불확실하다. restructuring, API 안정성, 문서라는 새 비용이 생긴다.
- **E**: 지금 evidence로도 정당화될 수 있는 가장 가까운 대안이라 fallback으로 둔다. 다만 외부 사용이 한 번도 없던 상태에서 닫으면, 그 판단도 evidence 없이 내린 것이 된다.

## 14. External Validation Gate

### 시험할 가설(좁힌 형태)

> 실제 저장소에서 coding agent와 일하는 개인·소규모 팀이 사람이 확정한 engineering Decision을 DUO에 두면, 그들이 대신 쓸 방법(docs + 지시 파일, 작은 gate, native review)보다 적은 유지 노력으로 drift를 잡거나 authority를 유지한다. 그리고 maintainer 도움 없이 계속 쓴다.

### 참여 조건과 최소 표본

| 조건 | 최소 | 왜 이 정도면 결정할 수 있는가 |
|---|---|---|
| 독립 외부 maintainer | 3명, 서로 다른 실제 저장소 3개(benchmark 작성자와 그 저장소 제외, 금전 관계 없음, 직접 활발히 개발 중이고 coding agent를 하나 이상 씀) | 1명은 사람과 도구를 구분할 수 없고, 2명은 결과가 갈리면 결정할 수 없다. 3명은 다수 결과가 존재하는 가장 작은 집합이며, 저장소 모양이 적어도 두 가지는 다르게 된다. 통계적 유의성이 아니라 go/no-go를 위한 질적 표본이다. 결과가 갈리면 늘린다 |
| 사용 기간 | 참여자마다 정상 개발 2주 이상(약 10 working days) | 시험 대상 주장(adoption 뒤 drift, supersession, Truth 유지, 반복 사용)은 시간이 지나야 드러난다. 한 session은 setup만 측정한다. 2주는 여러 review 주기와 결정을 바꿀 기회를 적어도 한 번 포함한다 |
| 확정 Decision | 참여자마다 3개 이상, 가능하면 enforcement 종류 2개 이상(symbols, paths, dependencies) | benchmark는 Decision당 규칙 하나였다. 규칙이 여럿이고 종류가 다를 때가 bespoke gate 비용이 하나의 gate와 달라지기 시작하는 가장 작은 경우다 |
| lifecycle 사건 | 기간 중 Decision 추가 또는 supersede 1회 이상 | lifecycle 주장은 결정이 바뀌어야 시험된다 |
| 비교 기준 | 참여자가 DUO 대신 쓸 방식을 처음에 적고, 가능하면 일부 기간 병행 | 질문은 "DUO가 동작하는가"가 아니라 "그 방식보다 DUO를 계속 쓰겠는가"다 |

### 진행 규칙

- 참여자는 공개 문서와 공개 package(0.2.1 또는 그 뒤의 maintenance release)만 받는다.
- maintainer의 도움은 공개 release로 내는 bug fix를 빼고 모두 기록한다. 도움 횟수 자체가 metric이다.
- 기간 중 feature는 바꾸지 않는다.
- telemetry를 넣지 않는다. 자료는 참여자가 고르는 local report(`duoctl stats` 요약, review JSON 수, 직접 적은 유지 시간)와 끝의 고정 질문 interview다.

### Metric

| Metric | 정의 |
|---|---|
| install → first useful review | 설치부터 참여자가 "쓸모 있었다"고 한 첫 review까지 시간 |
| confirmed Decisions created | 기간 중 확정·supersede한 Decision 수 |
| useful findings | 참여자가 행동으로 이어졌다고 한 claim·gap |
| false/noisy findings | 참여자가 무시하거나 틀렸다고 한 claim·gap(C239 WARN 포함, 따로 셈) |
| maintenance minutes | Truth 작성·확정·index·설정에 쓴 시간(참여자 기록) |
| alternative chosen | 기간 중 또는 끝에 docs·DIY·native review로 돌아갔는가 |
| repeated use | review·context를 다른 날에 반복했는가 |
| retained without help | maintainer 도움 없이 끝까지 썼고 기간 뒤에도 계속 쓰겠는가 |
| agent reuse | 둘 이상의 agent에서 같은 Truth를 썼는가(해당하는 경우) |
| abandon reason | 그만뒀다면 이유 |

stars, downloads, 설치 수만으로 판단하지 않는다.

### 결과 규칙

- **Continue**(새 Human Decision으로 좁힌 roadmap 재개 자격): 참여자 다수(3명 중 2명 이상)가 다음을 모두 충족한다. 끝까지 도움 없이 사용, 자기 기준 방식으로는 놓쳤거나 더 많은 노력이 들었을 useful finding이나 authority·재사용 사건 1개 이상, Truth 유지 노력이 가치에 비해 받아들일 만함, 기준 방식보다 DUO를 계속 쓰겠다는 판단.
- **Kill → E**: 다수가 기준 방식을 택하거나, 기간 전에 그만두거나, 모든 참여자를 합쳐 useful finding이 0이거나, Truth가 방치되거나, 참여자 판단으로 noisy finding이 useful finding보다 많다.
- **Inconclusive**(갈림, 활동 부족): 참여자를 더해 한 번 연장한다. 두 번째도 inconclusive면 E.
- **Recruitment failure**: T33에서 사람이 정한 모집 기간 안에 독립 참여자 3명을 모으지 못하면 수요가 약하다는 evidence로 보고 E를 결정한다(또는 그 시점에 새 Human Decision).

## 17. Claims DUO must stop making

- fixed architectural rule violation 탐지에서 DUO가 native AI review보다 우월하다.
- legacy·new(pre-existing·introduced) 분류는 DUO만 할 수 있다.
- 이 정도 Decision compliance에는 DUO가 필요하다.
- adoption provenance나 supersession을 하려면 DUO가 필요하다(DIY-1·DIY-2가 재현).
- Context Compiler가 focused agent 대비 token을 줄인다(관찰된 것은 저장소 전체 대비뿐).
- 0.2.1 packaging·release 품질이 제품 차별성이나 시장성의 근거다.
- category unique, moat, "first/only"(H-61, H-63).

## 18. Claims DUO may still make

capability에 관한 사실로만, 비교 우위 없이 쓴다.

- agent는 Decision을 제안만 하고, 확정은 사람이 terminal(ID 재입력)이나 local UI에서 한다.
- core review는 LLM 없이 실행되며 같은 저장소 상태에서 같은 결과를 낸다(T31·T32 10/10).
- review claim은 Decision, 파일·line 범위, diff hunk, content hash를 가리킨다.
- adoption baseline을 init 때 기록하고, Decision supersede와 lock을 상태로 유지한다.
- core review에 account, network, model이 필요 없다.
- Codex와 Claude Code가 MCP로 같은 repository Truth를 읽는다.
- 공개 benchmark가 대조군이 같은 판정을 낸 결과까지 raw evidence와 함께 공개한다.
- 합성 5,000파일 fixture에서 Packet은 source corpus보다 98.52% 작다(관련 파일 원문보다는 26% 큼).

**README 감사.** 현재 [README.md](../../README.md)에서 benchmark evidence와 명백히 충돌하는 거짓 주장은 찾지 못했다. "What DUO adds"는 capability 목록이고, benchmark 문단은 대조군이 같은 판정을 냈다고 이미 밝힌다. 두 가지 긴장은 기록한다.

1. "Why not just AGENTS.md…" 절은 차별점을 앞에 두는 구성이다.
2. "tell a violation that was already there (pre-existing) from one a change introduced"는 C240(adoption 뒤 debt도 `introduced`)과 정확히 맞지 않는다.

이번에는 바꾸지 않는다(H-66). positioning 조정은 별도 docs task **T32.6**으로 제안하며, gate 결과에 따라 하거나 사람이 먼저 하기로 정할 때 한다.

## 19. Kill / continue criteria

T27.5 §21 kill criteria를 T31·T32 뒤 상태로 다시 적는다(원래 절은 고치지 않는다).

| T27.5 kill criterion | 현재 상태 |
|---|---|
| 1. native·DIY가 같은 provenance·재현성을 더 낮은 유지 비용으로 제공 | 시험한 fixture에서 판정은 같았다. 유지 비용은 시험한 규모에서 비슷하거나 DIY가 낮았다. 장기·규모 비용은 Untested → 사실상 **부분 충족** |
| 2. adoption baseline·lifecycle이 docs·ADR·git history보다 이득을 주지 않음 | T32에서 판정 이득 없음. 기록 drift 방지는 Untested → **부분 충족** |
| 3. 결정적 review가 다른 도구가 놓친 actionable finding을 거의 추가하지 못함 | 두 benchmark에서 0건 → fixture 범위에서 **충족** |
| 4. Truth 유지 비용 > 막은 drift | Untested |
| 5. 언어 한계로 핵심 위반 탐지가 약함 | TypeScript에서만 시험, 다른 언어 Untested |

**Kill**(gate나 실사용에서 확인되면 E로 전환):

- 실제 사용자가 docs·DIY·native review를 계속 선호한다.
- Truth 유지 비용이 막은 drift보다 크다(Truth가 갱신되지 않고 방치됨).
- 반복 사용이 없다.
- 사용자가 결정적 provenance를 실제로 중요하게 여기지 않는다.
- setup ceremony(init, confirm, index)가 가치보다 크다.
- multi-agent authority 사용 사례가 거의 없다.
- noisy finding(C239 포함)이 useful finding보다 많다.

**Continue**(gate 통과 + 새 Human Decision의 근거):

- 독립 사용자가 반복해서 쓴다.
- 실제 drift를 막았다(참여자 기준 방식이라면 놓쳤을 것).
- Decision이 여럿일 때 bespoke gate·docs보다 유지 노력이 적다고 참여자가 판단한다.
- agent 교체·병행에서 Truth를 재사용해 가치를 얻었다.
- maintainer 도움 없이 DUO를 유지한다.
