# T25.2 Fingerprint / Scan cost audit and optimization gate

0.2.0 Milestone B의 두 번째 task다. 결정: H-57. 결론은 **audit only**: production 코드를 바꾸지 않았다. 남은 scan·fingerprint 비용은 content hash 정확성에 필요한 일(모든 byte 읽기와 SHA-256)과 Git process 비용이 지배하고, 판정을 바꾸지 않는 후보는 이득이 작거나(≤ 55 ms) resource gate를 넘지 못했다. Milestone B를 종료한다.

측정: `b4d457b` build, Windows 11, 22 logical CPU, Node 24.18.0, Defender 켜짐, warm file cache(no-op freshness는 처음 한 번 뒤 측정). TASK-019, T22, T25.1 수치는 그대로 둔다.

## 2. Scan pipeline

DUO는 디렉터리를 직접 순회하지 않는다. 경로는 Git에서 온다.

1. `rev-parse --show-prefix`(root 확인, T25.1부터 Git provider와 공유)
2. 병렬: `ls-files -z --stage`(tracked, mode, blob OID), `ls-files -z --others --exclude-standard`(untracked, `.gitignore`·nested `.gitignore`·`info/exclude`·global excludes는 Git이 적용), `diff-files -z --name-only --diff-filter=T`(type change)
3. 후보마다: `normalizeRepoPath`(이식 불가 이름 제외), submodule·중첩 저장소 제외
4. `createPathPolicy`: `.git` segment, `.duo-project`의 regenerable·history, agent integration 파일, secret 이름, `index.exclude`, `index.include`
5. `buildOutputMatcher`: 근거가 있는 build output 디렉터리(디렉터리별 memo)
6. 상위 디렉터리마다 `lstatSync` 1회(memo, symlink 디렉터리 아래 제외), 파일마다 `lstatSync` 1회(symlink, missing, 일반 파일 아님)
7. `findPathPortabilityCollisions`, UTF-8 경로순 정렬

`.duo-project`는 전체를 제외하지 않는다. regenerable(generated, cache, runtime)과 history(reviews)만 제외하고 Truth 파일(project.yaml, intent, specs, decisions, milestones, integrations)은 scan·fingerprint 대상이며 coverage에는 세지 않는다(C221). 분류:

| 분류 | 처리 |
|---|---|
| A. repository source | scan + fingerprint, L1/L2 analysis |
| B. Truth | scan + fingerprint(Truth 변경 감지) + loader 별도 읽기, coverage 제외 |
| C. ignored | Git이 나열하지 않음(tracked면 ignored 패턴과 관계없이 포함) |
| D. generated/cache/runtime | policy가 제외(Git ignore와 이중) |
| E. L0(분석기 없음) | scan + fingerprint만 |
| F. 분석 가능 | scan + fingerprint + analysis cache 확인 |

## 3. Fingerprint pipeline

`fingerprintRepositoryFiles`: 동시성 16 worker pool, 파일마다

1. `fs.promises.lstat`: scan 뒤 entry가 symlink나 일반 파일 아님으로 바뀌었으면 읽지 않는다(재확인)
2. `fs.promises.readFile`: 파일 전체. 크기 상한, binary 감지, 확장자에 따른 생략은 없다
3. `canonicalContent`: normalized-text 모드(확장자·파일 이름 목록)만 CRLF → LF
4. SHA-256(`createHash`, 메인 스레드에서 동기)
5. 결과는 `{ path, state, fingerprintMode, contentHash, size, gitBlobOid? }`, mtime 없음, 경로순

Git state 의존은 `gitBlobOid`(provenance, 비교 안 함)뿐이다. analyzer·config·Truth 의존은 fingerprint 밖(index state의 analyzer identity, config chain hash, Truth 파일 hash)에 있다.

| bulletproof-react | 532 | 2.6 | 14.1 | 82.4 | 8.7 | 5.3 |

| synthetic large | 5,017 | 0.5 | 100.6 | 639.6 | 1.4 | 31.0 |

## 4. Hash CPU와 파일 I/O

같은 byte를 메모리에서만 처리한 시간(5회 median): production 정규화 + SHA-256 / raw byte SHA-256.

| 대상 | 정규화 + SHA-256 | SHA-256만 | 정규화 비용 |
|---|---:|---:|---:|
| spring-petclinic | 3.0 | 0.8 | 2.2 |
| bulletproof-react | 7.7 | 1.7 | 6.0 |
| ActionRoguelike | 462.5 | 451.6 | 10.9 |
| ECS samples | 324.5 | 319.1 | 5.4 |
| synthetic large | 4.2 | 3.6 | 0.6 |

- 작은 저장소와 synthetic: hash는 병목이 아니다. 비용은 파일당 고정비(open, read, close의 thread pool 왕복)다. synthetic large는 0.5 MB에 read 640 ms(순차)다.
- ActionRoguelike: `.uasset` 1,761개(749.5 MB)가 비용이다. SHA-256 CPU 452 ms가 메인 스레드에서 직렬로 돈다. 읽기는 thread pool에서 병렬이라 동시성 16 fingerprint 669 ms의 하한이 사실상 hash CPU다.
- ECS: 두 가지가 섞인다. 4 KB 미만 5,801개(4.5 MB)의 고정비(순차 read 842 ms, lstat 142 ms)와 binary(fbx, png, tga, psd 등 약 480 MB)의 hash 약 290 ms.
- CRLF 정규화(JS byte loop)는 어디서도 11 ms를 넘지 않는다. `Buffer.indexOf` 정규화(byte 동일 확인)는 더 빠르지 않았다(ECS 320 ms 대 324 ms, spring 4.8 대 3.0).

## 5. Filesystem operation과 중복

no-op inspect 1회에서 같은 경로에 같은 종류의 호출이 두 번 이상인 경우와 종류를 넘는 경로별 패턴(`--mode count`):

| 패턴 | 경로 수(ECS) | 호출자 | 판단 |
|---|---:|---|---|
| `lstatSync` 1 + `lstat` 1 + `readFile` 1 | 8,075 | scan `entryKind`, fingerprint 재확인, fingerprint 읽기 | lstat 두 번은 목적이 다르다(아래 §6) |
| `lstatSync` 1 | 923 | scan 상위 디렉터리(memo, 디렉터리당 1회) | 중복 아님 |
| `lstat` 1 + `readFile` 1 | 851 | analysis cache entry(T25.1) | 중복 아님 |
| `lstat` × entry 수 | 3(`.duo-project`, `cache`, `analysis`) | cache entry마다 상위 segment symlink 검사 | T25.1에서 유지한 보안 검사. ECS 2,553회, 비동기 |
| `existsSync` + `lstatSync` + `lstat` + `readFile` + `readFileSync` | 3~4 Truth 파일 | loader 읽기, scan, fingerprint | loader는 parse, fingerprint는 byte hash. 이득 1 ms 미만 |
| `readFileSync` | config chain 몇 개 | `resolutionSignals`의 `hashOnDisk` | 기록된 config(index 밖 포함). 이득 1 ms 미만 |

hash 호출: `computeContentHash` 파일당 1회(중복 없음), `analysisCacheFileName` cache key당 1회, `indexStateToken` 1회(state 전체, ECS 4.4 MB).

Git 쪽: scan의 `diff-files --diff-filter=T`와 provider의 `status --porcelain=v2 --branch --untracked-files=no`가 각각 tracked 파일 전체를 stat한다. provider는 status의 header(HEAD OID, branch)만 쓴다. 단독으로 번갈아 잰 시간(`bench/experiments/git-header-cost.mjs`, 7회 median): status 92~139 ms, 같은 두 값을 주는 `symbolic-ref -q HEAD` 80~87 ms, `rev-parse -q --verify HEAD` 79~87 ms. Windows의 Git process 하나가 약 80 ms라서 바꿔도 ECS에서 55 ms, 나머지는 10~30 ms다(inspect 안에서 잰 status 458 ms는 다른 Git process와 동시에, 메인 스레드가 바쁠 때의 callback 시점이라 부풀려졌다). 또 status의 branch 단축 규칙(`refs/heads/`만 제거)은 `symbolic-ref --short`와 다르고 status는 index stat 정보를 새로 고치는 부수 효과가 있어 동등성 증명이 따로 필요하다.

## 6. Scan ↔ fingerprint 중복과 TOCTOU

scan의 `lstatSync`는 분류(symlink, missing, 일반 파일 아님)와 diagnostic을 위해, fingerprint의 `lstat`은 읽기 직전 재확인을 위해 있다. scan 결과를 fingerprint에 넘기고 재확인을 없애면:

- scan → 외부 process가 파일을 symlink로 교체 → fingerprint의 `readFile`이 symlink를 따라 저장소 밖 파일을 읽을 수 있다. 재확인은 이 창을 읽기 직전까지 좁힌다. 보안 의미(symlink 비추적)가 바뀌므로 합치지 않는다.
- 내용 정확성은 stat이 아니라 `readFile`로 읽은 byte의 hash에서 나온다. scan metadata를 재사용해도 내용 변경을 놓치지는 않지만, metadata로 hash를 생략하는 순간(size·mtime) 놓친다. 그것은 C 후보다.
- 줄일 수 있는 시간도 작다: fingerprint의 lstat은 비동기 동시성 16이라 ECS에서도 wall time 기여가 수십 ms다.

operation 안에서 공유할 metadata는 없다고 판단했다. FreshnessOperationContext 확장은 하지 않았다.

### 8.1 SHA-256 off the main thread

`bench/experiments/fingerprint-hash-offload.mjs`: production과 같은 파일 처리에서 digest만 `crypto.subtle.digest`(libuv thread pool, 기본 4)로, 임계값 이상 크기만. 번갈아 7~9회 median. 모든 변형의 결과가 production fingerprint와 같다.

| 대상 | production(동기, 16) | subtle 16 | subtle 32 | subtle 16 ≥ 64 KB | ≥ 256 KB | ≥ 1 MB |
|---|---:|---:|---:|---:|---:|---:|
| ActionRoguelike(9회) | 630 ms, RSS +150 MB | — | — | 494 ms, +228 MB | 522 ms, +230 MB | 585 ms, +238 MB |
| ECS(9회) | 841 ms, +30 MB | — | — | 750 ms, +50 MB | 762 ms, +36 MB | 776 ms, +33 MB |
| ActionRoguelike(5회) | 624 | 456 | 449 | 455 | — | 541 |
| ECS(7회) | 840 | 782 | 726 | 729(+128 MB) | — | 789 |
| synthetic large | 268 | 289 | 267 | 269 | — | 271 |
| synthetic medium | 60 | 61 | 58 | 58 | — | 59 |
| bulletproof-react | 36 | 38 | 39 | 35 | — | 35 |
| FastAPI | 17 | 21 | 19 | 18 | — | 18 |
| spring-petclinic | 10 | 11 | 11 | 10 | — | 10 |

Unreal에서 −136~−169 ms(no-op의 약 10%), Unity에서 −50~−111 ms(약 4%), 나머지는 0이다. `subtle.digest`는 입력을 복사하므로 큰 파일이 동시에 처리되는 ActionRoguelike에서 peak RSS 증가가 +150 MB에서 +228~238 MB로 일관되게 커졌다(ECS는 +33~128 MB로 흔들림). T25.1이 synthetic large에 +37 MB를 더한 위에 Unreal에서 +80 MB를 더 얹는 것은 resource gate(큰 spike가 겹치면 유지하지 않음)를 넘는다고 판단했다. 같은 이유로 worker thread 이전(파일 bundle, 시작 비용, 수명 관리)도 하지 않았다.

## 9. Mutation regression

`freshness-regression.e2e.test.ts`에 T25.2 진화 테스트 하나를 더했다(T25.1의 9개 시나리오, relationRulesVersion, Python metadata, Git 상태는 그대로). 단계마다 status, 다시 분석할 파일, freshness record, 두 번 물어 같은 답, index 뒤 current, Graph == clean full rebuild를 확인한다.

| 단계 | status | 다시 분석 |
|---|---|---|
| Truth 파일(`intent/vision.md`) 수정 | stale(`projectTruth`) | 없음 |
| Truth 파일 삭제 | stale(`projectTruth`) | 없음 |
| source 파일을 symlink로 교체 | stale, 그 파일 deleted(symlink는 따라가지 않음) | 없음 |
| 빈 파일 추가 | stale, added | 그 파일 |
| 3 MB 파일 마지막 byte 수정 | stale, changed | 없음(L0) |
| ignored binary 성격 파일 생김 | current, record 없음 | 없음 |
| ignored 파일 수정 | current | 없음 |
| nested `.gitignore`가 새 파일을 숨김 | stale(`.gitignore` 추가) | 없음 |
| nested `.gitignore` 변경으로 드러남 | stale, added | 그 파일 |

symlink를 만들 권한이 없는 Windows에서는 그 단계가 일반 수정이 된다(이 PC). Linux·macOS CI는 symlink 경로를 실행한다. relationRulesVersion 없음·옛 값, `pyproject.toml`·`setup.cfg` 변경은 T25.1 테스트가 계속 덮는다.
