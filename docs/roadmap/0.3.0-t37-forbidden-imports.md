# T37 Forbidden Imported Paths (H-72, next)

상태: **구현 완료(`next`)**. 승인된 결정: [H-72](../conflicts.md#human-결정-기록). 분석: [T36](0.3.0-t36-forbidden-relation-audit.md). T35 당시 결과(STOPPED / INCOMPLETE)는 바꾸지 않는다. 이 문서의 T37-S1C는 T35 S1의 재판정이 아니라 새 scenario다.

## 1. 의미

`forbids.imported_paths`(repository path pattern, `compileRepoPattern`): diff의 바뀐 new-side 줄과 겹치는 module reference가 현재 index에서 정확히 한 repository 파일로 해석되고 그 경로가 패턴에 맞으면 `decision-forbids-import` CONFLICT, reason `forbidden-import`. `enforcement: block`이면 기존 provenance 정책에 따라 BLOCK 후보. claim 문구는 "forbidden import on a changed line: <source>:<line> <kind> "<specifier>" [(type-only)] resolves to <target>"이고 관계가 새로 생겼다고 말하지 않는다.

- 대상: TS·JS import, export-from, dynamic import, require(type-only 포함), Python(상대, 발견된 root의 absolute), C++ 옆 파일 quoted include. Java·C#은 module resolution이 없다.
- 해석되지 않은 경우: claim 없음, BLOCK 없음, 텍스트 추측 없음. review limitation: `imports-unresolved`, `imports-ambiguous`, `imports-resolution-unsupported`(Java·C#), `imports-target-not-indexed`, `imports-index-unavailable`, `imports-reviewed-side-not-indexed`(reviewed side가 index된 working tree와 다를 때). external package는 limitation도 아님(`forbids.dependencies`). 이 limitation들은 `imported_paths`를 가진 활성 Decision이 있을 때만 붙는다.
- 어떤 파일과도 맞지 않는 패턴: 아무것도 보고하지 않음.
- violation key: `decision-forbids-import` + Decision + `import:<source file node>-><target file node>`. 같은 쌍의 여러 구문은 한 claim, 구문마다 evidence.

## 2. 구현

| 영역 | 변경 |
|---|---|
| core | schema `forbids.imported_paths`, model `forbids.importedPaths`(값이 있을 때만), lock digest 호환 |
| graph | `readIndexedModuleReferences(root, paths)`: index state의 `FileResolution.modules`와 analysis cache의 `SourceAnalysis.moduleReferences`를 같은 순서로 맞춰 읽기 전용으로 돌려준다. 다시 parse·resolve하지 않는다. 상태 `ok`, `not-indexed`, `not-analyzed`(L0), `unavailable` |
| director | rule `decisionForbidsImport`, evidence `moduleReferenceEvidence`(kind file, 구문 slice, metadata에 kind·specifier·typeOnly·resolvedTo), provenance `violation.unverifiable`, baseline `evaluatedRules`, HEAD 평가기의 import finding |
| integration | MCP `forbids.imported_paths`(`paths`와 같은 pattern 검증), schema·tool 설명 |

Evidence chain(BLOCK 근거, 모두 결정적): Decision 정의 slice(project-truth) → 바뀐 hunk(git) → import 구문 slice와 위치(repository, index된 SourceAnalysis) → 해석된 target 파일(repository, Graph File node).

## 3. Adoption Baseline

- 새 baseline은 `evaluatedRules`를 기록한다. working tree(`.duo-project` 밖)가 깨끗하면 `decision-forbids-import` 포함, dirty HEAD_BASELINE이면 빼고 limitation `import-relations-not-evaluated-dirty-working-tree`.
- `evaluatedRules`가 없는 기존 baseline: Decision `confirmed_at`이 baseline `recorded.at`보다 분명히 뒤면 기존 정책(`introduced` → BLOCK 후보), 아니면(앞이거나 없거나 시각이 아님) `unverified-at-adoption`(BLOCK 없음). baseline 파일은 다시 쓰지 않는다.

## 6. 성능

600개 TS 파일 저장소, 같은 변경(파일 60개: 기존 50개에 금지 import 추가, 새 파일 10개), `duoctl review --json` 7회 wall time median: `imported_paths` Decision 활성 3,882 ms(claim 60, BLOCK), 비활성 4,060 ms(claim 0). 차이는 측정 변동 안이다. 새 resolver나 전체 재분석은 없고, 바뀐 파일의 analysis cache 항목만 읽는다.

## 7. 남은 위험

- provenance 태그 `introduced`의 오해(C240), 위 §5. T38(H-73)에서 사람이 읽는 표시만 바꿨다.
- barrel·re-export 경유 import는 barrel 경로를 따로 금지하지 않으면 걸리지 않는다. barrel을 금지하면 같은 barrel의 다른 export도 막힌다.
- 기존 import 줄을 고치기만 해도(binding 추가 등) adoption 이후 관계면 BLOCK된다.
- Java·C#은 확인하지 않는다(limitation만).
- reviewed side(`--to`)가 working tree와 다르면 그 파일은 확인하지 않는다(limitation).
