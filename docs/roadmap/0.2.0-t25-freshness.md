# T25.1 Freshness verification optimization

0.2.0 Milestone B의 첫 task다. 결정: H-56. 두 최적화만 다룬다: A analysis cache 확인을 비동기 + 제한 동시성으로, B 한 freshness operation 안의 `git rev-parse --show-prefix` 중복 제거. 판정은 바뀌지 않는다(같은 답, 적은 일).

## 1. 결과

- A: analysis cache 확인을 동시성 16으로 읽는다. 각 entry의 path segment별 lstat, 읽기, key 확인은 그대로이고 결과는 key 순서로 모은다. Indexer와 inspect가 같은 판정 함수(`parseCachedAnalysis`)를 쓴다.
- B: `inspectIndex`와 `indexRepository`가 operation마다 work-tree probe 하나를 만들어 scan과 Git provider에 넘긴다. Git process가 8개에서 7개로 준다.
- 같은 세션, 같은 machine(Windows)에서 빌드를 번갈아 잰 no-op freshness median 차이(Build 0 대비, 5회): spring-petclinic −138 ms, bulletproof-react −149 ms, FastAPI −228 ms, ActionRoguelike −247 ms, ECS −536 ms, synthetic large −1,633 ms. real-world 이득은 작다. synthetic large에서 크다.
- 10개 변경 시나리오 × 4개 빌드에서 inspect 결과 전체, 진단, incremental Graph, clean full Graph의 digest가 같다. 8개 대상의 no-op inspect digest도 4개 빌드에서 같다. T23 harness로 잰 real-world 5개의 Graph, Context, Review 결정적 출력도 4개 빌드에서 같다(compare exit 0). Context와 Review 시간은 샘플 편차가 이득보다 커서 개선으로 보고하지 않는다(§6.3).
- public contract(CLI, MCP, UI schema, Truth, Review, Context, Graph, index state, exit code, stale/current 의미) 변경 없음. package version 0.1.2.

## 3. A: analysis cache 확인

### 3.1 이전 구조

`readCachedAnalysis(root, key)`가 Indexer와 inspect 양쪽에서 불렸다. `readRegenerable`이 path의 segment마다 `lstatSync`로 symlink를 거부하고 `readFileSync`로 읽는다(ENOENT → 없음, 그 외 → error). 그다음 JSON parse와 format, version, path, contentHash, analyzer, analyzerIdentity, analysis 확인. 어느 실패든 cache miss(`missing`)이고 예외로 올라가지 않는다. 파일 하나씩 순차로 처리했다.

### 3.2 변경

- `readRegenerableAsync`: 같은 segment를 같은 순서로 `fs.promises.lstat`, 같은 결과 규칙. reject하지 않는다.
- `parseCachedAnalysis(text, key)`: 이전 판정 그대로를 분리한 공통 함수. Indexer(`readCachedAnalyses`, analysis 보관)와 inspect(`cachedAnalysesValid`, 유효 여부만)가 둘 다 이것을 쓴다.
- `mapBounded`: worker pool. 동시에 최대 `ANALYSIS_CACHE_READ_CONCURRENCY`(16)개. 결과 배열은 입력 key 순서다.
- inspect: 파일 loop는 그대로 돌며 fresh 파일의 key를 loop 순서로 모은 뒤 한 번에 확인한다. 무효인 파일만 `missing`으로 바꾸고 changedFiles에 넣는다. changedFiles와 freshness record는 이후 정렬되어 출력된다.
- Indexer: 1단계에서 파일별 분석기, language, freshness, key를 scan 순서로 정하고(language 통계 포함), cache를 한 번에 읽은 뒤, 2단계에서 이전과 같은 순서로 파일을 처리한다. analyses, diagnostics, metrics의 순서와 내용이 이전과 같다.

### 3.3 Deterministic aggregation

completion 순서는 결과에 나타나지 않는다. 결과는 key 배열의 index에 쓰이고, 소비자는 그 배열을 원래 loop 순서로 읽는다. 단위 test에서 readFile mock으로 완료 순서를 뒤집어도 결과는 key 순서이고, 동시성 1/4/8/16/32/64가 모두 순차 참조 구현과 같다. 여러 cache entry를 동시에 깨뜨린 시나리오(잘림, 삭제, `null`)도 4개 빌드의 inspect digest가 같다.

### 3.4 Error semantics

| 경우 | 이전(동기) | 이후(비동기) |
|---|---|---|
| ENOENT | miss | miss |
| 잘린 JSON, 잘못된 JSON | miss | miss |
| 다른 key의 entry, 다른 analyzer identity, 다른 contentHash | miss | miss |
| 파일 자리에 directory | miss(read error) | miss(read error) |
| entry가 symlink, cache directory가 symlink·junction | miss(symlink 거부) | miss(symlink 거부) |
| 읽기 권한 없음(chmod 000, Windows 제외) | miss | miss |

어느 경우도 throw → stale이나 stale → fatal로 바뀌지 않는다. `readRegenerableAsync`는 reject하지 않으므로 pool에서 하나가 실패해도 다른 읽기가 unhandled rejection을 만들지 않는다. 측정 뒤 남은 파일 요청은 0이다(§6).

### 3.5 lstat, symlink 검사

줄이지 않았다. entry마다 같은 segment를 같은 순서로 검사하고, write 경로(`writeRegenerable`)와 prune은 바뀌지 않았다. lstat 총수가 4개 빌드에서 같다(§2).

## 4. B: `show-prefix` 중복

### 4.1 Root cause

`scanRepository`(`gitWorkTreePrefix`)와 `openGitProvider`가 같은 `path.resolve(root)`에서 같은 `git rev-parse --show-prefix`를 따로 실행했다. 둘 다 "root가 work tree의 top level인가"를 묻는다. 한 inspect 안에서 두 호출 사이에는 fingerprint와 analysis가 있을 뿐이다. 결과의 의미 있는 수명은 그 operation 하나다.

### 4.2 구현

`packages/analyzer/src/git/work-tree.ts`: `probeWorkTree(root)`가 `{ rootDir, prefix() }`를 만든다. `prefix()`는 처음 불릴 때 한 번 Git을 실행하고 그 promise를 probe 객체 안에만 둔다. `prefixFor(rootDir, probe)`는 probe의 rootDir가 같을 때만 그 답을 쓰고, 다르면 직접 묻는다. `inspectIndex`와 `indexRepository`가 실행마다 probe를 새로 만들어 scan과 provider에 넘긴다. process-global cache, cross-command cache, TTL, 이전 실행 결과 재사용은 없다. probe를 받지 않는 다른 호출자(collect, review의 diff provider, baseline, init plan, MCP 서버 시작)는 이전처럼 직접 묻는다. scan과 provider는 각자 이전과 같은 diagnostic을 만든다(scan 실패 시 scan의 diagnostic으로 먼저 끝나는 순서도 같다).

review와 baseline은 `inspectIndex` 뒤 diff용 `openGitProvider`로 한 번 더 묻는다. freshness operation 밖이라 이번에 합치지 않았다(review 1회 기준 show-prefix 3 → 2).

### 4.3 cwd, subdirectory, Git 상태

| 경우 | 결과(Build 0 = AB) |
|---|---|
| repo root | prefix "" → 진행 |
| 하위 directory에 `.duo-project` | `SCAN_ROOT_INVALID`(`it is "src/"`), inspect와 index 둘 다 |
| Git 밖 directory | `GIT_REPOSITORY_REQUIRED` |
| unborn(commit 없음) | full index → current, dirty edit → 그 파일만 stale → incremental → current, clean full과 같음 |
| detached HEAD | 같음 |
| shallow clone(depth 1) | 같음 |

## 6. Build 0 / A / B / AB

빌드: 0 = `3c5bdea`, A = 0 + cache 확인만, B = 0 + show-prefix 공유만, AB = 둘 다. A와 B를 합치면 AB와 byte 단위로 같다. 측정은 `bench/experiments/freshness-ab-suite.mjs`(같은 세션, 같은 machine).

### 6.1 Interleaved(5회차, 회차마다 빌드 순서 회전, 프로세스마다 no-op 3회 median)

Build 0 대비 차이는 회차별 차이의 median이다.

|---|---:|---:|---:|---:|---:|---:|
| spring-petclinic | 663 | +59 | −116 | −138 | 21 → 12 | 355 → 219 |
| bulletproof-react | 931 | −100 | −54 | −149 | 149 → 62 | 455 → 295 |
| FastAPI | 735 | +52 | −101 | −228 | 49 → 26 | 405 → 270 |
| ActionRoguelike | 1,845 | −29 | +50 | −247 | 95 → 59 | 448 → 258 |
| ECS samples | 4,372 | −963 | −692 | −536 | 524 → 281 | 624 → 304 |
| synthetic large | 4,593 | −754 | −6 | −1,633 | 1,946 → 693 | 1,080 → 1,062 |

단계별로 보면 효과가 분리된다. A는 analysis 단계만 줄이고(ECS −226~−257 ms, large −800~−1,137 ms), B는 resolution-and-git 단계를 Git process 하나만큼 줄인다(−73~−228 ms). 전체 시간의 A·B 단독 값은 기기 drift가 섞여 단계 값보다 흔들린다.

### 6.2 Block(2 round × 5회, 빌드별 연속)

synthetic small, medium, large와 real-world 5개 모두에서 inspect digest, status, edit 뒤 결과(stale → incremental 1 → current)가 4개 빌드에서 같다. analysis 단계 median: synthetic medium 414~437 → 143~166 ms, large 2,025~2,122 → 693~1,347 ms. 블록 측정의 전체 시간은 round 사이 기기 drift가 커서(ECS AB 2,102 → 4,760 ms) 판단에 쓰지 않는다.

Context와 Review는 freshness 한 번(§6.1에서 AB가 줄인 0.1~0.5 s)에 diff, seed, Packet, rule 계산이 더해진 시간이다. 샘플이 적고 같은 build 안의 편차(예: ECS AB Review 4,324와 5,371 ms)가 이득보다 커서 이 표로 개선이나 regression을 판단하지 않는다([performance benchmark](../performance-benchmark.md)의 같은 build 편차 0.78~2.18배). 개선 판단은 §6.1의 interleaved 측정으로 한다.

결정적 출력: `compare.mjs`가 0 대 A, 0 대 B, 0 대 AB 모두 exit 0이다. 5개 저장소 모두에서 Graph SHA-256, Context 파일·level·dependency digest, Review 결과, check(incremental = clean full 포함)가 같다.

### 6.4 RSS, heap, handle

interleaved no-op process의 peak: synthetic large RSS 331 → 368 MB, heap 144 → 176 MB(동시에 16개 entry text를 들고 있음). ECS RSS 365 → 373 MB, heap 169 → 134 MB. real-world 나머지는 ±30 MB 안. 남은 파일 요청 0, unhandled rejection 없음.

## 7. 검증

- `analysis-cache.test.ts`(3): 오류 종류별 결과가 순차 참조 구현과 같음, 동시성 1~64 동일·key 순서, symlink·junction cache directory, 완료 순서를 뒤집은 mock에서 in-flight ≤ 상한이고 1보다 큼.
- `freshness-regression.e2e.test.ts`(14): 0.2.0 audit §4.3의 9개 시나리오(status, 다시 분석할 파일, freshness record, inspect 두 번 같은 답, incremental, 그 뒤 current, Graph == clean full), relationRulesVersion 없음·옛 값 → stale(parse 0, `projectTruth`) → index → current, Python `pyproject.toml` 변경·`setup.cfg` 추가·`__init__.py` 삭제 → stale → index → current == clean full, analyzer identity 변경 → 6개 파일 `stale-analyzer`, subdirectory와 Git 밖, unborn·detached·shallow·dirty. 같은 file이 Build 0에서도 통과한다(답이 이전과 같음).
- `bench/experiments/freshness-equivalence.mjs`: 10개 시나리오 × 4개 빌드에서 inspect(value + diagnostics), index diagnostics, incremental Graph digest 동일, 각각 clean full과 같음.
- 기존 fuzz, recovery, incremental e2e, clean full equivalence.

## 8. 판단

유지한다. 판정은 4개 빌드에서 같고, AB가 real-world 5개 모두에서 no-op freshness를 줄였다(−138 ~ −536 ms). synthetic large에서는 −1.6 s다. 메모리 증가는 large에서 수십 MB이고 handle 압력은 상한으로 묶였다. 코드는 판정 함수 하나 분리, pool 하나, probe 하나다. real-world 이득은 0.2.0 audit의 상한(analysis 72·401 ms + Git process 1개) 범위 안이다.
