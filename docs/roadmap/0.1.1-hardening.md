## A. Windows UI E2E flaky (C213)

**현상.** `tests/conformance/rc.conformance.test.ts`의 "RC: local UI" 블록이 Windows CI에서 `TypeError: fetch failed` / `read ECONNRESET`으로 실패했다. e97fcf8에서 3회 연속, 과거에 통과한 53bbcc3를 같은 runner image(`windows-2025-vs2026` 20260922.246.2)로 다시 돌려 1회 실패했다. 로컬 Windows와 Ubuntu·macOS에서는 재현되지 않았다.

**원인.** 이 블록은 UI 요청 사이에 CLI를 `spawnSync`로 실행한다(`tests/cli/support.ts`의 `duoctl()`). 그동안 테스트 프로세스의 event loop가 멈추고, Node fetch(undici)의 연결 풀에 있던 keep-alive socket이 쉰다. UI 서버는 Node 기본값대로 `Keep-Alive: timeout=5`(5 s)로 idle socket을 닫는다. idle 시간이 5 s 경계에 닿은 순간 클라이언트가 그 socket에 요청을 쓰면 서버가 닫는 socket이라 reset된다.

**증명.** undici의 `diagnostics_channel`을 구독하는 preload(`bench/experiments/undici-trace.mjs`)로 요청마다 socket, 재사용 여부, 재사용 전 idle 시간을 기록했다.

- 로컬, 수정 전 1회: `POST /api/context`가 4,191 ms 쉬던 socket을 재사용했다. 그 사이에 있던 것은 `duoctl context` 한 번이다.
- Windows CI probe, 수정 전(keep-alive) 15회: UI 요청 315개 중 285개가 socket을 재사용했고, 재사용 socket의 최대 idle은 4,914 ms(서버 timeout보다 86 ms 짧음)였다. 이 15회에서는 reset이 나지 않았다. 경계 근처의 경쟁이라 매번 나지 않는다.
- `duoctl ui`에 대한 합성 실험(요청 → N초 동기 차단 → 요청, 4.4~5.4 s)은 reset을 재현하지 못했다. undici가 차단이 풀린 뒤 만료된 socket을 먼저 버리는 경우가 많기 때문이며, 이 실험 스크립트는 남기지 않았다.

**수정.** 제품 UI 서버와 timeout은 그대로 둔다. 테스트의 UI 요청에 `Connection: close`를 붙여 요청마다 새 연결을 쓰게 했다. 재사용할 idle socket이 없으므로 경계 경쟁이 생기지 않는다. 같은 블록의 `stop()`이 `duoctl ui` 프로세스의 종료를 기다리게 했다. 살아 있는 자식이 Windows에서 fixture 폴더를 잡고 있어 블록만 단독 실행(`-t`)하면 afterAll이 `EPERM`으로 실패했다. 변경은 이 테스트 파일 하나다.

**검증.** `bench/experiments/ui-keepalive-repeat.mjs`로 블록을 반복 실행했다.

| 환경 | 횟수 | 결과 |
|---|---:|---|
| 로컬 Windows 11, Node 24.18.0 | 40 | 40 통과, UI 요청 840, 재사용 0, 오류 0 |
| GitHub Windows runner(probe, 2 job) | 50 | 50 통과(exit 0), UI 요청 1,050, 재사용 0, 오류 0 |
| main CI d647f3b(3 OS 전체) | 1 | Ubuntu, macOS, Windows 성공(`pnpm test`, 배포 E2E, 설치본 conformance) |

## B. Release와 installed-package 검증

publish 전 검증은 이미 `pnpm release:preflight`가 한다(verify, 배포 E2E, conformance, pack, 재현성, scan, audit, npm 인증·scope·version, dry-run, CI). 같은 일을 하는 `release:verify-candidate`는 만들지 않았다.

publish 뒤 검증으로 `pnpm release:verify-published`(`scripts/release/verify-published.mjs`)를 추가했다.

- registry: name, version, `dist.integrity`, tarball URL, license, engines, bin, `dist-tags.latest`.
- 기대값: `--integrity`·`--commit`, 없으면 같은 version의 `.dist/release-candidate.json`.
- 설치: 빈 npm user config, 새 cache, 임시 prefix에 `npm install -g`. credential을 읽거나 쓰지 않는다.
- 설치본: 파일 수(registry `fileCount`와 비교), LICENSE, shrinkwrap, PATH에서 찾은 `duoctl --version`·`--version --json`·`--help`, 새 Git 저장소에서 `init` → `status`(initialized, index current).
- Git·GitHub: origin의 `v<version>` tag가 가리키는 commit, GitHub Release 존재와 draft 여부.
- 결과: `.dist/release-published.json`(`duo.release-published/1`), 문제가 있으면 exit 1.

network가 필요하므로 CI 필수 경로와 `pnpm verify`에는 넣지 않았다. 로컬 tarball 검증(`test:dist`, `test:conformance`)은 그대로 registry와 분리되어 있다. publish, tag, GitHub Release는 계속 사람이 실행한다.

0.1.0 결과(2026-09-30): integrity `sha512-NjSIMAKa…kQkCcQ==`가 RC와 같음, 설치 11 s, 25 파일, `duoctl 0.1.0`, graph schema 2, init·status 성공(LLM disabled), `v0.1.0` → `04bab58`(RC와 같음), GitHub Release 게시.

## C. Clean install과 existing project

먼저 기존 coverage를 대조했다. 대부분은 이미 설치본으로 검증된다.

| 대상 | 검증 위치 |
|---|---|
| clean global install, `duoctl --version` | `tests/distribution/dist.e2e.test.ts`(tarball), `release:verify-published`(registry) |
| existing Git repository, dirty adoption | `tests/cli/existing-project.e2e.test.ts`(설치본 conformance에서도 실행) |
| unknown language, TS/JS, Java, C# Unity, C++ Unreal, Python FastAPI, polyglot | `tests/cli/languages.e2e.test.ts`(conformance), dist cross-language |
| Codex, Claude Code installer, MCP launch | `tests/install`, `tests/mcp`(conformance), dist install codex·claude-code |
| local UI launch | `tests/cli/ui.e2e.test.ts`, dist `duoctl ui`, RC UI 블록 |
| fresh Git repository(커밋 1개) | `release:verify-published`의 init → status |

**gap: 커밋이 없는 저장소(C214).** `git init` 직후 `duoctl init`은 Truth와 index를 만든 뒤 baseline 단계에서 `ADOPTION_HEAD_REQUIRED`로 exit 1이 된다. 파일이 있으면 dirty라 `--baseline-policy head`가 먼저 필요하고, 그 뒤 같은 오류가 난다. 첫 commit 뒤 `duoctl init`을 다시 실행하면 앞 단계를 이어서 baseline을 만든다(exit 0, 확인함). 정확성 문제는 아니다. 하지만 출력이 "Baseline failed"와 exit 1이라 전체가 실패한 것처럼 보이고, 메시지는 "commit once"까지만 말한다. 테스트를 새로 추가하지 않았고, F의 문구 제안으로 다룬다.

## D. Freshness profile

`inspectIndex`는 status, MCP, UI, context, review가 매번 거치는 freshness 검사다. `bench/experiments/freshness-profile.mjs`로 단계별 시간과 연산 수를 쟀다. 연산 수는 Node 내장 모듈을 실험 프로세스 안에서만 감싸 세었고, 제품 코드와 결과는 바뀌지 않는다.

측정 조건: large fixture(`duo-bench-fixture/1`, 5,005 index 파일, 구조 분석 4,169), 기준 PC(Windows 11, Core Ultra 7 155H), Node 24.18.0, 장기 실행(registry 공유), 7회 median. 오늘 이 PC는 TASK-019 때보다 전반적으로 느렸다. 같은 날 `bench/experiments/steady.mjs`로 잰 large status는 3.9~4.1 s, context 4.0 s, review 5.4 s였다(TASK-019 기록 2.4, 2.5, 3.9 s). TASK-019 이후 이 경로의 코드는 바뀌지 않았으므로 환경 차이이며, [performance-benchmark](../performance-benchmark.md)의 기준 수치는 바꾸지 않는다. 아래는 비율과 연산 수로 읽는다.

| 단계 | median | 주요 연산(1회) |
|---|---:|---|
| truth | 27 ms | Truth 파일 12개 읽기 |
| scan | 452 ms | git `ls-files` 2, `diff-files` 1, `rev-parse` 1, lstat 5,036 |
| fingerprint | 1,002 ms | 파일 5,017개 lstat과 읽기(0.5 MB), SHA-256 5,017(4 ms) |
| state | 99 ms | index state 3.1 MB 읽기와 SHA-256 |
| registry | 10 ms | 공유 registry |
| analysis(cache 확인) | 2,138 ms | cache 4,169개 `readFileSync`(5.7 MB), symlink 검사 lstat 16,676(파일당 4), JSON parse |
| resolution-and-git | 410 ms | git `rev-parse` 2, `status` 1, `rev-list` 1 |
| 합계 | 4,048 ms | git 프로세스 8개(개당 약 110 ms), SQLite 문장 20여 개(무시할 수준) |

context는 freshness가 3.57 s / 3.77 s(95%)이고 tokenization은 3.4 ms다(token memo). review는 freshness 3.78 s, Git diff 1.0 s, context 0.43 s / 5.37 s다. hashing, SQLite, analyzer 선택, token counting은 병목이 아니다. 비용은 작은 파일을 많이 여는 일(cache 확인, fingerprint, scan)과 Git 프로세스 시작이다.

**안전한 후보(제안, 구현하지 않음).**

1. analysis cache 확인을 bounded concurrency 비동기 읽기로 바꾼다. 같은 cache 4,169개를 읽고 parse하는 시간(7회 median): 지금처럼 동기 순차 1,085 ms, 비동기 16개 472 ms, 64개 338 ms(`bench/experiments/cache-read-concurrency.mjs`, 결과 동일 확인). 읽는 byte, 검증 조건, 파일별 symlink 검사는 그대로이고 순서만 바뀐다. Indexer도 같은 판정 함수를 써야 inspect와 index 판단이 같게 유지된다. 기대 효과는 이 단계 0.6~0.75 s. 조건: clean-full equivalence와 fuzz, inspect/index 판정 동일성 테스트, 3 OS benchmark에서 개선 확인.
2. 한 번의 freshness 안에서 같은 Git 질의를 한 번만 한다. `rev-parse`가 3번 실행된다. 같은 호출 안의 한 시점 스냅샷을 공유하는 것이라 판정은 같다. 기대 효과는 Windows에서 약 0.2 s.

**측정했지만 권하지 않는 것.**

- fingerprint 동시성 16 → 64: 8회 median 515 → 444 ms(약 70 ms). 4회 측정에서는 1,082 → 501 ms로 보였지만 반복하자 사라졌다. 의미 있는 개선으로 보지 않는다.
- cache 경로 symlink 검사 축소(337 ms): 보안 검사 범위가 바뀐다(C202). 별도 결정 없이 하지 않는다.
- mtime·TTL·watcher·stale Graph 허용, cache 존재 여부만 검사: freshness 정확성 계약 위반.

RSS는 이번에 다시 재지 않았다(TASK-019 large 약 500 MB).

## E. Node runtime 호환

**24.15+의 근거.** 의존성의 engines는 `openai` `>=22`, MCP SDK `>=20`이다. 하한은 ADR-001 결정이다: `node:sqlite`가 Release Candidate가 된 24.15를 최소로 둔다. 배포 실행 파일(`apps/cli/src/bin.ts`)이 `engines.node`를 검사해 낮은 Node를 거절한다.

**Node 22.23.3 실험(공식 zip, SHA-256 확인).** workspace build의 `apps/cli/dist/main.js`는 버전 검사가 없어 그대로 실행된다.

- `duoctl --version`·`--version --json` 정상.
- vitest 전체(76 파일, CLI·MCP·UI·install E2E가 자식 프로세스로 Node 22 사용): 842 passed, 7 skipped, 466 s. 같은 PC의 Node 24 결과와 같다(skip은 두 버전 모두 Windows·symlink 조건).
- 차이: `node:sqlite`가 experimental이라 모든 프로세스가 stderr에 `ExperimentalWarning: SQLite is an experimental feature`를 쓴다. stdout과 JSON은 깨끗하다.
- 검증하지 못한 것: 설치본(dist E2E, conformance)은 launcher가 24.15+를 강제해 실행할 수 없었다. Node 22.x 안에서 experimental API가 바뀔 위험은 테스트로 알 수 없다.

**결론.** engines는 `>=24.15.0`로 유지한다. Node 22를 지원하려면 ADR-001을 다시 결정하고, 경고 처리 방식(출력 억제는 제품 동작 변경)을 정하고, 설치본 conformance를 Node 22에서 통과시켜야 한다. Node 22 LTS는 2027-04 종료 예정이라 효과가 제한적이다. 0.2.0 이후 사람이 결정할 항목으로 남긴다.

## F. 첫 사용자 흐름

새 저장소에서 README 순서(`--help` → `init` → `status` → 편집 → `review`/`context` → `index` → `review` → `install codex` → `install status`)를 실행해 사람용 출력을 확인했다.

| 질문 | 관찰 | 제안(0.1.1, 문구만) |
|---|---|---|
| 설치 직후 할 일 | README Quick Start가 순서를 보여 준다. `--help`는 명령 목록이다 | 없음 |
| init 뒤 다음 행동 | "DUO is set up. Next: duoctl status · duoctl context <task> · duoctl review". Agent 연결이 없다 | Next에 `duoctl install codex`(또는 `claude-code`) 추가 |
| index 필요와 정상 구분 | status가 `Index: current`/`stale`, review·context는 exit 6과 "Run duoctl index" | status의 stale 줄에 "run duoctl index" 추가 |
| MCP 설치 확인 | install은 쓰기 전 계획, `install status`가 Agent별 상태를 보여 준다 | 없음 |
| L0/L1/L2 | status에 `typescript L2 (1) · file-only L0 (1: .md)`, README 표와 같다 | 없음 |
| LLM 필요 여부 | status `LLM: disabled`, README "LLM은 선택 사항" | 없음 |
| 새 프로젝트의 첫 review | Truth가 비어 WARN("No confirmed Requirement or Decision is linked") | README에 "Truth를 확정하기 전 WARN은 정상" 한 줄 |
| 커밋 없는 저장소(C214) | exit 1, "commit once" | "commit, then run duoctl init again; Truth and index are kept" |

사람이 읽는 CLI 문구는 공개 계약이 아니다([compatibility](../release/compatibility.md)). H-46으로 init Agent 연결, status stale 안내, 커밋 없는 저장소 안내(C214) 세 가지를 0.1.1에 적용했다. 첫 review WARN 설명은 이번 범위에 넣지 않았다. `duoctl doctor` 같은 새 public command는 0.2.0 proposal로 둔다(G).
