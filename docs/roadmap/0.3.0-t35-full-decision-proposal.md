# T35 Full Decision Proposal: 설계와 H-71 제안 (next)

상태: H-71 승인(2026-10-05, main `docs/conflicts.md`에 기록). T35.1에서 `next`에 구현했다. dogfood(§10)는 S2·S3 성공, S1 실패(symbol 패턴 형식)로 stop gate를 충족하지 못해 T35는 완료가 아니다. 아래 §1~§9는 승인 전 설계 기록이다. 선행 작업: T34.2·T34.3 Informed Confirm([0.3.0 iteration §11](0.3.0-product-iteration.md#11-t342-구현-결과informed-confirm-next)).

목표: 사람이 YAML을 직접 쓰지 않아도 coding agent가 검토 가능한 완전한 Decision 초안을 만들고, 그 초안은 Human Informed Confirm을 거쳐야만 authority가 된다.

## 1. 현재 경계 (H-36, C140)

- MCP `duo_propose_decision` 입력: `title, question, answer, rationale?, governs?{requirements, paths, symbols}, agent?`. strict object(그 밖의 key는 거부).
- C140·H-36의 해석: "propose는 DecisionService `ProposalInput` 범위, supersedes·forbids는 Human이 확정 시 다룸".
- 실제로는 Human confirm 단계에 이 field를 추가·수정하는 수단이 없다. 그래서 enforce되는 규칙(`forbids` + `enforcement: block`)이나 대체(`supersedes`)는 사람이 YAML을 손으로 써야만 만들어진다.
- core `ProposalInput`과 proposal schema는 이미 `forbids`, `enforcement`, `supersedes`를 받는다. core `propose`는 쓰기 전에 loader와 같은 schema, trace 규칙(없는 참조 등), "supersede 대상은 confirmed"를 검사한다. agent의 쓰기 경계는 `decisions/proposals/`뿐이다(`guardDecisionWrite`).

## 2. field별 분석

| field | 형식(기존 그대로) | agent-facing 검증 | 판단 |
|---|---|---|---|
| `forbids` | strict `{ paths?, symbols?, dependencies? }`, 각 문자열 배열(Decision schema `decisionShape.forbids`) | `paths`: 기존 MCP `repoPattern` 검증(`normalizeRepoPattern`), 그리고 review가 쓰는 `compileRepoPattern`으로 compile되지 않으면 거부. review는 compile되지 않는 패턴을 조용히 버리므로(`rules.ts`) 입력 단계에서 막아야 한다. `symbols`: 기존 wildcard 문자열(`*Name*`), 길이·개수 상한. `dependencies`: package 이름 문자열. 배열 상한(예: 100), 빈 object 거부 | 추가. 새 syntax 없음 |
| `enforcement` | `"warn" \| "block"` | 같은 enum만. 생략과 명시를 구분해 그대로 저장(기본값 추측 없음). review는 `block`일 때만 BLOCK이고 생략은 BLOCK이 아니다. 이 의미는 바꾸지 않는다 | 추가 |
| `supersedes` | Decision ID 하나 | `D-\d+` 형식만(`DEFINITION_ID_PATTERN` 중 Decision). proposal 단계 검증은 core 그대로: 대상 없음 → `BROKEN_REFERENCE`, 대상이 confirmed가 아님(superseded·proposed·rejected) → `DECISION_SUPERSEDE_TARGET_INVALID`, 결과는 `PROPOSAL_INVALID`로 쓰지 않음. self·cycle은 confirm 단계 trace 규칙이 막는다(proposal은 아직 Decision이 아니어서 self가 될 수 없음). agent는 대상 파일을 바꾸지 않는다 | 추가 |
| `evidence`, `source`, `extensions` | — | — | **제외**. Decision 의미나 BLOCK에 영향이 없고, agent가 출처를 지어낼 위험(evidence pointer 위조)만 늘린다. 필요성이 드러나면 별도 결정 |
| `kind` | `decision \| constraint` | — | 제외(이번 범위 밖). 필요성 없음 |

## 3. supersede 안전 설계

1. agent는 `supersedes: D-001`이 담긴 **proposal만** 만든다. D-001 파일은 바뀌지 않는다(쓰기 경계: agent는 `decisions/proposals/`만, 기존 test가 확인).
2. proposal 단계: core가 대상 존재와 `confirmed` 상태를 확인한다. 이미 superseded면 proposal을 쓰지 않는다.
3. 확정 전 Human preview: 대상의 title·현재 state와 "becomes superseded by this Decision"을 ID 재입력 전에 보인다(T34.2).
4. 확정: Human만, digest-bound. preview 뒤 대상이 바뀌면(예: 다른 proposal이 먼저 D-001을 대체) `DECISION_CONFIRM_PREVIEW_CHANGED`로 아무것도 쓰지 않는다. 다시 preview하면 대상이 `superseded`로 보이고, 확정은 `DECISION_SUPERSEDE_TARGET_INVALID`로 거부된다. 사람은 reject할 수 있다.
5. D-001을 `superseded`로 표시하는 것은 Human confirm의 결과로서 DecisionService가 한다(lifecycle field `state`, `superseded_by`만, lock은 유효). agent 경로는 없다.
6. 같은 대상을 대체하는 pending proposal이 여럿이면 모두 목록에 남고, 처음 확정된 것만 성공한다. 경쟁을 미리 알리는 표시는 이번 범위 밖이다(§9 위험).

## 4. Human authority 경계

H-71이 바꾸는 것은 proposal의 표현력뿐이다. 다음은 그대로다.

- Agent may propose. proposal은 Project Truth가 아니고 review의 Decision이 아니다(pending은 `listDecisionProposals`가 정함).
- confirm·reject는 human만(`DECISION_PERMISSIONS`). MCP tool 수 9개 그대로, confirm·reject tool 없음.
- confirmed Decision 내용은 누구도 다시 쓰지 않는다(바꾸려면 새 proposal로 supersede).
- BLOCK은 Human이 확정한 `enforcement: block` Decision에서만 생긴다. agent의 proposal은 review verdict를 바꾸지 않는다.
- confirm, index, Truth 수정을 자동 실행하지 않는다. 확정 뒤 `duoctl index`는 사람이 실행한다(안내만).
- Informed Confirm은 제안자를 보여야 한다. 지금 preview에는 `proposed_by`·`proposed_by_kind`가 없으므로, 구현 범위에 "Proposed by: codex (agent)" 표시를 넣는다(CLI·UI, 읽기 전용).

## 6. H-71 제안 문구 (승인 시 `docs/conflicts.md`에 기록할 초안)

> | H-71 | (승인일) | T35 Full Decision Proposal. H-36(C140)의 MCP proposal 범위를 넓힌다. H-36은 "supersedes·forbids는 Human이 확정 시 다룸"이라고 했지만 확정 단계에는 그 수단이 없어 enforce·supersede Decision이 YAML 직접 작성으로만 만들어졌다. T34.2·T34.3 Informed Confirm(확정 전 전체 candidate 표시, digest-bound confirm, UI previewDigest 필수)을 전제로 다음을 결정한다. (1) `duo_propose_decision` 입력에 `forbids`(`{paths?, symbols?, dependencies?}`, 기존 Decision schema 형식), `enforcement`(`warn`·`block`), `supersedes`(기존 Decision ID 하나)를 추가한다. 다른 field(`evidence`, `source`, `extensions`, `kind`)는 계속 agent-facing이 아니다. `forbids.paths`는 review가 compile할 수 있는 repository pattern만 받는다. 생략한 `enforcement`는 생략으로 저장하고 기본값을 만들지 않는다. (2) proposal은 Project Truth가 아니며 review verdict를 바꾸지 않는다. BLOCK은 Human이 확정한 `enforcement: block` Decision에서만 생긴다. (3) agent는 confirm·reject를 할 수 없고, confirmed Decision을 수정하거나 기존 Decision을 직접 `superseded`로 표시할 수 없다. supersede는 Human이 새 proposal을 확정할 때 DecisionService가 기록한다. supersede 대상은 proposal 단계에서 존재하고 `confirmed`여야 하며, self·cycle은 확정 단계에서 거부한다. (4) Human은 Informed Confirm에서 제안자(agent 이름·종류)를 포함한 전체 내용을 확인하고 ID를 다시 입력하며, 확정은 그 preview의 digest에 묶인다. (5) MCP tool 수(9개)와 confirm·reject 부재, write boundary, confirm·index·Truth 자동 실행 금지는 바뀌지 않는다. (6) 이 결정은 branch `next`(H-70 development track)에만 적용되며 0.2.1과 External Validation 01에는 영향이 없다. main 반영과 publish는 별도 Human Decision이다 | integration(MCP), CLI·UI preview, docs 06·07, `next` |

## 9. 남은 위험

- agent가 과도하거나 잘못된 enforce 규칙을 제안할 수 있다. 확정 전에 전부 보이지만, 사람이 `forbids` 범위를 정확히 판단할 근거(현재 몇 개 파일·symbol에 걸리는지)는 preview에 없다. "현재 매칭 수" 표시는 Graph가 필요해 별도 후보로 둔다.
- 제안 남발로 pending 목록이 noise가 될 수 있다. 상한이나 정리 도구는 이번 범위 밖.
- 같은 대상을 대체하는 경쟁 proposal을 미리 알리지 않는다(확정 시점에만 드러남).
- 수정 경로는 reject 후 재제안이다. 사람이 proposal 일부만 고치는 CLI는 없다(그건 YAML 직접 수정으로 돌아감).
- digest의 staleness 포함으로 인한 re-preview 빈도(T34.3 dogfood 관찰 항목)는 그대로다.
- H-71은 H-36을 바꾸는 Human Decision이다. 승인 전 구현하지 않는다.

**S1 실패 원인.** agent가 `forbids.symbols: ["src/db/legacy-db.ts#LegacyDb"]`를 보냈다. review의 `decision-forbids`는 바뀐 symbol의 qualified name(`LegacyDb`, `LegacyDb.run`)을 `*` wildcard 패턴과 비교하므로 이 문자열은 어떤 symbol과도 맞지 않고, 규칙은 조용히 효력이 없다.

1. agent-facing 계약(schema, tool 설명)이 `forbids.symbols`의 의미(qualified name wildcard, 예: `LegacyDb`, `*LegacyDb*`, `LegacyDb.run`)를 알려 주지 않는다.
2. DUO 자신의 context 출력이 symbol을 `ref: "src/db/legacy-db.ts#LegacyDb"` 형식으로 보여 주고, agent는 그 형식을 그대로 썼다(governs.symbols도 같은 형식이며 index가 "matches no symbol"을 경고했지만 forbids에는 경고가 없다).
3. MCP는 paths만 compiler로 검증했고 symbols는 임의 text를 받는다. review는 맞지 않는 패턴을 오류로 보이지 않는다.
4. Informed Confirm은 문자열을 정확히 보이지만 그 패턴이 지금 아무것도 가리키지 않는다는 신호는 없다.
5. 의미의 한계도 있다: `forbids.symbols`는 이름이 맞는 symbol의 변경을 잡을 뿐 "LegacyDb를 새로 사용하는 코드"(다른 이름의 함수가 LegacyDb를 호출)를 잡지 않는다.
