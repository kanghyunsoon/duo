# T27.1 OpenAI-Compatible Provider

0.2.0 Milestone E의 첫 task다. 결정: H-49, H-60. DUO의 provider-neutral LLM 구조를 그대로 두고, 사람이 project.yaml에 명시한 OpenAI-compatible endpoint를 Responses 또는 Chat Completions transport로 쓸 수 있게 했다. 공식 `OpenAIResponsesProvider`는 바뀌지 않았다.

## 1. 기존 구조 감사

| 층 | 무엇 | T27.1 |
|---|---|---|
| `LLMProvider` 계약(director) | `id`, `status()`, `invoke(request)`, `cacheIdentity()`. request = instructions, input, text 또는 structured(JSON Schema), maxOutputTokens, signal | 그대로 |
| `invokeLLM`(director) | 유일한 호출 경로: status·취소 확인, instructions·input redaction(0.1.2), 시간 제한(`llm.timeout_ms`), 응답 cache(`cacheIdentity` + redacted request), token 추정, structured 검증(`validate`), Evidence 인용 검사, 실패 message redaction | 그대로 |
| 공식 provider(integration) | 공식 endpoint, Responses만, `store: false`, `maxRetries: 0`, SDK 환경 값 차단, 동적 import, 오류 분류(C188~C196) | endpoint 상수를 core에서 가져옴(같은 값) |
| factory·pool | 설정 + 환경 → provider, 상태, 이유 | `openai-compatible` 분기, pool key에 transport·mode |
| semantic review | director `semanticAssist` → `invokeLLM`. CLI `review --semantic`, MCP `includeSemanticAssist` 모두 같은 operation | 그대로 |
| doctor·status | factory 상태·이유 code | compatible이면 사람 출력에 transport와 origin |

계약을 넓힐 필요가 없었다. 새 provider는 같은 `LLMProvider`를 구현하고 `invokeLLM` 뒤에만 있다.

## 2. 설정

project.yaml `llm`에 `provider: openai-compatible`, `transport`, `structured_output`을 더했다(additive). `openai-compatible`은 `model`, `base_url`, `transport`, `api_key_env`, `structured_output`이 모두 필수이고, 하나라도 없으면 project.yaml 검증 오류다(`SCHEMA_INVALID_VALUE`, 예: `llm.transport: is required for provider openai-compatible (no default): responses or chat-completions`). 알 수 없는 값(`auto`, `none`)은 enum 오류다. `transport`·`structured_output`을 `openai-responses`에 쓰면 오류, `provider: none`은 다른 값을 무시한다. 기존 `none`·`openai-responses` 설정은 그대로 유효하고 의미도 같다(`openai-responses`의 `base_url`은 이전처럼 실행 시 unavailable).

정적인 설정 오류는 load 오류, 환경에 따라 달라지는 문제(key 없음, `OPENAI_CUSTOM_HEADERS`)는 provider `unavailable`이다. 설정 오류가 있는 project.yaml은 다른 Truth 오류와 같이 doctor의 `truth.project`에 code와 경로로 보인다.

**api_key_env**: 기본값이 없다. `ENV_NAME_PATTERN`(`^[A-Za-z_][A-Za-z0-9_]{0,127}$`)이 아니면 오류. key는 그 변수에서만 읽는다(`OPENAI_API_KEY`가 있어도 쓰지 않음, 테스트로 고정). `api_key_env: OPENAI_API_KEY`를 직접 쓰는 것은 허용한다.

## 3. Endpoint 정책과 공식 endpoint 보호

core `llm-endpoint.ts`의 `parseCompatibleBaseUrl`(WHATWG URL). 공식 provider의 `OPENAI_OFFICIAL_BASE_URL`도 같은 파일로 옮겨 하나의 원천이 됐다.

| 허용 | 거부(code) |
|---|---|
| `https://gateway.example/v1`, `https://gateway.example/prefix/openai/v1`, `https://gateway.example` | `http://gateway.example/v1`, `http://192.168.1.10/v1`, `http://10.0.0.5/v1`, `http://my-internal-server/v1`(`insecure-http`) |
| `http://localhost:8080/v1`, `http://127.0.0.1:8080/v1`, `http://127.12.34.56:8080/v1`, `http://[::1]:8080/v1` | `ftp://…`(`scheme`), `/relative/v1`, `//host/v1`(`not-absolute`) |
| | `https://user:pass@host/v1`, `https://@host/v1`(`userinfo`), `?x=1`, 빈 `?`, `#fragment`(`query-or-fragment`), `https://host//v1`(`empty-path-segment`) |
| | `https://api.openai.com/v1`, 대문자, 끝 점(`api.openai.com.`), `eu.api.openai.com`(`official-openai`: "use provider openai-responses") |

오류 message는 code의 설명이며 값(URL, user info, host)을 되풀이하지 않는다(테스트: `hunter2`, host가 diagnostic에 없음). canonical은 origin + path(끝 `/` 제거, 기본 port 제거, host 소문자), 표시는 origin(`scheme://host[:port]`)뿐이다. 환경 변수로 `base_url`을 바꾸는 기능은 없다(SDK에 `baseURL`을 명시하므로 `OPENAI_BASE_URL`은 읽히지 않는다, 테스트로 고정).

## 4. Endpoint 결합

SDK는 `new URL(baseURL + path)`이고 끝 `/`와 앞 `/`가 겹치면 하나를 뺀다. canonical에는 끝 `/`가 없으므로 `https://g.example/a/b/v1` → `…/a/b/v1/chat/completions`, `https://g.example` → `…/chat/completions`, 설정의 `…/v1/` → `…/v1/chat/completions`. `/v1/v1`이나 prefix 누락이 없다(실제 SDK + fake fetch로 URL 확인). 빈 segment(`//`)는 설정에서 거부한다.

## 5. Request mapping

| | Responses | Chat Completions |
|---|---|---|
| 본문 | `model, instructions, input, store: false, max_output_tokens?` | `model, messages: [system: instructions, user: input], max_tokens?` |
| `json-schema` | `text.format = { type: "json_schema", name, schema(strict 변환), strict: true }` | `response_format = { type: "json_schema", json_schema: { name, schema, strict: true } }` |
| `json-object` | `text.format = { type: "json_object" }` + 지시문에 schema | `response_format = { type: "json_object" }` + 지시문에 schema |
| `prompt-only` | format 없음 + 지시문에 schema | `response_format` 없음 + 지시문에 schema |
| 없는 것 | tools, conversation, `previous_response_id`, stream | tools, functions, tool_choice, `n`, stream, `store` |

`json-object`·`prompt-only`의 지시문 끝에 "JSON 객체 하나만, Markdown·code fence 없이, 이 JSON Schema에 맞게"와 schema를 붙인다(schema는 DUO가 만든 것이라 redaction 경계 뒤에 붙여도 repository 내용이 없다). 6조합 모두 실제 SDK가 보내는 HTTP body를 캡처해 해당 field만 있고 다른 mode의 field가 없음을 확인했다. `prompt-only`도 parse와 검증은 기존 그대로다(code fence를 벗기지 않는다).

공식 provider 구현을 custom baseURL용으로 바꾸지 않았다. 공유한 것은 pure helper `toStrictSchema`와 `OPENAI_STRUCTURED_OUTPUT_POLICY`뿐이다. 응답 해석과 오류 mapping은 provider별로 따로 둔다(H-49).

## 6. Fallback, retry, timeout, redirect

- **fallback 없음**: `json-schema` 400 → 한 요청, `provider-error`, `json-object`·`prompt-only` 재시도 0. Responses 404 → Chat 0회. Chat 404 → Responses 0회. `/models` 0회(요청 경로를 모두 기록).
- **retry 없음**: `maxRetries: 0`. 429·500·503·network error 모두 요청 1회(SDK가 `retry-after: 0`을 받아도).
- **timeout**: `invokeLLM`의 시간 제한이 멈춰 있는 요청을 끊는다(요청 1회, `timeout`). SDK 시도당 timeout은 10분으로 DUO보다 길다.
- **redirect**: 주입한 fetch가 마지막에 `redirect: "manual"`을 강제한다. 3xx는 그대로 SDK에 돌아가 `provider-error`("the endpoint answered with a redirect (HTTP 307); DUO does not follow redirects")가 된다. 실제 loopback 서버 둘로 cross-origin 307을 재현해 두 번째 origin이 요청을 하나도 받지 않음을 확인했다. 이 줄을 지우면 테스트가 실패한다(mutation 확인). SDK가 fetch 주입을 지원하므로 새 HTTP client가 필요 없었다.

## 7. Redaction, cache, 오류

- **redaction**: compatible provider는 `invokeLLM` 뒤에만 있다. 바뀐 코드 줄에 OpenAI 형식·AWS 형식 secret을 넣은 fixture로 두 transport × 필요한 mode에서 캡처한 HTTP body에 원문이 없고 `[REDACTED]`가 있다. Review JSON stdout 전체, semantic supplement, stderr, MCP 결과, `.duo-project/cache/llm/` 파일에도 secret·key·endpoint path가 없다. Authorization header는 mock 안에서 값 비교만 하고 저장·출력하지 않는다.
- **cache identity**: `openai-compatible;origin=…;endpoint=<canonical sha256 앞 16자>;transport=…;structured=…;policy=strict-1;adapter=1;model=…`. endpoint·transport·model·mode가 다르면 miss, key만 다르면 같다. secret만 다른 같은 redacted 요청은 hit(0.1.2 불변식). path는 hash로만 들어가 Review의 provider 기록에도 나오지 않는다.
- **오류 분류**: 400·404·422 `provider-error`, 401·403 `authentication`, 408·409·5xx `unavailable`(retryable), 429 `rate-limit`, 3xx `provider-error`, timeout·abort·연결 실패는 class 이름으로. 성공 응답 뒤 JSON 아님, 빈 출력, null·배열 content, refusal, `finish_reason` length, choice 없음, incomplete, schema 불일치, 알 수 없는 field는 `invalid-response`. message는 "the endpoint …"로 DUO가 만들고 URL·key·SDK message를 담지 않는다.

## 8. Doctor와 status

Doctor는 network 없이 설정과 환경만 본다. configured면 `ok`: `openai-compatible · m-1 · chat-completions · json-object · http://127.0.0.1:<port> · key from GMS_E2E_KEY (value not shown)`. key 변수가 없으면 `warning credential-missing`(종료 코드 0, Next에 넣지 않음). `duo.doctor/1`에는 이 check의 facts로 `endpoint`(origin), `transport`, `structuredOutput`을 더했다(facts 추가는 additive, compatibility 문서의 규칙). status는 사람 출력만 바뀌었다: `LLM: configured · openai-compatible m-1 · chat-completions · http://127.0.0.1:<port>`. `duo.status/1`은 그대로다. path, query, user info, key는 어디에도 나오지 않는다.

## 9. 회귀

- 공식 provider: 기존 테스트(공식 endpoint만, 환경 redirect 없음, `store: false`, strict json_schema, 오류 분류, cache identity, 사용자 base_url·`OPENAI_BASE_URL`·`OPENAI_CUSTOM_HEADERS` 거부)가 그대로 통과한다. 변경은 상수 import 한 줄이다.
- provider none: client를 만들지 않고 `cacheIdentity`가 없으며 `--semantic`이 요청을 보내지 않는다(e2e, 요청 0).
- install·doctor·status·review·MCP 기존 테스트 통과.

## 10. Live smoke

`pnpm test:compatible-smoke`(`tests/compatible-smoke`). `DUO_COMPATIBLE_SMOKE=1`과 `DUO_COMPATIBLE_SMOKE_BASE_URL`, `_MODEL`, `_TRANSPORT`, `_STRUCTURED_OUTPUT`, `_API_KEY_ENV`(key가 있는 변수의 이름)가 모두 있을 때만 실제 요청 하나를 보낸다. 없으면 skip(network 0). 기본 test·CI·release preflight에 들어가지 않는다. key는 환경 변수에서만 읽고, 출력은 provider kind, origin, transport, mode, model, 결과 category 한 줄이다. loopback 가짜 endpoint(`/secret-prefix/v1`)로 harness를 실행해 성공과 출력에 path·key가 없음을 확인했다. 실제 GMS 등 외부 endpoint는 실행하지 않았다.

GMS 전용 class·분기는 없다. README의 GMS 예시는 "설정 예시이며 endpoint capability는 확인이 필요"로 구분했고 transport는 공개 예시에 맞춰 `chat-completions`, structured_output은 `prompt-only`로 두었다. Responses 지원은 주장하지 않는다.

## 11. 검증

- core `llm-endpoint.test.ts`(6): 허용·거부 URL, 필수 필드, enum, provider별 field, 값 비노출.
- integration `llm/compatible/provider.test.ts`(13): 6조합 body·URL·key·redirect 옵션, prefix 결합, 모든 mode의 DUO 검증, invalid-response 경우, fallback 0, retry 0, 오류 분류, timeout, cross-origin redirect, redaction, cache identity, response cache hit·miss, factory 환경 규칙.
- `tests/cli/compatible.e2e.test.ts`(7, conformance 포함): 빌드된 duoctl(설치본)로 loopback endpoint에 review `--semantic` 4조합, fallback·retry·redirect, cache, MCP `includeSemanticAssist`, doctor·status, 설정 오류 비노출, provider none.
- mutation: redirect 강제, `store: false`, prompt-only의 format 제외를 각각 지우면 테스트가 실패한다.
