# T24.2 Python source-root discovery (C219) and T24.1 residual audit

0.2.0 Milestone C의 두 번째 task다. 결정: H-52. Python 공개 level은 L1 그대로다.

## 1. 결과

Python absolute import는 이제 저장소 root와 `src/`뿐 아니라, package 구조와 project metadata에서 찾은 source root 아래에서도 해석된다. 디렉터리 이름은 보지 않는다. 한 파일이 쓸 수 있는 root 둘 이상에 같은 module이 있으면 edge를 만들지 않는다. 해석 결과는 파일 추가·삭제와 metadata 내용 변경에 다시 계산된다. analyzer 출력, Symbol, Graph schema, 공개 형식은 그대로다.

## 2. Phase 0: T24.1 잔여 의미 감사

### 2.1 Python 같은 이름 정의 (0-A)

`bench/experiments/python-redefinition.mjs`로 확인했다.

| case | Symbol | primary(`source`, Evidence pointer) | Context(T24.1 이후) | Review seed(마지막 정의 수정) |
|---|---|---|---|---|
| A. `def foo(): return 1` 뒤 `def foo(): return 2` | `foo` 하나, additional 1개 | 첫 정의(실행 시 덮여 쓰이지 않는 쪽) | 두 정의 모두, 범위 `:1-2,5-6` | `foo` |
| B. `@overload` stub 2개 + 구현 | `foo` 하나, additional 2개 | 첫 `@overload` stub(구현은 additional) | stub 둘과 구현 모두 | `foo` |
| C. class 안 `def foo(self)` 뒤 `def foo(self, x)` | `A.foo` 하나, additional 1개 | 첫 정의 | 두 정의 모두 | `A.foo` |

Evidence hash는 세 경우 모두 모든 정의를 덮는다. Python의 일반 재정의는 overload가 아니다(나중 정의가 이름을 다시 묶는다). 지금 primary가 실행되지 않는 첫 정의를 가리키고, Context는 어느 정의가 유효한지 말하지 않는다. T24.1 이전에는 그 죽은 정의만 보였으므로 T24.1은 정보를 늘렸고 되돌리지 않는다. 남은 의미 문제는 C226(Open)이다.

제안(구현하지 않음): Python extractor에서 `@overload`(`typing.overload`·`typing_extensions.overload`) 정의를 본문 없는 선언으로 넘겨 구현이 primary가 되게 하고, 같은 scope의 일반 재정의는 마지막 정의를 primary로 한다. analyzer 출력(`source`)이 바뀌므로 Python analyzer version을 올리고 재분석하며, Graph 변화는 재정의가 있는 Python Symbol에 한정된다. C219와 무관한 analyzer 의미 변경이라 따로 진행한다.

### 2.2 Evidence pointer와 hash (0-B)

결론은 A다: repository Evidence의 hash는 Symbol 전체(모든 위치)의 hash이고, pointer는 primary를 보여 주는 표시용 위치다(C227).

| 질문 | 확인 |
|---|---|
| 1. hash는 무엇의 hash인가 | core `Evidence.contentHash`: "the exact content this evidence stands for". Symbol은 모든 위치의 정확한 slice를 source 순서로 `\n`으로 이은 text의 sha256(T24.1). 위치가 하나면 그 slice(이전과 같음) |
| 2. pointer slice로 hash를 재현해야 하는가 | 그렇게 하는 코드가 없다. 위치가 여럿이면 재현되지 않고, 하나면 재현된다(test로 고정) |
| 3. Review Record 검증 | `verifyReviewRecord`는 schema와 content-addressed record ID만 본다. pointer·hash 관계를 쓰지 않는다 |
| 4. trace·UI·MCP 노출 | CLI review는 pointer 경로·줄, UI Reviews·Evidence는 pointer와 primary 줄(`/api/source`)만 보여 준다. hash의 의미를 사용자에게 설명하는 surface는 없다. MCP는 값으로만 돌려준다 |
| 5. stale evidence 판정 | 쓰지 않는다. freshness는 파일 fingerprint로 판정한다 |
| 6. Decision evidence | Truth의 Decision evidence `content_hash`는 읽기만 하고 repository Evidence와 대조하지 않는다 |

고정: core `Evidence.contentHash` 주석, [03 Evidence](../03-data-model.md), `overloads.e2e.test.ts`의 invariant test(합 hash, primary pointer, 위치 하나일 때 pointer slice로 재현).

## 3. 이전 Python resolution pipeline (C219 감사)

| 지점 | 이전 동작 |
|---|---|
| 파일 발견 | scanner, `.py`는 Python analyzer(L1) |
| module 이름 | 따로 계산하지 않는다. specifier(`app.models`, `.models`, relative level)를 그대로 넘긴다 |
| relative import | importing 파일의 디렉터리에서 level만큼 올라가 `<rel>.py` 또는 `<rel>/__init__.py`. 저장소 밖이면 external |
| absolute import | 고정 목록 `PYTHON_ROOTS = ["", "src/"]` 아래에서 같은 두 후보. 0개 external(stdlib·설치 package), 2개 이상 ambiguous |
| `__init__.py` | package 자체의 후보 파일일 뿐 root 결정에 쓰지 않음 |
| namespace package | 별도 취급 없음(root·src 아래면 파일 후보로 찾힘) |
| 위치 | graph builder의 module resolver(`createLanguageModuleResolver`). analyzer가 아니다 |
| analysis cache | key는 path·contentHash·analyzer identity. import 해석은 analysis에 없으므로 영향 없음 |
| resolution 저장·무효화 | 파일별 module 결과를 index state에 저장. `stale-version`(resolver version), `stale-source`(그 파일 변경), `stale-file-set`(파일 추가·삭제, 모든 결과), `stale-config`(resolver가 알린 config 파일 변경). Python은 config 파일이 없었다 |
| IMPORTS edge | resolved일 때만 File → File, `resolution: "python-local"` |
| Context | IMPORTS는 traversal edge(가중치 0.5). 같은 파일의 Symbol은 CONTAINS로 이어진다 |

## 4. 발견 규칙

`packages/graph/src/build/resolve/python.ts` `discoverPythonRoots`. index 실행마다 한 번, 첫 Python 요청 때 계산한다.

| root | 조건 | 쓰는 파일 |
|---|---|---|
| repository | 항상 저장소 root(이전과 같음) | 모든 파일 |
| src | 항상 `src/`(이전과 같음) | 모든 파일 |
| package | `__init__.py`가 있고 부모에는 없는 최상위 regular package의 부모 디렉터리. package 이름이 Python identifier여야 한다(`10. Feature`, `my-lib`은 아님) | 그 부모 디렉터리 아래 파일 |
| metadata | Python project 디렉터리 P와, P/src에 Python 파일이 있으면 P/src. P는 `pyproject.toml`에 `[project]`·`[build-system]`·`[tool.poetry]`가 있거나 `setup.cfg`에 `[metadata]`·`[options]`가 있는 디렉터리 | P 아래 파일 |

- 해석: 파일 F가 쓸 수 있는 root(위 표의 범위에 F가 드는 것)에서 `<root>/<a/b>.py`, `<root>/<a/b>/__init__.py` 후보를 모은다. 1개면 resolved, 2개 이상이면 ambiguous(edge 없음), 0개면 external이다. relative import는 이전과 같다.
- 디렉터리 이름(backend, api, server, app)은 보지 않는다. "Python 파일이 있는 모든 부모"를 root로 삼지 않는다.
- 범위를 두는 이유: `one/app`과 `two/app`이 있을 때 저장소 root의 `main.py`가 `app.models`를 쓰면 어느 쪽도 고르지 않는다(external). `one/` 안의 파일은 자기 project의 `one/app`을 쓴다. 다른 project 디렉터리의 package를 가로질러 잇지 않는다.
- 순서: root는 path, scope의 UTF-8 순이다. 파일 시스템 순서나 Set 순서와 무관하다(test로 확인).

### pyproject·package metadata 범위

| metadata | 처리 |
|---|---|
| `pyproject.toml` `[project]`·`[build-system]`·`[tool.poetry]` | P와 P/src: setuptools·hatchling·poetry가 설정 없이 package를 찾는 기본 위치 |
| `setup.cfg` `[metadata]`·`[options]` | 같음 |
| tool 설정뿐인 `pyproject.toml`(`[tool.ruff]` 등), uv workspace 정의 | project로 보지 않음 |
| package 위치를 옮기는 설정: `package-dir`/`package_dir`, `packages`, `py-modules`, `where`, `sources`, `only-include`, `[tool.setuptools.packages.find]`, `[options.packages.find]`, `[tool.hatch.build…]`, `[tool.pdm.build]` | 해석하지 않는다(UNKNOWN). 그 project에는 metadata root를 만들지 않고 구조 root만 쓴다 |
| `setup.py` | 코드이므로 읽지 않는다. 있으면 그 디렉터리의 metadata root를 만들지 않는다(UNKNOWN) |

TOML 전체를 해석하지 않는다. 표 이름과 key 이름만 줄 단위로 찾는다. 저장소 밖(site-packages, venv, PYTHONPATH, home)은 보지 않고, metadata는 core `readSourceFile`(저장소 경계·symlink 검사)로 읽는다.

## 5. Cache invalidation

같은 Python 파일 byte로도 root가 바뀌면 해석이 달라진다. 해석은 analysis cache가 아니라 module resolution 결과에 있으므로 그 무효화에 연결했다.

- `PYTHON_RESOLUTION_VERSION` 1 → 2: 저장된 Python 결과는 한 번 `stale-version`으로 다시 계산된다. version 문자열은 Graph에 없다.
- 파일 추가·삭제(package 디렉터리, `__init__.py`, root 이동, rename, metadata 파일 생성·삭제): 기존 `stale-file-set`.
- metadata 내용 변경: Python 파일은 읽은 `pyproject.toml`·`setup.cfg` 목록을 `configFiles`로 기록한다. 내용 hash가 바뀌면 모든 Python 파일이 `stale-config`가 된다. TypeScript 파일은 영향이 없다.
- 이 기록을 빼면 "metadata가 package를 옮김" 단계에서 incremental Graph가 clean full과 달라지고(edge 24 대 23) 오래된 edge가 남는 것을 test로 확인했다.
- mtime을 쓰지 않는다. analyzer version은 그대로다(parse 결과 불변).
