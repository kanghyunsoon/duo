# T24.4 Python effective definition (C226)

0.2.0 Milestone C의 네 번째 task다. 결정: H-54. Python 공개 level은 L1 그대로다.

## 1. 결과

Python은 같은 scope의 같은 이름 정의를 Symbol 하나로 합친다(T18.0). 지금까지 그 Symbol의 primary 위치(Graph `source`)는 맨 앞 정의였다. 이제 syntax만으로 실효 정의가 확실한 두 경우에 primary가 그 정의다.

- 같은 suite의 일반 재정의: 마지막 `def`
- 인식된 `typing.overload` stub과 구현 하나: 구현

나머지(property 계열, 조건부 정의, 모르는 decorator, 다른 binding이 끼어든 경우, 구현 없는 overload)는 이전처럼 맨 앞 정의가 primary다. 모든 정의는 계속 Symbol의 위치다. Symbol ID, Graph schema, payload, Evidence ID와 hash, Context 본문, Review seed는 그대로이고, 바뀌는 것은 해당 Symbol의 `source`와 `additionalLocations`가 서로 자리를 바꾸는 것뿐이다. 그 결과 Evidence pointer, UI `Show lines`, 검색 location, Packet item `source`가 실효 정의를 가리킨다.

질문에 대한 답:

1. **persisted `source`를 바꿔야 하는가.** 값이 실제로 쓰이는 곳(Evidence pointer, UI, 검색, Packet item `source`)은 모두 `source`를 읽는다. query layer에서 바꾸려면 이 소비자마다 Python 의미를 알거나 별도 metadata를 읽어야 한다. `source`를 바꾸는 것이 가장 작다.
2. **query layer `preferredLocation`이면 충분한가.** 실효 정의 판정에는 decorator, import, suite 같은 AST 사실이 필요하고 Graph에는 없다. query layer가 계산하려면 그 사실을 어딘가 저장해야 한다(§3 B·C·D).
3. **digest.** 재정의가 있는 Python Symbol의 행만 바뀐다. payload `analyzerVersion`을 올리지 않으므로 다른 Python 행과 다른 언어는 그대로다. 5개 real-world 저장소 digest는 모두 그대로다(FastAPI에 해당 패턴 없음, §7.4).
4. **adoption baseline.** violation key에 줄 번호가 없고, Review는 baseline을 key로 비교하므로 새 위반처럼 보이지 않는다.
5. **migration·reindex.** schema·format migration 없음. analyzer identity가 바뀌어 기존 index의 Python 파일 분석 cache가 맞지 않게 되고, 다음 index가 보통 invalidation으로 다시 분석한다.

## 4. 규칙

`PythonExtractor.preferredDefinition`. 정의 묶음은 지금 Symbol identity 그대로다(module `foo`, `A.foo`, `A.static.foo`, 중첩 class). C226 때문에 묶음을 넓히지 않는다. 함수 안 중첩 정의는 이전처럼 Symbol이 아니다.

공통 조건(하나라도 아니면 맨 앞 정의 유지):

- 묶음의 모든 정의가 함수다(class가 섞이면 제외).
- 모든 정의가 같은 suite에 있고, 그 suite가 module 또는 class body다. if, else, try, except, with, for, while 안은 실행에 따라 binding이 달라지므로 판정하지 않는다(같은 if block 안 두 정의도 제외).
- 그 suite의 다른 문장이 같은 이름을 묶거나 지우지 않는다: 대입, import, `del`, for·with 대상, block 안의 같은 이름 `def`, identity가 다른 같은 이름 `def`(`@staticmethod` 대 instance).
- decorator는 `@staticmethod`, `@classmethod`(이미 identity에 반영), 인식된 overload만 있다. 그 밖의 decorator(`@property`, `@x.setter`, route 등록, alias)는 앞 binding 위에 무엇을 만들거나 등록할 수 있으므로 판정하지 않는다.
- 순서는 한 파일 안의 canonical SourceLocation 순서다. 다른 파일이나 import 실행 순서는 쓰지 않는다.

**일반 재정의.** overload stub이 없으면 마지막 정의가 primary다. `def`와 `async def`는 같은 이름 binding이라 같은 규칙이다(I, J).

**typing.overload.** 인식은 decorator가 `@overload`이고 module에 `from typing import overload`가 있거나, `@typing.overload`이고 `import typing`이 있을 때만이다. 그 import가 그 이름의 유일한 module-level binding이어야 한다(alias, star import, 다른 import·대입·def 없음, class body에서 가리지 않음). `typing_extensions`, `from typing import overload as ov`, 같은 이름을 다시 묶는 경우는 인식하지 않는다(alias 해석 없음). 본문이 `...`라는 사실은 쓰지 않는다. stub이 있으면, stub이 아닌 정의가 정확히 하나이고 그것이 마지막일 때 그 구현이 primary다. 구현이 없거나, 둘 이상이거나, 구현 뒤에 stub이 있으면 판정하지 않는다. stub은 Symbol의 위치로 남아 Context와 Evidence에 계속 나온다.

**property.** `@property` 뒤 `@value.setter`·`@value.deleter`는 descriptor를 단계적으로 만든다. decorator 조건 때문에 판정하지 않고 getter가 primary로 남는다(이전과 같음). property 모델은 만들지 않았다.

**범위.** runtime binding 전체, 조건 실행, decorator 의미, type checker 수준 overload 해석, 동적 재대입(`global`, `setattr`, 함수 안 대입)은 다루지 않는다.

## 5. 소비자

### 5.1 Evidence

hash는 모든 위치의 aggregate(canonical 순서)라 primary 선택과 무관하고 그대로다. Evidence ID도 node ID + hash라 그대로다. pointer `lines`는 primary이므로 실효 정의를 가리킨다. pointer slice로 hash를 재현하지 않는다는 T24.1·T24.2 invariant는 유지한다. 형식 변경 없음.

### 5.2 Context

모든 정의와 stub을 canonical 순서로 보이는 T24.1 표현을 그대로 둔다. 실효 정의를 앞으로 옮기지 않았다: overload에서는 stub(type signature) 다음에 구현이 오는 원문 순서가 읽기 자연스럽고, 순서를 언어마다 다르게 하면 Context 본문과 digest가 바뀐다. 바뀌는 것은 item `source`(primary)뿐이다. ranking 변경 없음(C229). `CONTEXT_POLICY_VERSION` 2 그대로다.

### 5.3 Review

seed는 모든 위치와 hunk의 겹침이다. stub이나 앞 정의를 고친 hunk도 같은 Symbol을 seed한다(§7.3).

### 5.4 UI

`Show lines`는 Evidence pointer를 읽으므로 실효 정의를 보인다. 여러 위치 UI는 만들지 않았다. UI schema 불변.

### 5.5 Annotation attachment

builder의 annotation 후보가 Symbol의 primary 위치뿐이었다. primary를 마지막 정의로 옮기면 첫 stub 위의 `# duo: REQ`가 Symbol이 아니라 File에 붙는 회귀가 생긴다. 후보를 Symbol의 모든 위치(primary + `additionalLocations`)로 바꿨다. 규칙(바로 뒤 후보 → 감싸는 가장 작은 후보 → File)은 그대로다. 이전에 primary에 붙던 annotation은 그대로 붙고, 추가 위치 바로 위나 안의 annotation은 이제 File·바깥 class 대신 그 Symbol에 붙는다. 이 변화는 모든 언어에 적용된다(TypeScript overload signature, Java·C#·C++ overload, accessor 쌍). 5개 real-world 저장소에는 `duo:` annotation이 없어 Graph 변화가 없다.

## 6. Graph·cache·migration

- Symbol ID 변화 0.
- Graph schema, payload schema, `analyzerVersion`("1") 불변. Python analyzer identity에 `facts=definitions-1`(C++의 `facts=callables-1`과 같은 장치). analyzer registry digest가 바뀌므로 기존 index의 Python 분석 cache는 다시 만들어진다.
- Graph 행 변화: 판정이 바뀐 Python Symbol의 `source`·`additionalLocations`만.
- migration, 수동 reindex 불필요.

## 8. C218 suffix include invariant (H-54에 기록)

T24.3의 "쓰인 include 경로가 저장소의 한 파일 경로 끝과 같다" 증거는 C++ 선언·정의 쌍 판정의 보조 증거일 뿐이다. Graph IMPORTS 해석, 일반 C++ include resolver, build-system include path 추론, compiler 의미 추론에 쓰지 않는다. 조건도 그대로다: 저장소 안에서 suffix 일치가 정확히 하나, 선언·정의의 qualified owner·이름·signature 일치, 양방향 유일, 둘 이상이면 쌍 없음. 경로 비교는 저장소·Git 경로 기준의 결정적 정규화이고, OS의 대소문자 무시 동작을 근거로 느슨하게 하지 않는다.

## 9. 남은 correctness 항목과 Milestone C

| 항목 | 내용 | 분류 | L1 correctness를 막는가 |
|---|---|---|---|
| C224 | overload member identity | Deferred(H-52): member identity를 쓰는 첫 기능(L2 call resolution, member 단위 Truth 참조)과 함께 | 아니다. 모든 overload 위치는 C217로 보인다. 지금 member를 따로 가리키는 소비자가 없다 |
| C229 | polyglot Context ranking(FastAPI 생성 TS 편향) | 별도 Context milestone(0.2.0 audit §6) | 아니다. 후보 누락이 아니라 순위 문제이고, C219 뒤 Python 파일은 후보에 들어온다 |
| C232 | C++ Graph IMPORTS의 include path | C++ capability 개선(L1 `imports: partial`로 공개됨) | 아니다. 잘못된 edge가 아니라 문서화된 누락이다. 쌍 판정은 C218 증거로 따로 해결됐다 |
| C231 | Truth qualifiedName 참조가 header·cpp 두 Symbol과 일치 | **T24.5 제안** | **C++에서는 막는다** |

C231 판단 근거. header에 선언하고 `.cpp`에 정의한 C++ member는 qualifiedName이 같은 Symbol 둘이다. Truth 참조는 qualifiedName이 Symbol 정확히 하나와 일치할 때만 edge를 만들므로, 가장 자연스러운 C++ 이름 참조가 거의 모든 member에서 `DECLARED_SYMBOL_UNRESOLVED`가 된다. Requirement `implements`는 `paths`로 후보를 좁혀 피할 수 있지만 Decision `governs.symbols`는 paths 없이 해석되어(builder `declaredSymbol(dec, name, [])`) 피할 방법이 없다. 그러면 governs edge가 없어 Review가 그 Decision의 대상 변경을 Decision과 연결하지 못하고, adoption baseline에는 영구 `declared-reference` finding이 남는다. 잘못된 edge는 없지만(false negative), Truth → code 연결은 DUO의 핵심 계약이고 C++ 사용자에게 체계적으로 실패한다. T24.3이 그 쌍을 이미 보수적으로 증명하므로 해결 범위가 작다.

**판단: Python, Java, C#, TypeScript의 Milestone C 항목은 닫혔다(C217, C219, C226). C++은 C231이 남아 Milestone C를 지금 닫지 않는다. T24.5(C231)를 끝내고 Milestone C를 닫은 뒤 Milestone B Freshness로 간다.** C231을 0.2.0 이후로 미루는 결정이면 Milestone C를 지금 닫고 C231을 C++ 알려진 제한으로 문서화하면 된다(Human 결정 대상).

### 9.1 T24.5 제안: C231 C++ 선언·정의 쌍에 대한 Truth qualifiedName 참조 (구현하지 않음)

**문제.** `implements.symbols`, `governs.symbols`의 qualifiedName이 Indexer가 기록한 선언·정의 쌍 하나의 두 Symbol과 일치하면 지금은 unresolved, edge 없음이다.

**목표.** 일치하는 Symbol이 모두 정확히 한 declaration link 그룹의 구성원이고 다른 Symbol이 없을 때만, 그 참조를 그 그룹으로 해석한다.

**먼저 감사할 것.** builder에서 `declarationLinks` 계산과 `declaredCodeRelations` 순서, edge를 받는 소비자(trace, impact, Review governs·implements rule, Context seed, adoption baseline의 declared-reference finding, UI·MCP trace), 저장된 Review Record·baseline에 그 finding이 있을 때의 표시.

**설계안 비교.** (a) 그룹 구성원 모두에 기존 type edge(IMPLEMENTS·GOVERNS), (b) 정의에만, (c) 선언에만, (d) Graph 불변 + query layer에서 Truth 참조를 그룹으로 해석. 비교 항목: Graph digest(새 edge는 이전에 unresolved였던 참조에만 생겨야 함), 기존 edge 불변, Review가 header만 또는 cpp만 고친 diff를 Decision과 연결하는지, impact 방향, baseline(이전 finding이 "해결됨"으로 보이고 새 위반으로 보이지 않는지), edge metadata 형식(새 basis 값이 공개 계약 변경인지).

**규칙.** 이름만으로 그룹을 만들지 않는다(T24.3 link만 근거). 일치 Symbol에 그룹 밖 Symbol이 하나라도 있으면 지금처럼 unresolved. 쌍이 없는 경우(template, 내부 linkage, include 없음)는 그대로 unresolved. Requirement `paths`가 있으면 지금처럼 먼저 좁힌다. C232와 suffix include 범위(H-54)는 바꾸지 않는다.

**검증.** fixture: 쌍 + Decision governs, 쌍 + Requirement implements(paths 있음·없음), 쌍 + 같은 이름 세 번째 Symbol, template·static·익명 namespace(쌍 없음), link를 깨는 변화(include 제거, signature 변경)와 되살리는 변화의 incremental == clean full, 다른 파일의 변화로 link가 바뀔 때 edge가 stale하지 않음. real-world: 5개 저장소는 Truth 참조가 없으므로 digest 불변이어야 함.

**멈출 조건.** 새 edge type, Graph schema·payload 변경, 기존 edge 변화, baseline migration이 필요하면 구현하지 않고 보고한다.

**범위 밖.** C232, C224, Python·Java·C# Truth 참조 규칙, include resolver, Freshness.
