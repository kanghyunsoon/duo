# T26.2 Agent-facing Ambiguity Remediation

0.2.0 Milestone D의 마지막 task다. 결정: H-59. MCP `duo_get_context`가 `ambiguous`일 때 coding agent가 다음 시도를 알 수 있게 한다. 바뀐 것은 사람과 agent가 읽는 문구뿐이다. resolver, 후보, ranking, structured payload는 그대로다(같은 16개 과제의 `context --json` 결과가 수정 전과 byte 단위로 같다).

## 1. 기존 ambiguity 경로

| 층 | 무엇을 하는가 |
|---|---|
| Context Compiler `resolveSeeds`(`seeds.ts`) | task를 token으로 나눈다. 정의 ID, `/`가 있는 경로, 유일한 이름은 정확한 신호(exact)다. 같은 이름의 Symbol이 2~5개면 `symbol-name`, 같은 qualified name이 여럿이면 `qualified-name`, 정확한 신호가 없고 Requirement 둘 이상이 keyword 점수로 같으면 `keyword-tie` ambiguity다. ambiguity는 정확한 신호가 하나도 없을 때만 멈춘다(`exact === 0`) |
| `compileContext` | 멈추면 `status: "ambiguous"`, `resolution.ambiguities[] = { term, reason, options: [{ id, ref, kind, title? }] }` |
| Knowledge Gap | `ambiguous-target` gap(ask)과 질문 "\"term\" matches several targets: refs. Which one do you mean?" |
| integration `projectContext` | 같은 결과를 `duo.context/1` payload로(CLI `--json` result = MCP structuredContent) |
| MCP `duo_get_context` summary | `Context ambiguous` + `requiresHumanInput` + 사람용 질문. 다시 시도하는 방법은 없었다 |
| CLI `duoctl context` | 질문 줄과, T26.1부터 고정 안내 한 줄(`apps/cli` 메시지) |

T26.1의 고정 안내("`/`가 있는 저장소 상대 경로나 Requirement·Decision ID를 넣으면 정확한 시작점")는 두 군데에서 정확하지 않았다(C235). 첫째, 같은 파일 안의 후보(`src/shapes.ts#Circle.area`, `src/shapes.ts#Square.area`)는 경로로 구분되지 않는다. 경로를 넣으면 Context는 진행하지만 그 파일 전체에서 시작할 뿐 대상을 고르지 않는다. 둘째, tokenizer는 token 앞뒤의 `.`을 지우므로 `./src/util/text.ts`는 `/src/util/text.ts`가 되어 경로로 읽히지 않는다(수정 전 build에서도 ambiguous). 루트의 파일(`/` 없음)은 경로로 이름을 붙일 수 없다.

## 2. 공유 구조

`packages/director/src/context/remediation.ts`의 `ambiguityRemediation(ambiguity)` → `{ term, reason, handles, definitionIdAlso }`. resolver가 쓰는 token 규칙(`isPathSignal`, `isNameSignal`, 같은 `rawTokens`와 이름 정규식)으로 판정하므로 안내가 곧 resolver가 받아들이는 입력이다.

| handle | 조건 | 근거 |
|---|---|---|
| `path` | 후보마다 파일이 다르고 각 경로가 한 token으로 그대로 남으며 `/`를 포함 | 경로 token은 exact seed이고 그 파일에서 시작한다 |
| `qualified-name` | 후보의 qualified name이 모두 다르고 각 이름이 이름 token(ID 모양이 아님) | 유일한 qualified name은 exact symbol seed |
| `definition-id` | `keyword-tie`이고 후보가 모두 정의 ID | ID는 exact seed |
| 없음 | 어느 하나도 모든 후보를 가르지 못함(예: `a.ts#Pool.launch`, `a.ts#Worker.launch`, `b.ts#Worker.launch`) | 사람이 정해야 한다 |

`definitionIdAlso`는 symbol ambiguity에 handle이 있을 때만 true다. 과제에 실제 Requirement·Decision ID가 있으면 exact seed라서 Context가 진행하지만, 그 ID가 symbol 후보 중 하나를 고르지는 않는다. 그래서 "과제가 그 Requirement·Decision에 관한 것이면"이라는 조건을 붙이고, handle이 없는 경우에는 쓰지 않는다. 새 public field, action schema, framework는 없다. CLI와 MCP가 같은 판정을 각자 문구로 그린다.

## 3. 문구

MCP summary(agent용, 기존 `INDEX_REQUIRED:`와 같은 모양):

```text
Context ambiguous

requiresHumanInput: true
Question for the human: "normalize" matches several targets: src/game/physics.ts#normalize, src/util/text.ts#normalize. Which one do you mean?

AMBIGUOUS: "normalize" matches several targets. Retry duo_get_context with one target's repository-relative file path (as listed in context.resolution.ambiguities, without a leading ./) in the task. If the task is about a specific Requirement or Decision, its ID is also an exact starting point. Do not guess a target or invent an ID; if the task does not say which one, ask the human.
```

- qualified name: "… with one target's qualified name (as listed in context.resolution.ambiguities, for example Class.method) in the task. A file path does not tell these targets apart. …"
- 둘 다: "… repository-relative file path (without a leading ./) or qualified name …"
- Requirement tie: "AMBIGUOUS: several Requirements match this task equally. Retry duo_get_context with one Requirement ID (as listed in context.resolution.ambiguities) in the task. Do not guess …"
- 없음: "AMBIGUOUS: \"launch\" matches several targets. No single file path or name tells these targets apart. Ask the human which one is meant."

CLI(en·ko, 질문 줄 아래): `"normalize": add one target's repository-relative file path, as listed above (with its /, without a leading ./), to the task.` / `"normalize": 위 목록에 있는 대상 하나의 저장소 상대 파일 경로(/ 포함, 앞에 ./ 없이)를 과제에 넣으세요.` 같은 handle 다섯 가지와 ID 문장. 후보 목록은 원래 있던 질문 줄과 `context.resolution.ambiguities`에 그대로 있다. 가장 그럴듯한 후보를 고르라거나 첫 후보를 쓰라는 안내, 파일명·ID 예시 생성은 없다(`Class.method`는 형식 예시).

- resolver diff: 16개 과제(위 재시도 포함, `./src/util/text.ts`, `tune area src/shapes.ts`, `start launch src/jobs/a.ts`, `AuthService.refresh`, `Refresh Token`, `GAME-42`)의 `context --json` result가 수정 전·후 build에서 byte 동일.

- secret·경로: AWS 형식 canary를 과제에 넣어도 MCP·CLI 문구에 나오지 않는다. 문구는 저장소 상대 ref와 term만 쓰고 `redactSecrets`를 거친다. fixture 절대 경로와 home 경로는 나오지 않는다.

## 6. 다음: Milestone E — T27.1 OpenAI-Compatible Provider spec 제안(구현하지 않음)

H-49를 그대로 따른다. 공식 `OpenAIResponsesProvider`는 바꾸지 않는다(공식 endpoint, Responses API만, `base_url`·`OPENAI_BASE_URL` 거부, 테스트 그대로).

1. **별도 provider.** `llm.provider: openai-compatible`(core schema enum에 additive). integration `llm/compatible/`에 `OpenAICompatibleProvider`. 공식 provider와 코드·테스트·cache identity를 공유하지 않는다(공통 contract만).
2. **명시적 설정.** project.yaml `llm`: `model`(필수), `base_url`(필수), `transport: responses | chat-completions`(필수, 기본값 없음), `api_key_env`. 환경 변수(`OPENAI_BASE_URL` 등)는 endpoint를 바꾸지 못한다. 빠지면 `unavailable`이고 doctor·status가 이유 code로 보인다(`base-url-missing`, `transport-missing`, `credential-missing`; doctor reason 추가는 additive).
3. **자동 판단 금지.** Responses → Chat Completions fallback, endpoint capability 추측, `/models` 조회, model 선택이 없다. 실패는 그대로 실패로 보고한다.
4. **Transport.** Responses: 공식 provider와 같은 요청 모양(instructions, input, max_output_tokens, structured는 json_schema). Chat Completions: `messages = [system: instructions, user: input]`, `max_tokens`, structured는 설정한 방식. 두 transport의 응답·오류 mapping은 따로 둔다.
5. **Structured output.** 설정 `structured_output: json-schema | json-object | none`(endpoint마다 지원이 달라 명시). 어느 경우에도 DUO의 최종 schema validation과 evidence 인용 검사(`invokeLLM`)를 우회하지 않는다. `none`이면 지시문에 schema를 넣고 DUO가 검사한다.
6. **보안 경계.** 호출은 `invokeLLM`만 거친다: 0.1.2 공통 redaction(instructions·input), timeout은 DUO가 소유(SDK `maxRetries: 0`, SDK timeout은 DUO보다 길게), 실패 message redaction. key는 환경 변수에서만 읽고 파일·metric·record·cache key·문구에 없다. README와 `--semantic` 안내에 "Evidence 발췌가 설정한 endpoint로 전송된다"를 쓴다.
7. **오류 분류.** 401·403 `authentication`, 429 `rate-limit`, 400·404·422 non-retryable `provider-error`, 5xx·network `unavailable`, abort `timeout`·`cancelled`, 성공 응답 뒤 빈 응답·refusal·incomplete·JSON·schema·evidence 실패는 `invalid-response`(C188~C196 규칙과 같음).
8. **Cache identity.** `openai-compatible|<transport>|<정규화한 base_url>|<model>|<structured_output>|<adapter version>`. endpoint가 identity에 들어가 다른 endpoint의 답을 재사용하지 않는다(C212). secret 없음.
9. **검증.** fake fetch로 실제 SDK 요청을 두 transport에서 확인, 오류 mapping 표, redaction canary, cache identity 분리, 공식 provider 회귀 0, network 없는 CI. 실제 호환 endpoint(GMS 등) smoke는 사용자가 실행하는 opt-in이며 release gate가 아니다.
10. **범위 밖.** Anthropic·local provider, streaming, tool call, 여러 message 대화, endpoint 자동 탐색, GMS 전용 class.

Milestone E 시작 전 Human Decision이 필요한 항목:

- `api_key_env` 기본값: compatible provider에서 `OPENAI_API_KEY`를 기본으로 쓰면 공식 key가 제3자 endpoint로 갈 수 있다. 제안은 필수(기본값 없음).
- `base_url` scheme: 제안은 `https`만, `http`는 loopback(`127.0.0.1`, `localhost`)일 때만.
- `structured_output` 값 세 가지와 `none` 허용 여부.
- Responses transport에서 `store: false`를 보낼지: 공식 provider는 항상 보내지만 호환 endpoint는 모르는 field를 거절할 수 있다. 제안은 보내되 설정으로 끄지 않음(거절되면 `provider-error`로 보고).
- status·doctor에 endpoint host를 보일지(secret은 아니지만 사용자 환경 정보): 제안은 host만 표시.
- GMS smoke를 opt-in 검증으로 둘지.
