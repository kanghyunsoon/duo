## 1. 현재 Decision workflow (0.2.1, 코드 기준)

모든 쓰기는 core `DecisionService`(`packages/core/src/decisions/service.ts`)가 한다. "AI may propose, Human confirms": agent·system은 propose만, confirm·reject는 human만. confirmed Decision 내용은 다시 쓰지 않고 `supersedes`를 가진 새 Decision으로 바꾼다(ADR-013).

| 단계 | 경로 | 사용자 행동 |
|---|---|---|
| 생성(사람) | 사람용 생성 명령 없음. `.duo-project/decisions/D-###.yaml`을 `state: proposed`로 직접 작성(README 예시와 같음) | ID를 직접 고르고 YAML field(id, title, kind, state, question, answer, forbids, enforcement, governs)를 손으로 씀 |
| proposal(agent) | MCP `duo_propose_decision` → `decisions/proposals/P-###.yaml`. 입력은 title, question, answer, rationale, governs뿐(C140·H-36: "supersedes·forbids는 Human이 확정 시 다룸") | 사람 행동 없음. 다만 agent는 enforce할 규칙(`forbids`, `enforcement`)도, 대체(`supersedes`)도 제안할 수 없음 |
| confirm | `duoctl decision confirm <P-### 또는 D-###>`(TTY 필수, ID 재입력) 또는 `duoctl ui` dialog(ID 재입력) | CLI 화면에는 title, question, answer, governs만 나옴. forbids, enforcement, supersedes 대상, staleness, 할당될 D-ID는 나오지 않음. stale 경고는 확정 **뒤에** "confirmed anyway"로만 나옴. UI dialog는 supersedes·stale·next ID를 미리 보이지만 forbids·enforcement는 보이지 않음 |
| reject | `duoctl decision reject <P-###> [--reason]`(TTY, ID 재입력) 또는 UI | 1 command |
| supersede | 명령 없음. 새 YAML에 `supersedes: D-old`를 쓰고 confirm. DUO가 old의 `state: superseded`, `superseded_by`만 바꿈 | old 내용을 복사해 고친 새 파일을 손으로 작성. agent는 supersede proposal을 만들 수 없음 |
| 확정 후 반영 | `indexRequired: true`: Graph·review·context는 `duoctl index`(또는 `--refresh`) 뒤에 새 Decision을 봄 | 1 command 추가. 안 하면 review가 `INDEX_REQUIRED` |
| stale Decision 인지 | proposal: `based_on` digest로 staleness 계산(`previewConfirm`). confirmed Decision: review가 diff에 든 Decision 파일의 lock 불일치·내용 변경·삭제를 CONFLICT로 냄(`decision-integrity`), supersede 양쪽 불일치는 PARTIAL(`supersede-integrity`) | 같은 question의 active Decision이 둘이 되거나, forbids 대상이 더 이상 존재하지 않는 Decision은 알려 주지 않음 |
| review에서 Decision 확인 | `duoctl review`: `decision-forbids` CONFLICT(D-ID, 증거 pointer: 위반 위치 + D-###.yaml 행). active Decision만 적용 | supersede 관계·이전 Decision은 출력에 없음(C241) |
| current authority 확인 | CLI에 active Decision 목록 없음(`decision list`는 pending만, `status`는 개수만). `duoctl ui`(Direction 페이지), `duoctl trace D-###`(SUPERSEDES edge), 파일 직접 열기 | context switch |
| agent의 참조 | bridge block(`AGENTS.md`/`CLAUDE.md`) + MCP `duo_get_context`(Packet에 active Decision과 "Decision History (superseded, not active)"), `duo_get_decision`(state, active, supersedes, supersededBy), `duo_review_changes` | stale index면 `index-required` → 사람이 `duoctl index` |

T33.2 dry-run(공개 0.2.1, throwaway repo)에서 손으로 쓴 proposed YAML → `duoctl decision confirm D-001`(TTY) → `review --refresh` BLOCK까지 동작을 확인했다. 확정 직후 plain `review`는 `INDEX_REQUIRED`였다.

**가장 큰 friction**: enforce되는 Decision을 만들거나 기존 Decision을 바꾸는 일(W1·W2·W4)이 결국 YAML 손 작성으로 끝난다. H-36은 agent proposal에서 `supersedes`·`forbids`를 빼면서 "Human이 확정할 때 다룬다"고 했지만, 두 confirm surface 어디에도 그 수단이 없고 CLI·UI 모두 확정 화면에 `forbids`·`enforcement`(= BLOCK 여부를 정하는 내용)를 보여 주지 않는다. 그래서 (a) 사람은 확정할 내용을 보려고 파일을 열고, (b) agent 경로로는 enforce 규칙과 대체가 불가능하며, (c) "Human confirmation"이 일부 내용을 보지 않은 채 하는 ceremony가 될 수 있다(exit interview 8번 "safeguard or ceremony"가 바로 이것을 묻는다).

## 3. C239 / C240 / C241

| | C239 missing-intent WARN | C240 `introduced` 라벨 | C241 current·superseded authority |
|---|---|---|---|
| 사용자 문제 | 정상 변경도 WARN. `--fail-on warn`·`--strict` pipeline은 거부. adoption 직후(확정 Requirement·Decision이 거의 없을 때) 거의 모든 변경에서 발생 → noise, 신뢰 하락. T31·T32 control 10/10 | adoption 뒤·이번 diff 전에 들어온 위반을 이번 변경이 "추가했다"고 읽게 함. 위반이 언제 들어왔는지 출력에 없음 | supersede 뒤 review는 D-002 claim만 내고 D-001을 언급하지 않음. 무엇이 현재 authority이고 무엇을 대체했는지는 인용 YAML·trace·파일로만 확인 |
| root cause | `gap/assess.ts`가 packet signal `no-confirmed-intent`를 `action: surface` gap으로 만들고, `review/aggregate.ts`가 surface gap을 모두 WARN basis에 넣음 | `review/claims.ts`가 provenance를 adoption baseline에만 대고 계산: baseline에 없으면 diff가 추가했는지와 무관하게 `introduced` | review rule은 active Decision만 평가(`isActive`), claim에는 Decision ID만 있음. lifecycle 정보는 Truth·trace·Context Packet에 있고(Packet은 이미 history를 렌더) review result에는 없음 |
| 가능한 UX fix | missing-intent를 note로는 남기되 verdict basis에서 빼거나, task·Truth가 없을 때만 빼기 | provenance를 "이번 diff가 추가"와 "adoption 뒤, 이번 diff 전부터 있음"으로 나누거나 additive field(예: `addedByChange`)로 구분. blockEligible은 그대로(면책하지 않음) | review result에 인용·영향받은 Decision의 lifecycle 요약(현재 authority, supersedes chain, supersededBy)을 additive로 넣고 CLI에 한 줄 표시 |
| semantic risk | 높음. ADR-007·H-32의 "gap은 WARN으로 surface" 의도를 바꾸고, verdict·exit code가 바뀜. 진짜 "의도 미기록" 신호를 숨길 수 있음 | 낮음~중간. 라벨만 바꾸면 판정 불변. from-side 존재 판정이 언어별 분석 수준에 묶임(L0 파일에서는 판단 불가 → 기존 `unverified-at-adoption`과 겹침) | 낮음. 표시만, verdict 불변. superseded Decision이 아직 적용된다고 오해시키지 않는 문구 필요 |

| validation과 독립? | 기술적으로 `next`에서 가능. 다만 External Validation이 C239를 noise로 보는지 직접 관찰하므로, 의미 결정은 그 evidence를 본 뒤가 낫다 | 가능(라벨만). 우선순위 낮음 | 가능(표시만). 0.2.1 participant 결과에 영향 없음 |

## 9. 추천 첫 implementation: D. Informed confirm

딱 하나만 추천한다. 이유:

1. 이번 질문의 조건인 human-confirmed authority를 **강화**하면서 유지 비용(파일·UI를 여는 context switch, 잘못 확정 후 supersede 재작업)을 줄인다. 확정 대상인 `forbids`·`enforcement`가 지금은 두 surface 모두에서 보이지 않는다.
2. 가장 큰 비용 절감 후보인 B의 **선행 조건**이다. agent가 enforce 규칙과 supersede를 초안으로 쓰게 하려면, 사람이 확정 화면에서 그 내용을 전부 보아야 한다. D 없이 B를 하면 authority가 약해진다.
3. 이미 있는 core `previewConfirm`(UI가 T18.1부터 사용)을 CLI가 재사용하므로 비용이 작고, 판정·schema·Truth 형식을 바꾸지 않는다.
4. C239~C241 관찰과 겹치지 않아 External Validation 해석을 흐리지 않는다.

범위(승인 시):

- `duoctl decision confirm <id>`: ID 재입력 전에 title, question, answer, rationale, governs, **forbids, enforcement**, **supersedes 대상(title, state)과 "SUPERSEDED가 됨"**, **stale 경고**, 할당될 D-ID 표시. proposal과 `state: proposed` D-### 모두.
- `duoctl decision reject <id>`: 같은 내용 표시(재입력 전).
- UI confirm dialog: forbids·enforcement 표시 추가(HTTP 투영 field 추가).
- 바꾸지 않음: ID 재입력, TTY 요구, DecisionService 쓰기, `decision` JSON result, review·context·MCP.

예상 영향 파일: `apps/cli/src/commands/decision.ts`, `apps/cli/src/messages.ts`, `apps/cli/src/cli.test.ts`, `packages/core/src/decisions/service.ts`(`previewConfirm`이 D-### 수용) 및 test, `packages/integration/src/http/projection.ts`, `packages/ui/src/types.ts`, `packages/ui/src/pages/decisions.tsx`, `docs/07-cli-interface.md`, `docs/08-ui-spec.md`(해당 시).

완료 기준 제안: 위 field가 CLI·UI 확정 전에 보임, supersede proposal 확정 전에 대상과 상태 변화가 보임, stale이 확정 전에 보임, 기존 decision·review·MCP test 불변, 3 OS CI.

다음 후보 순서(각각 별도 승인): B(H-36 재결정 포함) → A(C241) → C239·C240은 External Validation evidence를 본 뒤 의미 결정.

## 11. T34.2 구현 결과(Informed confirm, `next`)

- core `DecisionService.previewConfirm`이 proposal과 YAML Decision(`D-###`) 모두에 대해, confirm이 쓰는 것과 같은 candidate 읽기(파일의 parsed YAML)로 전체 내용 field, 확정 방식, 예상 Decision ID(보장 아님), staleness, supersede 대상, digest를 돌려준다. 없는 field는 없는 대로 둔다.
- `confirm(actor, id, { expectedDigest })`는 repository lock 안에서 candidate를 다시 읽고 digest가 다르면 `DECISION_CONFIRM_PREVIEW_CHANGED`로 아무것도 쓰지 않는다. 자동 재시도나 바뀐 candidate의 자동 확정은 없다. digest에는 Expected ID를 넣지 않으며 실제 ID는 확정 결과가 정한다.
- CLI `decision confirm`·`reject`와 UI confirm dialog가 이 preview를 ID 재입력 전에 보이고, confirm은 digest를 넘긴다. ID 재입력·TTY 요구·Human 전용 권한은 그대로다.
- 바뀌지 않은 것: MCP `duo_propose_decision` 입력(H-36), Project Truth schema, confirmed Decision 변경 규칙, review·index 의미, C239~C241, External Validation 문서, 0.2.1 artifact. 문서: [07 CLI](../07-cli-interface.md#duoctl-decision), [08 UI](../08-ui-spec.md), [03 data model](../03-data-model.md).
