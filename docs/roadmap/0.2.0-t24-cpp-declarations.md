# T24.3 C++ declaration / definition linking (C218)

0.2.0 Milestone C의 세 번째 task다. 결정: H-53. C++ 공개 level은 L1 그대로다. 같은 commit 묶음 앞에서 benchmark 집계 C230을 bench만 고쳤다(§8).

## 1. 결과

C++ header의 선언과 `.cpp`의 out-of-line 정의가 syntax로 같은 callable임이 증명되면, Indexer가 그 쌍을 Graph metadata(`declaration_links`)로 기록한다. Context Compiler는 쌍으로 이어진 Symbol을 논리 대상 하나로 다룬다: 이름이 그 그룹에만 해당하면 ambiguous 대신 그룹을 seed로 쓰고, Packet item 하나에 선언과 구현 범위를 모두 보여 준다. Symbol ID, Graph node·edge와 digest, Evidence, Review seed는 그대로다.

## 2. 이전 C++ 선언·정의 표현

| 항목 | 이전 동작 |
|---|---|
| header 선언 | class 안 `field_declaration`, namespace의 `declaration`. Symbol ID `sym:<header>#<identity>`. static member는 identity `A.static.f` |
| out-of-line 정의 | `function_definition` + `A::f`(`qualified_identifier`). scope는 namespace + 한정 이름. memberScope는 항상 instance, identity `A.f` |
| qualifiedName | 둘 다 `ns.A.f`(namespace·class·이름을 `.`로) |
| overload | 같은 파일의 같은 identity는 Symbol 하나(C217). header에 한 Symbol, cpp에 한 Symbol |
| constructor·destructor·operator | 이름 = class, `~A`, `operator==`(operator_name text) |
| free function·static·익명 namespace | 같은 qualifiedName. static은 exported false, 익명 namespace는 scope에 나타나지 않음 |
| template | template 안 정의도 Symbol(소유 유지), `A<T>::f`는 `A.f` |
| parameter·const·ref·noexcept·trailing return·default argument | Symbol에 기록 없음 |
| include | 옆 파일의 quoted include만 IMPORTS(C++ L1) |
| Graph | 두 Symbol은 관계가 없다(CONTAINS로 각자의 File·class에만) |
| Context | 이름 또는 qualifiedName이 둘과 일치 → `ambiguous`, Packet 없음(정확한 신호가 없을 때). 경로를 쓴 과제는 그 이름의 Symbol을 seed로 쓰지 못함 |
| Evidence·Review·trace·impact·UI·MCP | Symbol별(서로 무관) |

감사 probe `bench/experiments/cpp-decl-def.mjs`(형태 A~S): qualifiedName 과제가 A~E, H, J~L, N~S에서 `ambiguous`였다.

C를 골랐다. 쌍은 Graph 밖의 metadata이고 Context만 읽는다. 쌍을 Graph 관계로 노출할 필요가 생기면(L2, trace) 그때 B를 공개 계약 변경으로 결정한다.

## 4. Pairing

**사실(analyzer).** C++ extractor가 callable 위치마다 `CallableDeclaration { location, role, signature? }`를 SourceAnalysis에 남긴다. role은 본문이 있으면 definition, 없으면 declaration. builder는 이것을 Symbol payload에 넣지 않는다. analysis cache만 다시 만들도록 C++ analyzer identity에 `facts=callables-1`을 더했다(payload의 `analyzerVersion` 1은 그대로라 Graph 행이 바뀌지 않는다).

**key.** qualifiedName(공백 제거: `operator ==`는 `operator==`) + syntax signature. static member도 qualifiedName은 같으므로 identity(`A.static.f`)가 아니라 qualifiedName을 쓴다. kind는 key에 넣지 않는다(`void ns::f(){}`는 syntax상 method로 보이지만 같은 callable).

**조건(모두).**

1. key가 같은 선언이 저장소 전체에 정확히 하나, 정의도 정확히 하나(양방향 유일). 둘 이상이면 아무것도 고르지 않는다.
2. 정의 파일의 quoted `#include`가 선언 파일을 가리킨다: C++ L1 규칙으로 옆 파일에 해석되거나, 쓰인 경로가 저장소에서 정확히 한 파일의 경로 끝과 같다(Unreal `#include "ActionSystem/RogueActionComponent.h"`, Public/Private의 `#include "U.h"`). include search path, build 파일, transitive include는 읽지 않는다. 쓰인 경로가 두 파일 이상의 끝과 같으면 증거가 아니다. 이 증거는 쌍 판정에만 쓰고 Graph IMPORTS edge(L1 include capability)는 바꾸지 않는다. ActionRoguelike의 `StartActionByName`은 signature가 같았지만 module 기준 include라 옆 파일 해석만으로는 쌍이 되지 않았다(§7).
3. 서로 다른 파일(같은 파일이면 C217로 이미 Symbol 하나).

이름만, 이름 + 인자 수, 파일 이름·디렉터리·거리로는 잇지 않는다. 계산은 key Map 한 번이고(선언 × 정의 전수 비교 없음), 매 index마다 모든 analysis에서 다시 만든다.

**signature 정규화.**

| 요소 | 처리 |
|---|---|
| 공백, 줄바꿈 | 단어 사이 공백 하나만 남기고 `* & , ( ) [ ] < > :` 주변은 지움 |
| 주석 | 뺌 |
| parameter 이름 | 뺌(declarator 안쪽 identifier: `int (&a)[3]` → `int(&)[3]`, `void (*cb)(int)` → `void(*)(int)`) |
| default argument | `=`와 값을 뺌(선언에만 쓰는 것이라 같은 callable) |
| `(void)` | `()`와 같음(C++ 규칙) |
| `...` | 그대로(익명 token이라 따로 읽음: 빠지면 `f(int, ...)`와 `f(int)`가 같아짐) |
| cv qualifier `const`·`volatile`, ref qualifier `&`·`&&` | parameter list 뒤의 것을 붙임: `()const`, `()&&` |
| `noexcept`, `override`·`final`, `= 0`, trailing return, return type, `virtual`·`static`·`inline` | 뺌(overload를 가르지 않거나 선언에만 씀) |
| const 위치(`const int`/`int const`), namespace 한정(`std::string`/`string`), 배열과 pointer(`int a[]`/`int* a`), typedef·alias, `class X*`/`X*` | 바꾸지 않음. 의미가 같아도 철자가 다르면 쌍을 만들지 않는다(false negative 허용) |

**쌍을 만들지 않는 선언.** template(`template_declaration` 안, `A<T>::f`), 내부 linkage(namespace 수준 `static`, 익명 namespace), friend, `= default`·`= delete`(본문 없는 정의), 읽지 않는 parameter 형태, parse 오류. macro로 만든 선언은 parser가 보지 못해 Symbol이 없다. header 안 inline 본문은 definition이므로 cpp 정의와 이어지지 않는다(정의 둘).

Truth qualifiedName 참조가 쌍 하나와만 일치할 때의 해석은 T24.5(C231)다: [0.2.0-t24-cpp-truth-references.md](0.2.0-t24-cpp-truth-references.md).

suffix include 증거의 사용 범위(쌍 판정 보조 증거일 뿐, IMPORTS·일반 include resolver·build include path·compiler 의미에 쓰지 않음, 대소문자 비교를 느슨하게 하지 않음)는 H-54에 고정했다([T24.4 §8](0.2.0-t24-python-definitions.md#8-c218-suffix-include-invariant-h-54에-기록)).

## 5. Context 표현

- seed: 이름(`symbol-name`)이나 qualifiedName(`symbol`) 후보가 모두 한 그룹이면 그룹 구성원 모두가 seed다. 그룹 밖 후보가 하나라도 있으면 이전처럼 ambiguous다.
- item: 그룹의 Symbol item은 그룹 전체 위치를 (경로, 위치) 순서로 보여 준다. 머리줄 `Basic.Foo (method) native/Basic.cpp:2-4 + native/Basic.h:3`, L2·L3의 각 부분 앞에 `// 경로:줄`. 위치마다 정확한 범위(본문 또는 선언 줄)와 바로 위 주석만 넣고 파일 전체는 넣지 않는다.
- 중복: 같은 그룹 item은 하나만 남긴다(mandatory, 순서 값, 깊이, ID 순). 선언이 들어 있는 class는 그룹 item이 그 줄을 보이므로 L3를 뺀다(같은 파일 범위만 비교).
- budget: item 단위. 공개 item의 `id`·`source`는 남은 Symbol의 것이다(형식 불변). 그룹이 아닌 Symbol의 text는 T24.1과 같다. `CONTEXT_POLICY_VERSION`은 2 그대로(바뀌는 seed와 text가 digest에 들어감, C225와 같은 이유).

## 6. Evidence·Review·cache

- Evidence: Symbol별 그대로다. 그룹의 두 Symbol은 서로 다른 Evidence ID와 pointer를 가진다. T24.1 invariant(C227)는 Symbol마다 성립한다. 그룹은 Packet 표현일 뿐 Evidence identity가 아니다.
- Review: hunk는 겹친 Symbol 하나를 seed로 잡는다(선언 수정 → header Symbol, 구현 수정 → cpp Symbol). claim이 늘지 않는다. Review context는 그 seed의 그룹 item(선언 + 구현)을 보여 준다.
- invalidation: 쌍은 analysis(파일 hash, analyzer identity)와 include 해석 결과로만 정해지고 둘 다 index state token에 들어간다. 매 index에서 전체를 다시 계산해 token과 같은 transaction에 쓴다. 이웃 header만 바뀌어도 그 header가 다시 분석되고 cpp analysis는 cache에서 오지만 쌍은 새로 계산된다. mtime을 쓰지 않는다.
- 이전 DUO가 만든 Graph에는 `declaration_links`가 없다: Context는 쌍 없음으로 본다. C++ analyzer identity가 바뀌어 C++ 파일이 있는 저장소의 index는 stale이 되고, 다음 index에서 기록된다.
