## 2. Detailed Case Analysis

### 2.1 Case `L4` — Importer Scope Contract Limit (`S15P31A106-264` / Follow-up `#47`)

#### Minimal Reproduction & Evidence Source
- **Evidence Source**: Reproduced in both the source test suite ([`fp-fn-repros.e2e.test.ts`](../../packages/director/src/review/fp-fn-repros.e2e.test.ts), where `next` has the exact `v0.3.3` product code) and the published npm `duoctl 0.3.3` run in `#24` (`bench/value-validation/results/detection-01.json`).
- **Decision `D-001`**:
  - `governs.paths: ["src/ui/**"]`
  - `forbids.imported_paths: ["src/db/legacy-db.ts"]`
  - `enforcement: block`
- **Diff**: Add `src/services/archive.ts` containing `import { legacyQuery } from "../db/legacy-db.js";`.
- **Observed Result**: `verdict: "BLOCK"`, 1 `decision-forbids-import` claim (`provenance: "introduced"`, `blockEligible: true`).
- **0.3.3 Contract vs `#24` Benchmark Oracle**:
  - **0.3.3 Contract Expected**: `BLOCK`. Under H-72 and T40 N3, `forbids` is repository-wide and `governs.paths` does not narrow `forbids`. Thus, DUO 0.3.3 is behaving strictly according to its current specification.
  - **`#24` Benchmark Oracle (R1)**: `compliant` (`PASS`). Rule R1 in `#24` intends to forbid `src/ui/**` from importing `src/db/legacy-db.js` while allowing `src/services/**`. The mismatch is therefore a **contract expressiveness limit**, not an implementation bug against the 0.3.3 spec.

#### Exact Code Trace
1. In [`packages/director/src/review/rules.ts`](../../packages/director/src/review/rules.ts) (`decisionForbidsImport`, lines 443–468), the rule iterates over `usable` and checks every resolved changed reference against `match` without filtering by the importing file's path (`f.path`):
   ```ts
   usable.forEach((f, i) => {
     const r = indexed[i];
     if (r === undefined || r.status === "unavailable") { unavailable.push(f.path); return; }
     if (r.status !== "ok") return; // no analyzer (L0): the changed file's capability limitation is reported already
     for (const ref of r.references) {
       const hunks = f.hunks.filter((h) => overlapsLines(ref.location, hunkRange(h))).map((h) => h.evidenceId);
       if (hunks.length === 0) continue;
       const where = `${f.path}:${ref.location.startLine ?? "?"}`;
       const target = ref.target;
       if (target === undefined) {
         ...
         continue; // external: forbids.dependencies, not imported_paths
       }
       for (const { d, match } of matchers) {
         if (!match.some((m) => m(target))) continue;
         const key = `${d.id}\n${f.path}\n${target}`;
         const g = groups.get(key) ?? { d, source: f.path, target, sites: [] };
         g.sites.push({ ref, hunks });
         groups.set(key, g);
       }
     }
   });
   ```
2. `d.governs.paths` is not consulted in `decisionForbidsImport` (nor in `decisionForbids`, lines 387–436), matching [conflicts.md](../conflicts.md) (H-72) and [0.3.0-t40-rc-blockers.md](0.3.0-t40-rc-blockers.md) (N3: `Forbids scope: repository-wide (governs does not narrow forbids)`).
3. In [`packages/core/src/schema/schemas.ts`](../../packages/core/src/schema/schemas.ts) (`decisionShape`, lines 172–174):
   ```ts
   governs: z.strictObject({ requirements: ids().optional(), paths: texts().optional(), symbols: texts().optional() }).optional(),
   /** imported_paths (H-72): repository path patterns; a changed import resolving to a matching file conflicts. */
   forbids: z.strictObject({ dependencies: texts().optional(), symbols: texts().optional(), paths: texts().optional(), imported_paths: texts().optional() }).optional(),
   ```
   Because `forbids` has no importer-path filter field, a Decision cannot restrict `imported_paths` to a specific importing layer (`src/ui/**`).

#### Classification & Follow-up Candidate (`#47`, Needs Maintainer Decision)
- **Status (#47, Maintainer Decision on the issue):** fixed by the optional `forbids.importer_paths` field. It narrows only `imported_paths` to importing files that match it, the Adoption Baseline applies the same filter, `governs.paths` keeps its meaning, and a Decision without the field keeps its Lock digest and repository-wide behavior. An empty list or `importer_paths` without `imported_paths` is invalid input.
- **Classification**: **Documented contract limit in 0.3.3; 0.4 candidate requiring a Maintainer Decision (`#47`).**
- **Why `governs.paths` must not silently narrow `forbids`**:
  - Existing Decisions commonly list the protected target module in `governs.paths` (e.g., `governs.paths: ["src/db/legacy-db.ts"]` + `forbids.imported_paths: ["src/db/legacy-db.ts"]`). Silently narrowing `forbids` to importers matching `governs.paths` would stop checking `src/ui/**`.
- **Candidate Proposal (`#47` — Needs Maintainer Decision)**:
  - Consider adding an optional importer scope field on `forbids` (such as `importer_paths` / `from_paths`) in `DecisionSchema`. Because this modifies the `.duo-project/decisions/*.yaml` schema, `decisionLockDigest`, and review verdict semantics, it requires a formal Maintainer Decision before implementation.

### 2.2 Case `D3` — Second Forbidden Import in a Baseline-Exempt File (`S15P31A106-265` / Follow-up `#48`)

#### Minimal Reproduction & Evidence Source
- **Evidence Source**: Reproduced in both the source test suite ([`fp-fn-repros.e2e.test.ts`](../../packages/director/src/review/fp-fn-repros.e2e.test.ts)) and the published npm `duoctl 0.3.3` run in `#24` (`detection-01.json`).
- **Baseline State (`HEAD`)**: `src/ui/legacy-orders-page.ts` already contains `import { legacyQuery } from "../db/legacy-db.js";` on line 1, and an Adoption Baseline has been captured.
- **Diff (`WORKTREE`)**: Keep line 1 and add a **second** import statement on line 2:
  ```ts
  import { legacyQuery } from "../db/legacy-db.js";
  import { legacyQuery as legacyCount } from "../db/legacy-db.js";
  ```
- **Observed Result**: `verdict: "WARN"`, 1 claim with `provenance: "pre-existing-touched"` and `blockEligible: false`.
- **0.3.3 Contract vs `#24` Benchmark Oracle**:
  - Under the H-72 adoption baseline policy, provenance is tracked per `File -> File` `IMPORTS` relation (`import:file:<source>->file:<target>`), so any changed import statement between that file pair is classified as `pre-existing-touched` (`WARN`).
  - In `#24` (`D3`), adding a second import statement on a new line is oracle `violation` (`BLOCK`).

#### Exact Code Trace
1. **Baseline Key Granularity**: In [`packages/director/src/adoption/head.ts`](../../packages/director/src/adoption/head.ts) (`headBaselineFindings`, lines 112–120), baseline findings for `decision-forbids-import` are recorded per `File -> File` `IMPORTS` edge in the Graph:
   ```ts
   for (const f of headFiles.filter((p) => !input.divergent.has(p))) {
     for (const e of input.graph.adjacentEdges([fileRef(f)], { direction: "outgoing", types: ["IMPORTS"], limit: 10_000 }).edges) {
       const to = parseNodeId(e.to);
       if (to?.type !== "file" || !inHead.has(to.path)) continue;
       for (const { d, match } of importing) {
         if (match.some((m) => m(to.path))) add("decision-forbids-import", d.id, `import:${nodeId(fileRef(f))}->${nodeId(fileRef(to.path))}`, { path: f, enforced: d.enforcement === "block" });
       }
     }
   }
   ```
2. **Review Rule Grouping**: In [`packages/director/src/review/rules.ts`](../../packages/director/src/review/rules.ts) (`decisionForbidsImport`, lines 462–488), all changed module references in `f.path` resolving to `target` under `d.id` are grouped under `const key = `${d.id}\n${f.path}\n${target}`` and passed to `makeClaim` with:
   ```ts
   violation: { key: violationKey("decision-forbids-import", g.d.id, `import:${nodeId(fileRef(g.source))}->${nodeId(fileRef(g.target))}`), touched: true, ...(unverifiable ? { unverifiable: true } : {}) },
   ```
3. **Provenance Classification**: In [`packages/director/src/review/claims.ts`](../../packages/director/src/review/claims.ts) (`makeClaim`, lines 84–92):
   ```ts
   const provenance = v === undefined || ctx.baselineKeys === undefined || input.alignment === "ALIGNED" ? undefined
     : !ctx.baselineKeys.has(v.key) ? (unverifiable ? "unverified-at-adoption" as const : "introduced" as const)
       : v.touched ? "pre-existing-touched" as const : "pre-existing" as const;
   const preExisting = provenance === "pre-existing" || provenance === "pre-existing-touched";
   ```
   and on line 92:
   ```ts
   blockEligible: input.alignment === "CONFLICT" && enforced && blockEligible(basis) && !preExisting && provenance !== "unverified-at-adoption",
   ```
   Because `ctx.baselineKeys.has(v.key)` is `true` and `v.touched` is `true`, `provenance` is `"pre-existing-touched"`, `preExisting` is `true`, `blockEligible` becomes `false`, and the review verdict is `WARN`.

#### Classification & Follow-up Candidate (`#48`, Needs Maintainer Decision)
- **Classification**: **0.4 candidate requiring a Maintainer Decision (`#48`)** because changing `WARN` (`pre-existing-touched`) to `BLOCK` (`introduced`) alters review verdicts and revises the H-72 file-pair adoption baseline provenance policy.
- **Candidate Proposal (`#48` — Needs Maintainer Decision)**:
  - Decide whether adoption baseline provenance for `decision-forbids-import` remains strictly file-pair-based (H-72) or becomes statement/count-aware (for example, comparing changed new-side import statements against `ctx.from` (`HEAD`) import statements for the same `(source, target)` pair, or recording statement counts in baseline findings).

### 2.3 Case `L1` — 1-Hop Barrel Re-export (`S15P31A106-266` / Follow-up `#49`)

#### Minimal Reproduction & Evidence Source
- **Evidence Source**: Reproduced in both the source test suite ([`fp-fn-repros.e2e.test.ts`](../../packages/director/src/review/fp-fn-repros.e2e.test.ts)) and the published npm `duoctl 0.3.3` run in `#24` (`detection-01.json`).
- **Barrel File**: `src/db/index.ts` contains `export { legacyQuery } from "./legacy-db.js";`.
- **Diff**: Add `src/ui/report-page.ts` containing `import { legacyQuery } from "../db/index.js";`.
- **Observed Result**: `verdict: "PASS"`, 0 claims, 0 limitations.
- **`#24` Benchmark Classification**: In `#24` (`bench/value-validation/cases.mjs`), `L1` has `scope.duo: "out"` and is excluded from in-scope scoring because 0.3.3 `forbids.imported_paths` is documented as checking direct 1-hop module resolution only.

#### Exact Code Trace
1. **1-Hop Module Resolution**: In [`packages/graph/src/incremental/references.ts`](../../packages/graph/src/incremental/references.ts) (`readIndexedModuleReferences`, lines 63–67), each `entry.analysis.moduleReferences[j]` is paired with its direct 1-hop `modules[j]`:
   ```ts
   references: refs.map((r, j) => {
     const resolution = modules[j] as ModuleResolution;
     const target = resolution.status === "resolved" && resolution.path !== path && files.has(resolution.path) ? resolution.path : undefined;
     return { kind: r.kind, specifier: r.specifier, typeOnly: r.typeOnly, location: r.location, resolution, ...(target === undefined ? {} : { target }) };
   }),
   ```
   For `import { legacyQuery } from "../db/index.js"`, `target` is `"src/db/index.ts"`.
2. **Direct Target Glob Match Only**: In [`packages/director/src/review/rules.ts`](../../packages/director/src/review/rules.ts) (`decisionForbidsImport`, line 461):
   ```ts
   if (!match.some((m) => m(target))) continue;
   ```
   Because `"src/db/index.ts"` does not match `["src/db/legacy-db.ts"]`, the reference does not match.
3. **Existing Re-export Machinery in `@duo-director/graph`**:
   - [`packages/graph/src/build/exports.ts`](../../packages/graph/src/build/exports.ts) (`ExportIndex.find`, lines 58–114) already follows TS/JS re-export chains up to `MAX_REEXPORT_DEPTH = 4` (`export { x } from "./mod"` and `export * from "./mod"`).
   - However, `ExportIndex` is currently used only in [`packages/graph/src/build/collect.ts`](../../packages/graph/src/build/collect.ts) to resolve `CALLS` edges to their defining symbol; resolved re-export target files are not stored on `FileResolution.modules` or checked by `decisionForbidsImport`.

#### Classification & Follow-up Candidate (`#49`, Needs Maintainer Decision)
- **Status (#49 Stage 1, Maintainer Decision L1-C):** the review computes the re-export chain at review time from the indexed analysis (no index format change). When a changed reference resolves to a file that is not forbidden but re-exports, through `export ... from` chains of at most 4 hops, a name the import takes from a forbidden file, it reports `imports-through-reexport` with the chain. Unrelated names from the same barrel are not reported. Verdicts are unchanged. Stage 2 (binding-level `forbidden-import`, PASS → BLOCK) needs a Human Decision row and stays a todo.
- **Classification**: **Out of current analyzer scope (`scope.duo: "out"` in `#24`, documented limit in 0.3.3); 0.4 improvement candidate for TS/JS (`#49`, needs Maintainer Decision).** *(re-export chains are followed only for TS/JS; Python resolves relative and same-repository absolute imports but not re-exports through `__init__.py`.)*
- **Candidate Proposal (`#49` — Needs Maintainer Decision)**:
  - Because changing `PASS` to `BLOCK` (or adding a new limitation code) on barrel re-exports changes the H-72 `forbids.imported_paths` review contract, a Maintainer Decision is required to choose between:
    - **Candidate L1-A**: Persist resolved binding target files from `ExportIndex` on TS/JS module resolutions (bounded by `MAX_REEXPORT_DEPTH = 4`) and match them in `decisionForbidsImport`.
    - **Candidate L1-B**: Keep `decisionForbidsImport` 1-hop only, or surface an explicit limitation when an imported file re-exports from a forbidden path.

### 2.4 Case `L2` — Computed Dynamic Import & Template-Literal Dynamic Import (`S15P31A106-267` / Follow-up `#50`)

#### Minimal Reproduction & Evidence Source
- **Case `L2a` (Computed dynamic import)**:
  - **Evidence Source**: Reproduced in both the source test suite ([`fp-fn-repros.e2e.test.ts`](../../packages/director/src/review/fp-fn-repros.e2e.test.ts)) and the published npm `duoctl 0.3.3` run in `#24` (`detection-01.json`).
  - **Diff**: Add `src/ui/lazy-page.ts` with `return import(\`../db/${name}.js\`);`.
  - **Observed Result**: `verdict: "PASS"`, 0 claims, **0 limitations** (`importLimits(res)` is `[]`).
  - **`#24` Benchmark Classification**: Marked `scope.duo: "out"` in `#24` (`cases.mjs`) because resolving arbitrary runtime expressions is outside static analyzer scope; however, no `imports-unresolved` limitation is surfaced.
- **Case `L2b` (Static no-substitution template literal dynamic import)**:
  - **Evidence Source**: **Source test (`next` = `v0.3.3` product code) only** — newly identified during `#30` code trace; not part of the `#24` published npm run.
  - **Diff**: Add `src/ui/lazy-static-template.ts` with ``return import(`../db/legacy-db.js`);``.
  - **Observed Result**: `verdict: "PASS"`, 0 claims, **0 limitations**.

#### Exact Code Trace
1. In [`packages/analyzer/src/language/tree-sitter/ts-js-extract.ts`](../../packages/analyzer/src/language/tree-sitter/ts-js-extract.ts) (`literalText`, lines 98–103):
   ```ts
   function literalText(node: Node | undefined): string | undefined {
     if (node === undefined) return undefined;
     if (node.type === "string") return stringValue(node);
     if (node.type === "template_string" && !node.namedChildren.some((c) => c.type === "template_substitution")) return node.text.slice(1, -1);
     return undefined;
   }
   ```
2. However, in `Extractor.call` (`packages/analyzer/src/language/tree-sitter/ts-js-extract.ts`, lines 656–668):
   ```ts
   const only = args?.type === "arguments" && args.namedChildren.length === 1 ? args.namedChildren[0] : undefined;
   if (fn.type === "import") {
     if (only?.type === "string") this.module(node, only, "dynamic-import", false, []);
     return;
   }
   if (fn.type === "identifier" && fn.text === "require" && only?.type === "string") {
     this.module(node, only, "require", false, this.requireBindings(node));
     return;
   }
   ```
3. Because `Extractor.call` checks `only?.type === "string"` and immediately executes `return;`:
   - **In `L2b` (static template literal ``import(`../db/legacy-db.js`)``)**: `only.type` is `"template_string"`. Even though `literalText(only)` (used inside `this.module(...)`) already extracts no-substitution `template_string` nodes via `node.text.slice(1, -1)`, the `only?.type === "string"` guard prevents `this.module(...)` from being called.
   - **In `L2a` (computed dynamic import ``import(`../db/${name}.js`)``)**: `if (fn.type === "import")` returns without recording an entry in `this.moduleReferences`. As a result, `readIndexedModuleReferences` has no reference for line 2, and `decisionForbidsImport` (`packages/director/src/review/rules.ts`, lines 452–459) never reaches `if (s === "unresolved") unresolved.push(where);`.

#### Classification & Follow-up Candidate (`#50`, Needs Maintainer Decision)
- **Status (#50 L2a, Maintainer Decision T158):** `L2a` is fixed: a non-literal `import()` argument (a variable, an expression, a template literal with substitutions) is recorded without its text as a module reference with `syntax.computed`, the resolver returns `unresolved` / `computed-specifier`, and review reports `imports-unresolved` on the changed line. Verdicts are unchanged.
- **Status (#50 L2b, H-90):** `L2b` is fixed: `import()` and `require()` whose only argument is a template literal without substitutions are the same module reference as the string literal (TS/JS analyzer facts `template-imports-1`, so cached analyses are made again and an existing index is stale until the next `duoctl index`). An added forbidden import is `introduced` / BLOCK; one in a pair already in the Adoption Baseline is `pre-existing-touched` / WARN. `require(expr)` with a computed argument stays out of scope.
- **Classification**:
  - **`L2a` (Resolving arbitrary computed expressions)**: **Out of current analyzer scope (`scope.duo: "out"` in `#24`)**.
  - **`L2a` (Surfacing a limitation for computed dynamic imports) & `L2b` (Extracting no-substitution template literals)**: **0.4 candidate (`#50`; `L2b` changes `PASS` -> `BLOCK` and therefore needs a Maintainer Decision)**.
- **Candidate Proposal (`#50` — Needs Maintainer Decision)**:
  1. In `Extractor.call` (`ts-js-extract.ts`), gate `this.module(...)` on `only !== undefined && literalText(only) !== undefined` so no-substitution template literals (`L2b`) are extracted and resolved like string literals.
  2. For `import(expr)` with a non-literal argument (`L2a`), record an unresolved module reference (or emit a dedicated limitation) so `decisionForbidsImport` reports `imports-unresolved` on changed lines without guessing runtime targets.
