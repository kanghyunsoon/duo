# DUO 0.2.0 Audit (T22)

상태: T22 조사 결과의 공식 기록과 0.2.0 계획(H-48~H-50으로 확정, T23 구현). 기준점은 0.1.2(`@duo-director/cli@0.1.2`, tag `v0.1.2` = `93010a4`)다. T22 측정은 0.1.1 코드(`834bc6f`)에서 했다. 0.1.2 변경은 LLM provider 요청 경로뿐이라 아래 analysis, freshness, Context, Review 수치에 영향이 없다. 이 문서는 production code와 공개 계약을 바꾸지 않는다. 공개 지원 수준은 그대로다: 모든 Git repository L0, TypeScript/JavaScript L2, Java·C#·C++·Python L1, 그 밖의 언어 파일은 file-level L0.

측정 도구는 `bench/experiments/`에 있다([부록](#부록-t22-측정-도구)). 측정 결과 원본(`bench/results/local/`)은 Git에 넣지 않는다.

## 1. Executive Summary

DUO는 형태가 다른 공개 저장소 5개에서 모두 동작했다. init은 exit 0으로 baseline까지 만들었고, index는 current였으며, 파일 하나를 고친 뒤의 incremental index는 그 파일 하나만 다시 분석했다. 가장 큰 Unity 저장소(scan 8,078 파일)에서 no-op freshness는 4.1 s, Context는 6.5 s, Review는 7.0 s, peak RSS는 485 MB였다.

가장 큰 위험은 속도보다 정확성이다. Java·C#·C++ L1 analyzer는 같은 이름의 overload를 Symbol 하나로 합치고, Context와 Review는 첫 overload의 범위만 쓴다. 이때 diagnostic이 없어서 사용자는 Packet에서 코드가 빠졌다는 사실을 알 수 없다(T23에서 원인 확인, §15).

| 분류 | 항목 | 다음 |
|---|---|---|
| resolved | optional semantic assist의 provider 요청 redaction(§2) | 0.1.2에서 해결 |
| correctness issue | Java·C#·C++ overload symbol loss, C++ 선언·정의 false ambiguity, Python source root(§5) | Milestone C |
| performance issue | freshness가 Context 시간의 95%, Review 시간의 70%(synthetic large). 실제 Unity·Unreal에서는 fingerprint, scan, git이 주비용(§4) | Milestone A, B |
| current limitation | Java·C# 파일 간 Edge 없음, 같은 Java package 참조 누락, polyglot 생성 TS bias(§6), Unity·Unreal asset의 L0 비중(§11), onboarding gap(§9), Node 22 미지원(§8), provider는 공식 OpenAI endpoint 전용(§10) | 0.2.0 또는 이후 |
| future capability | Python L2, Java·C#·C++ L2, Node 22, asset-aware analysis, OpenAI-compatible provider, Trusted Publishing, cross-language resolution | §13 |

## 2. Security

**Resolved in 0.1.2** (C216, H-47).

- 경로: optional semantic assist(Review `--semantic`, MCP `includeSemanticAssist`)이고, provider와 API key를 설정한 경우에만 해당한다.
- 문제: provider 요청에 들어가는 evidence 발췌 일부가 Context Packet과 같은 secret redaction을 거치지 않았다.
- 기본 경로: provider none(기본값)에서는 provider 호출과 network 요청이 없으므로 영향이 없다.
- 해결: provider를 부르는 공통 경계(`invokeLLM`)가 모든 요청의 instructions와 input을 Context와 같은 redaction으로 치환한 뒤 provider, response cache key, token 추정에 넘긴다. semantic assist 발췌는 자르기 전에 치환한다.
- 이후 provider: 새 provider도 모두 이 경계를 지나야 한다(§10).
- 로컬 cache(H-50): 0.1.1 이하에서 semantic assist를 실제 provider와 함께 썼고 provider가 저장소 secret을 응답에 echo했다면 로컬 LLM response cache에 그 값이 남아 있을 수 있다. 예방 차원에서 `.duo-project/cache/llm/`을 지워도 된다. 로컬이고 Git ignored이며 다시 만들어진다. 이 안내는 [SECURITY.md](../../SECURITY.md)에 있고, DUO가 cache를 자동으로 지우지는 않는다.

T22에서 다시 확인한 항목: UI는 loopback에서만 열리고 Host·Origin·session·CSRF를 검사하며 CSP는 `default-src 'none'`이다. 코드의 외부 URL은 공식 OpenAI endpoint 하나다. telemetry는 없다. `.duo-project/.gitignore`는 generated, cache, runtime을 덮는다. package 안의 절대 경로는 0개다.

재현 절차는 기록하지 않는다.

## 3. Real-world Performance

**환경.** Windows 11, Intel Core Ultra 7 155H(22 logical core), 32 GB, Node 24.18.0, DUO 0.1.1 코드(`834bc6f`).

**방법.** `bench/experiments/realworld-suite.mjs`가 공개 저장소를 depth 1로 OS temp에 clone한다. 그다음 저장소마다 새 process로 `realworld.mjs`를 실행한다.

- CLI init: cold process의 `duoctl init --non-interactive --baseline-policy head`(Truth, 첫 index, adoption baseline)
- initial index: 같은 process에서 generated와 cache를 지운 뒤 `indexRepository`
- no-op freshness: `inspectIndex` 3회 median. registry를 공유하는 장기 실행(MCP·UI) 조건이고 fs·git 호출 수 계측이 켜져 있다

- context: 경로를 쓰지 않은 과제로 2회 median
- review: HEAD → WORKTREE 1회
- peak RSS: 측정 process 전체

**TASK-019와의 관계.** 위 수치는 [performance-benchmark](../performance-benchmark.md)의 TASK-019 synthetic 수치와 별개의 데이터다. ## 4. Freshness Findings

### 4.1 T21 초기 가설

T21은 synthetic large fixture(5,005 index 파일, 구조 분석 4,169)에서 `inspectIndex`를 7회 측정했다. median은 4,048 ms였다([0.1.1 hardening D](0.1.1-hardening.md#d-freshness-profile)).

| 단계 | median |
|---|---:|
| truth | 27 ms |
| scan | 452 ms |
| fingerprint | 1,002 ms |
| state | 99 ms |
| registry | 10 ms |
| analysis(cache 확인) | 2,138 ms |
| resolution-and-git | 410 ms |

T21은 여기서 두 결론을 냈다. 첫째, 비용의 절반 이상이 analysis cache 확인이다. 이 단계는 cache 4,169개에 `readFileSync` 5.7 MB와 `lstat` 16,676회를 쓴다. 둘째, `rev-parse`가 3번 중복 실행된다. 또 synthetic large에서 Context 시간의 95%, Review 시간의 70%가 freshness였다.

### 4.2 T22 수정 결론

실제 Unreal·Unity 저장소에서 `freshness-profile.mjs --plain`을 3회 실행한 median은 다음과 같다. 계측을 끈 측정이라 §3의 no-op 값보다 작다.

| 단계 | ActionRoguelike | ECS samples |
|---|---:|---:|
| truth | 18 ms | 19 ms |
| scan | 334 ms (22%) | 789 ms (30%) |
| fingerprint | 715 ms (47%) | 970 ms (37%) |
| state | 18 ms | 89 ms |
| registry | 2 ms | 10 ms |
| analysis(cache 확인) | 72 ms (5%) | 401 ms (15%) |
| resolution-and-git | 353 ms (23%) | 415 ms (16%) |
| 합계 | 1,531 ms | 2,651 ms |

- synthetic large에서는 analysis cache 확인의 비중이 크다. 실제 Unity·Unreal에서는 구조 분석 파일이 적고(168, 851) L0 파일이 많아서 fingerprint, scan, git의 비중이 더 크다.
- 실제 중복 Git 질의는 `rev-parse --show-prefix` 하나다. scan과 resolution에서 한 번씩 실행된다. freshness 한 번의 Git 명령은 다음 8개다: `rev-parse --show-prefix`, `ls-files -z --stage`, `ls-files -z --others --exclude-standard`, `diff-files -z --name-only --diff-filter=T`, `rev-parse --show-prefix`, `status --porcelain=v2 …`, `rev-parse --show-object-format --is-shallow-repository`, `rev-list --max-parents=0 HEAD`. T21의 "rev-parse 3회 중복"은 틀렸다. 세 번째 `rev-parse`는 다른 질의다.
- grammar loading(87~115 ms)은 주요 병목이 아니다.

### 4.3 안전 후보(구현하지 않음)

1. **analysis cache의 async·parallel 확인.** T21에서 cache 4,169개를 읽고 parse하는 시간(7회 median)은 동기 순차 1,085 ms, 비동기 16개 472 ms, 비동기 64개 338 ms였다. T22 prototype(`cache-prefetch-equivalence.mjs`, medium fixture, 동시성 64)은 production 코드를 바꾸지 않고 같은 byte를 미리 읽어 넘겼다. symlink 검사, JSON parse, key 검증은 production 그대로다. 아래 9개 시나리오에서 inspect 결과, incremental graph, clean full rebuild graph가 모두 byte 단위로 같았다. inspect 시간은 2.9~3.7 s에서 2.0~2.4 s로 줄었다.

   | 시나리오 | status | 다시 분석할 파일 |
   |---|---|---:|
   | 변경 없음 | current | 0 |
   | TypeScript 파일 수정 | stale | 1 |
   | source 파일 삭제 | stale | 0 |
   | source 파일 이름 변경 | stale | 1 |
   | 같은 byte로 다시 쓰고 mtime만 변경 | current | 0 |
   | cache entry를 잘라 손상 | stale | 1 |
   | cache entry 삭제 | stale | 1 |
   | cache entry를 다른 파일의 entry와 바꿈 | stale | 1 |
   | 새 Java 파일 | stale | 1 |

   real-world 효과에는 상한이 있다. 이 단계는 ActionRoguelike에서 72 ms, ECS에서 401 ms이므로 줄일 수 있는 시간도 그보다 작다.
2. **`show-prefix` 중복 제거.** 한 freshness 호출 안에서 같은 시점의 결과를 공유한다. git process 8개 중 1개가 줄고 판정은 바뀌지 않는다.

측정했지만 권하지 않는 것: fingerprint 동시성 16 → 64(약 70 ms), cache 경로 symlink 검사 축소(보안 검사 범위 변경, C202), TTL·mtime-only·watcher·stale Graph 허용·cache 존재 여부만 확인.

구현 조건: TTL로만 freshness를 판정하지 않는다. mtime만으로 정확성을 판단하지 않고, timestamp만으로 content equality를 판단하지 않는다. stale Graph를 허용하지 않는다. clean-full equivalence를 항상 유지한다. inspect와 index는 같은 판정 함수를 쓴다.

## 5. L1 Correctness Issues

아래 세 항목은 기능 요청이 아니다. 현재 Graph가 source를 틀리게 표현하는 정확성 문제다. 근거: `analyzer-probe.mjs`, `overload-probe.mjs`, §3 저장소.

### 5.1 Overload symbol loss: Java, C#, C++ (C217)

- **Observed.** Java `ServiceImpl.run()`과 `run(int)`은 Symbol `ServiceImpl.run` 하나가 되고 source는 첫 선언의 범위다. C# `Player.Move()`과 `Move(int)`도 `Game.Player.Move` 하나가 된다. C++ `AWeapon::Fire()`과 `Fire(int)`은 `.h`와 `.cpp`에 하나씩 남는다. `checkGraph`는 diagnostic을 내지 않는다. 과제 "ServiceImpl run times"의 Context에는 `run(int)` 본문이 없다. TypeScript는 overload signature와 implementation이 implementation Symbol 하나로 합쳐지며, 이것은 의도한 동작이다. **T23 정정:** 나머지 overload의 위치는 사라지지 않고 Graph payload의 `additionalLocations`에 남는다. 다만 그 값을 읽는 곳이 없다(§15). **T24.1:** Context, Evidence, Review diff seed가 이 위치를 모두 읽도록 고쳤다. Symbol identity는 그대로다([T24.1](0.2.0-t24-overloads.md), C217 Resolved, member identity는 C224).
- **Impact.** 과제가 가리키는 코드가 Context에서 빠진다. Review diff seed는 hunk와 Symbol `source`의 겹침으로 정하므로, 두 번째 overload를 고친 hunk는 바깥 class Symbol로 귀속된다. diagnostic이 없으므로 사용자는 합쳐졌다는 사실을 알 수 없다.
- **Expected invariant.** analyzer가 인식한 선언은 정확히 하나의 Symbol이 되거나 명시적인 diagnostic을 남긴다. 조용히 사라지지 않는다. overload는 그 언어가 정의하는 callable signature로 구분한다. 이름 뒤 random suffix나 선언 순서 번호로 구분하지 않는다. overload가 없는 Symbol의 ID는 바뀌지 않아야 한다. Symbol ID는 CLI·MCP 결과와 사람이 보존한 Review Record의 evidence pointer에 나타나기 때문이다.
- **설계 질문.** symbol identity가 language, qualified name, callable signature, source location, declaration·definition relation을 표현해야 하는지 검토한다. 언어마다 규칙이 다르므로 하나의 문자열 heuristic으로 합치지 않는다. L1의 signature는 쓰인 그대로의 문법 정보다. type resolution이 없으므로 `List<String>`과 `java.util.List<String>`은 다른 signature가 된다. 이 한계를 문서화한다.
- **Prerequisite for L2.** CALLS는 특정 overload를 가리켜야 한다. 존재하지 않는 Symbol로는 호출을 해석할 수 없다.

### 5.2 C++ header declaration과 cpp definition의 false ambiguity (C218)

> **T24.3에서 해결(H-53).** 설계와 결과: [0.2.0-t24-cpp-declarations.md](0.2.0-t24-cpp-declarations.md).

- **Observed.** `Weapon.h`의 `game.AWeapon.Fire`와 `Weapon.cpp`의 `game.AWeapon.Fire`는 관계없는 두 Symbol이다. ActionRoguelike에서 과제 "RogueActionComponent StartActionByName RogueAction"을 주면 `StartActionByName`이 header 선언과 cpp 정의 둘 다에 걸려 ambiguous가 되고 Packet이 없다. 경로를 쓴 과제로는 Packet이 만들어지고 기대 파일 3개 중 2개가 들어간다(§6).
- **Impact.** Unreal·C++에서 가장 흔한 과제 형태인 "class + method 이름"에서 Packet이 나오지 않는다. 선언과 정의가 서로 무관한 것으로 보인다.
- **Expected invariant.** namespace, class, 이름, signature가 모두 일치할 때만 선언과 정의를 연결한다. 이름만 같다고 자동으로 합치지 않는다. 다른 translation unit의 자유 함수, `static` 함수, overload, 다른 namespace가 그런 경우다. ambiguity는 실제로 다른 entity일 때만 보고한다.
- **Prerequisite for L2.** include 해석과 call target은 선언과 정의를 하나의 entity로 봐야 한다. 연결에 signature가 필요하므로 5.1이 먼저다.

### 5.3 Python source root limitation (C219)

> **T24.2에서 해결(H-52).** 발견 규칙과 결과: [0.2.0-t24-python-roots.md](0.2.0-t24-python-roots.md).

- **Observed.** absolute import는 repository root와 `src/` 아래에서만 해석된다. FastAPI template의 `backend/app` 아래에서 `from app.models import …`는 IMPORTS Edge 0개다. package가 root에 있는 probe에서는 상대 import, absolute import, 같은 module 안의 CALLS가 모두 생성되었다.
- **Impact.** `backend/`, `services/<name>/`, monorepo 같은 흔한 구조에서 import graph가 없다. FastAPI 일반 과제의 Context 1/3(§6)과 관련 있을 가능성이 있다.
- **Expected invariant.** absolute import는 module이 발견된 source root 아래에 있고 경로가 유일할 때만 파일로 해석한다. 그 밖에는 external 또는 unresolved로 두고 limitation을 보고하며 추측하지 않는다. `backend/app`을 hard-code하지 않는다.
- **발견 규칙 검토 대상.** `pyproject.toml`(setuptools `package-dir`·`packages.find`, Poetry `packages` 등), `setup.cfg`, src-layout, `__init__.py`가 있는 최상위 package의 부모 디렉터리, 사람이 설정하는 Truth의 root 목록. 발견한 root는 status에 보고한다.
- **Prerequisite for L2.** L2의 정의가 "모든 import를 module resolver가 결정"하는 것이므로 source root가 그 기반이다.

### 5.4 정확성 문제가 아닌 current limitation

이미 문서화된 한계다: Java·C#에는 파일 간 IMPORTS·CALLS Edge가 없고(probe에서 0개), C# partial class는 Symbol 둘로 남으며, C++ include path(Unreal Public/Private module)는 해석하지 않는다([language-support](../language-support.md)).

## 6. Context Quality

기준은 적절한 evidence가 Packet에서 빠지지 않았는가이다. token 절감률은 저장소와 과제에 따라 크게 달라 일반화하지 않는다. 경로 없는 과제는 `realworld.mjs`, 경로를 쓴 과제는 `context-quality.mjs`로 쟀다.

## 8. Node 22 Investigation

Node 22.23.3 공식 zip(SHA-256 확인)으로 실험했다.

- 공개된 package의 clean install은 성공했다.
- launcher의 engines 검사(`>=24.15.0`)가 의도대로 exit 1로 막는다.
- CLI bundle(`cli-*.js`)을 직접 실행하면 주요 기능이 Node 24와 같게 동작했다: version, init, index, status, context, review, MCP(tool 9개, stdout clean), UI.
- 설치본 conformance는 66/66이다. 배포 E2E의 실패 12개는 모두 engines 검사 때문이다. workspace 테스트는 842 pass, 7 skip으로 Node 24와 같다.
- `node:sqlite` ExperimentalWarning이 모든 명령의 stderr에 나온다. 원인은 graph package store의 정적 import다.

**결론.** Node 22 지원 가능성은 있다. 하지만 engines `>=24.15.0`은 유지한다. ADR-001을 다시 결정하기 전에는 지원을 선언하지 않는다. 그 결정에는 경고 처리 방식, CI의 Node 22 matrix, engines 변경을 함께 포함한다.

## 10. Provider Architecture

**현재.** `OpenAIResponsesProvider`를 유지한다. 공식 OpenAI endpoint 전용이고 config `base_url`과 `OPENAI_BASE_URL` override를 막는다(H-39, ADR-012, C212). 바꾸지 않는다.

**향후.** `OpenAICompatibleProvider`(가칭)를 별도로 구현한다. endpoint와 credential 환경 변수 이름은 명시적으로 설정하고, response cache identity에 endpoint family를 넣는다. GMS는 전용 class가 아니라 이 provider의 configuration 후보로 본다.

**GMS.** GMS는 OpenAI API 경로를 자기 host 아래에 두는 base URL과 Bearer key를 쓴다. T22에서 찾은 공개 사용 예시는 모두 `/chat/completions`만 썼다. GMS의 Responses API 지원은 확인하지 못했다(실제 호출은 하지 않음). 그래서 Chat Completions가 필요할 가능성이 높다.

**결정(Q-PROVIDER, H-49).** 공식 `OpenAIResponsesProvider`는 그대로다: 공식 endpoint만, Responses API만, custom base URL 금지, 기존 보안·timeout·retry 정책 유지. H-39의 "Chat Completions adapter 금지"는 이 provider에 계속 적용한다. 별도로 구현할 `OpenAICompatibleProvider`에 한해 Chat Completions transport를 허용한다. 조건은 다음과 같다.

- 공식 provider와 별도 provider다.
- transport와 API mode는 사용자가 명시적으로 선택한다.
- Responses → Chat Completions 자동 fallback은 없다.
- endpoint capability를 추측해 자동으로 바꾸지 않는다.
- 0.1.2의 공통 provider redaction 경계를 지난다.
- timeout·retry ownership은 DUO가 가진다.
- provider가 structured output을 지원하지 않아도 DUO 최종 schema validation을 우회하지 않는다.
- provider별 response mapping과 error mapping은 따로 둔다.
- 공식 provider 계약은 바꾸지 않는다.

GMS는 전용 class가 아니라 이 provider의 configuration·use-case 후보다. 방향만 정했고 구현은 0.2.0 Milestone E다.

**모든 future provider의 전제.** 모든 호출이 0.1.2의 `invokeLLM` redaction 경계를 지난다. DUO validation(JSON parse → schema → Evidence ID)이 최종 경계로 남는다. key를 config, cache identity, metrics, diagnostics에 넣지 않는다. 기본값은 off이고 implicit discovery는 없다. provider-error와 invalid-response 구분은 기존과 같다.

## 11. Unity / Unreal Noise

- ECS samples는 coverage 8,074 파일 중 7,223개(89%)가 L0였다. 여기에는 `.meta` 4,169개와 scene, prefab이 들어 있다.
- ActionRoguelike는 1,948개 중 1,780개(91%)가 L0였고 indexed 크기는 753 MiB였다. 확장자별 집계는 하지 않았다.
- 이 파일들은 scan과 fingerprint 비용을 만든다(§4.2). Context 품질은 해치지 않았다(ECS 3/3).

지금 `.meta`, prefab, scene을 ignore 대상으로 결정하지 않는다. Unity `.meta`에는 asset과 script를 잇는 GUID가 있고 scene·prefab은 그 GUID로 서로를 참조한다. 다음 세 방향을 별도 설계 문제로 남긴다.

| 방향 | 얻는 것 | 잃는 것 |
|---|---|---|
| ignore | scan·fingerprint 비용 감소 | asset 변경의 Review evidence, GUID 관계 |
| deprioritize | Context 예산 보호 | freshness 비용은 그대로 |
| asset-aware analysis | GUID 관계를 Graph에 표현 | 새 analyzer와 설계 필요 |

지금도 사용자는 `project.yaml`의 `index.exclude`로 직접 제외할 수 있다. DUO가 권하는 기본값은 아니다.

## 14. T23: Reproducible Real-world Benchmark Harness

**상태: 구현(T23).** 결과, 구조, 결과 형식, 실패 구분, 3 OS 결과는 [performance-benchmark의 Real-world baseline](../performance-benchmark.md#real-world-baseline-t23)에 있다(C221, C222). 아래는 착수 전 spec이다. 구현에서 달라진 점: manifest를 `bench/realworld-repos.mjs`로 분리했고, 1-file 편집은 주석 대신 새 최상위 선언을 붙이며, Context 시나리오는 편집 전의 pristine tree에서 잰다. `compare.mjs`는 한 쪽에 여러 결과 파일을 받고, 비교 불가를 exit 2로 구분한다.

**선택: T23 = Real-world Benchmark Harness.** 새 framework를 만들지 않고 기존 `bench/`를 확장한다. Freshness Optimization을 먼저 하지 않는 이유는 다음과 같다.

1. Freshness의 real-world 이득은 아직 불확실하다. synthetic large에서는 analysis cache 확인이 2,138 ms이지만 실제 Unreal과 Unity에서는 72 ms와 401 ms다. B가 할 만한지는 real-world before/after로 판단해야 한다.
2. 지금의 real-world 측정은 재현되지 않는다. suite는 각 저장소의 그 시점 HEAD를 clone하므로 다시 실행하면 다른 commit을 잰다. `bench/compare.mjs`는 synthetic 결과 형식만 읽는다.
3. 같은 PC가 날에 따라 약 1.6배 달랐다. before/after는 같은 세션에서 재야 하고, 결정적 출력과 시간을 분리해 비교해야 한다.
4. 필요한 조각은 이미 있다: `realworld.mjs`, `realworld-suite.mjs`, `context-quality.mjs`, `compare.mjs`, `invariant.mjs`. 확장 규모가 작다.
5. B의 완료 조건(3 OS before/after, clean-full equivalence)과 C의 확인(Context found/missing)이 모두 이 baseline을 쓴다.

### Scope

1. `bench/experiments/realworld.mjs`를 `bench/realworld.mjs`로 올린다. `--out`과 `--runs N`(no-op 반복, 기본 3)을 더한다. 1-file 편집 뒤 incremental graph와 clean full rebuild graph의 `dumpGraph` 동일성을 확인한다. 출력은 결정적 부분과 시간 부분을 분리한다.
2. `bench/experiments/realworld-suite.mjs`를 `bench/realworld-suite.mjs`로 올린다. 저장소 목록에 T22 commit SHA를 고정하고, SHA를 depth 1로 fetch해 OS temp에 받는다. HEAD가 고정 SHA와 다르면 측정 전에 실패한다. `context-quality.mjs`의 경로를 쓴 과제를 저장소별 과제 목록에 합친다. 결과 형식은 `duo.bench-realworld/1`이고 machine, Node, DUO commit과 dirty 여부, 저장소별 SHA를 담는다. 옵션은 `--only`, `--out`, `--duo-root <checkout>`(before/after용으로 다른 checkout의 build를 실행)이다.
3. `bench/compare.mjs`가 형식에 따라 분기한다. real-world 결정적 필드를 비교한다: 저장소 SHA, scan 수, coverage, 제외 사유별 수, no-op status, incremental mode와 분석 파일 수, clean-full 동일 여부, Context status·found·missing·files, Review verdict. 시간은 나란히 보고하고 비율을 적되 gate로 쓰지 않는다. 저장소 SHA나 OS가 다르면 비교를 거절한다.
4. `package.json`에 `benchmark:realworld`를 추가한다. `benchmark`와 CI 필수 경로에는 넣지 않는다.
5. 수동 `workflow_dispatch` job 하나: 3 OS에서 작은 저장소 3개(spring-petclinic, bulletproof-react, FastAPI template)를 측정하고 결과 JSON을 artifact로 올린다. push와 PR에서는 실행하지 않는다.

## 15. T24 첫 task 제안: C217 overload-safe Symbol identity (구현하지 않음)

> **T24.1 갱신(H-51).** 이 절의 설계 방향 "set 크기가 2 이상이면 overload마다 signature를 ID에 붙인다"는 채택하지 않았다. 저장소가 `foo()`에서 `foo()` + `foo(int)`로 바뀌는 순간 기존 `foo()`의 ID가 바뀐다(identity churn). T24.1은 Symbol identity를 그대로 두고 `additionalLocations`를 Context·Evidence·Review가 쓰게 했다: [0.2.0-t24-overloads.md](0.2.0-t24-overloads.md). 아래 조사 내용(Symbol ID가 닿는 곳, migration 조건)은 그대로 유효하고, member identity는 C224(T24.2)에서 다시 설계한다.

**조사한 현재 계약(0.1.2 코드).**

- identity: `StructuralCollector.symbol()`이 최상위는 qualifiedName, member는 `Type.name`·`Type.static.name`을 identity로 정한다. `merged()`는 같은 identity의 선언을 Symbol 하나로 합친다. primary는 본문이 있는 첫 선언이고 나머지는 `additionalLocations`다. Node ID는 `sym:<path>#<identity>`(core `nodeId`)다. TypeScript의 "overload signature + implementation = 한 Symbol" 규칙(H-22)을 본문이 여럿인 언어에도 적용한 결과다.
- 저장과 사용: Graph payload에 `additionalLocations`가 저장되지만 읽는 곳이 없다. Context 후보와 slice, Review diff seed(hunk와 `source` 범위의 겹침), Impact는 primary `source`만 쓴다. 두 번째 overload를 고친 hunk는 바깥 class Symbol로 귀속된다.
- probe: Java `ServiceImpl.run` source 4-6 + additional 8-10, C# `Game.Player.Move` 5 + 6, C++ `.h`와 `.cpp` 각각 `game.AWeapon.Fire` 하나 + additional, Python 같은 이름 재정의 `f` 1-2 + 4-5.
- 실제 규모(T23 clone, 합쳐진 Symbol 수): spring-petclinic 2(`Owner.getPet`, `VetRepository.findAll`), ActionRoguelike 11(constructor 9, method 2), ECS samples 48(method 37, constructor 10, property 1), TypeScript와 Python 저장소 0.

**Symbol ID가 닿는 곳.**

| 영역 | 현재 | overload를 나누면 | migration |
|---|---|---|---|
| 재생성 데이터(graph.db, index state, analysis cache) | analyzer identity, `graph_schema_version` | analyzer version을 올려 재분석하고, payload 형식이 바뀌면 schema version을 올려 incompatible 보고 뒤 재구축한다 | 필요 없음(공개 계약 아님) |
| Truth `implements.symbols`, `governs.symbols`, `forbids.symbols`, `match.symbols`(사람 소유, `schema_version: 1`) | qualifiedName이 Symbol 정확히 1개와 일치할 때만 edge, 아니면 `DECLARED_SYMBOL_UNRESOLVED` | 같은 qualifiedName이 여러 개가 되어 기존 참조가 unresolved로 바뀐다 | 해석 규칙 필요 |
| adoption baseline(`duo.adoption-baseline/1`, tracked) | `forbids.symbols` 위반의 offending은 Symbol node ID | overloaded Symbol의 key가 바뀌어 pre-existing이 introduced로 재분류될 수 있다(BLOCK 가능) | offending을 overload set identity로 유지하거나 형식 version을 올린다 |
| Review Record(`duo.review-record/1`, tracked) | claim subject에 node ID, claim ID는 subject를 포함한 hash, evidence pointer는 path·line·hash | 옛 record는 옛 ID를 가진 이력으로 남는다 | 필요 없음(재해석하지 않음). UI 이력은 현재 Graph에 없는 ID를 그대로 보여 준다 |
| CLI·MCP payload(`duo.context-packet/1`, `duo.trace/1`, `duo.impact/1`) | node ID는 값 | overloaded Symbol만 새 ID | overload 없는 ID가 그대로면 형식 불변 |
| Context seed | 이름·qualifiedName keyword seed | 같은 이름 여러 개 → ambiguous 가능 | overload set을 한 seed 후보로 묶는 규칙 필요 |

**판단.** 아래 세 조건을 지키면 migration 없이 가능하다.

1. overload가 없는 Symbol의 ID, qualifiedName, source는 그대로다.
2. Truth의 qualifiedName 참조는 같은 파일 안 overload set 전체를 가리킨다. 지금의 합친 Symbol이 뜻하던 범위와 같다. 개별 overload 참조 문법은 선택적으로 추가한다.
3. adoption baseline의 Symbol offending은 overload set identity를 쓴다. 이 값은 지금 ID와 같은 문자열이다.

하나라도 지킬 수 없으면 해당 형식의 version을 올리는 결정이 먼저다. 조용히 재해석하지 않는다(H-35).

**설계 방향(ADR 필요).**

- overload set은 같은 파일, 같은 identity를 가진 선언의 집합이다. set 크기가 1이면 지금과 같은 Symbol이다.
- 크기가 2 이상이면 각 overload가 자기 Symbol과 source를 가진다. overload ID는 set identity에 언어별 syntactic signature를 더한다. signature는 parameter type을 쓰인 그대로 쓰고, 이름, 기본값, 공백은 뺀다. 언어별로 정할 것:
  - Java: varargs `...`, generic 인자 텍스트
  - C#: `ref`·`out`·`in`·`params`, nullable `?`
  - C++: template parameter, method의 `const`·`&`·`&&` 포함 여부
  이름 + arity나 선언 순서 번호로 정하지 않는다. type resolution이 없으므로 `List<String>`과 `java.util.List<String>`은 다른 signature다(문서화).
- signature가 같은 두 선언(서로 다른 `#if` branch, parse 한계)은 조용히 합치지 않고 diagnostic을 남긴다.
- C++ header의 본문 없는 선언과 cpp 정의의 연결은 C218에서 한다. T24는 같은 파일 안의 overload만 다룬다.
- Python의 같은 이름 재정의는 overload가 아니다(런타임은 마지막 정의를 쓴다). T24 범위 밖이며 따로 기록한다. **T24.4:** 확실한 경우 실효 정의를 primary로 둔다(C226 Resolved, [0.2.0-t24-python-definitions.md](0.2.0-t24-python-definitions.md)).
- TypeScript는 바꾸지 않는다.

**Scope.** Java·C#·C++ analyzer identity와 analyzer version, builder의 Truth Symbol 참조 해석, adoption baseline의 Symbol offending 규칙, Context seed의 overload set 처리, [language-support](../language-support.md)와 [04-project-graph](../04-project-graph.md) 갱신, ADR.

**Non-goals.** C218, C219, L2 resolver, CALLS 해석 변경, TypeScript·Python 변경, 공개 analysis level 변경, Truth schema version 변경.

**Acceptance criteria.**

1. probe의 overload(Java `run()`/`run(int)`, C# `Move()`/`Move(int)`, C++ `Fire()`/`Fire(int)`)가 각각 Symbol과 source를 가진다. 과제 "ServiceImpl run times"의 Packet에 `run(int)` 본문이 있다.
2. overload가 없는 Symbol의 node 행은 T23 harness 5개 저장소에서 byte 단위로 같다. Graph 차이는 합쳐졌던 Symbol(위 규모)과 그 edge로 한정되고 diff로 설명된다.
3. Truth 참조 `ServiceImpl.run`이 두 overload 모두에 edge를 만들고, 새 `DECLARED_SYMBOL_UNRESOLVED`가 생기지 않는다.
4. 0.1.2 build로 캡처한 adoption baseline의 pre-existing `forbids.symbols` 위반이 T24 build에서 introduced로 바뀌지 않는다(fixture).
5. 같은 signature 충돌은 diagnostic이 된다.
6. 5개 저장소 모두 incremental = clean full이고, fuzz와 3 OS CI가 통과한다.
7. analyzer version을 올리면 기존 cache를 다시 분석하고 index가 current로 수렴한다.

**Before/after.** T23 `--duo-root` A/B를 같은 세션에서 3 round 실행한다. 결정적 diff는 합쳐졌던 Symbol이 있는 파일에만 있어야 한다.

**Rollback.** overload가 없는 Symbol ID가 하나라도 바뀌거나, 기존 Truth 참조가 unresolved로 바뀌거나, baseline 재분류가 생기면 되돌리고 ADR을 다시 연다.
