## 2. 현재 gap → verdict mapping (코드 기준)

`packages/director/src/review/aggregate.ts` `reviewVerdict`: BLOCK = blockEligible claim, ASK = `gaps.requiresHumanInput`일 때 action ask인 gap, WARN = non-blockEligible·non-pre-existing PARTIAL·CONFLICT·UNKNOWN drift claim **+ action surface인 모든 gap**, 아니면 PASS. gap action은 `gap/assess.ts`가 정한다.

| gap | 조건 | action | verdict 영향 |
|---|---|---|---|
| ambiguous-target | explicit task 대상이 둘 이상 | ask | ASK |
| unresolved-target(unresolved ID) | task의 ID가 Truth에 없음 | ask | ASK |
| pending-decision | requiresHumanDecision이고 명시적 연결(explicit seed, 1 Edge, task의 proposal ID) | ask | ASK |
| pending-decision | 검색으로만 닿음 | surface | WARN |
| declared UNKNOWN direct | 활성 Decision이 해결하지 않음 | ask | ASK |
| declared UNKNOWN related | 같음 | surface | WARN |
| declared UNKNOWN none / 해결됨 | | ignore | 없음 |
| **missing-intent** | seed 없음(`no-seed`) 또는 packet signal `no-confirmed-intent` | surface | **WARN** |

`assess.ts` 머리 주석: "no seed, no confirmed intent: surface (a bug fix may not need intent; nothing proves otherwise)".

## 5. 권장: Option B와 경계

- **PASS 의미**: ADR-007·03 `ReviewResult`의 PASS는 "현재 Evidence 범위에서 방향 위반을 찾지 못했다"이고 버그 없음·완전한 coverage를 뜻하지 않는다. PASS가 "gap 없음"을 보증한다는 문장은 없다. PASS + missing-intent gap은 계약상 가능하다(정지 조건 2 해당 없음). 03의 ReviewResult는 `verdict`와 `gaps`를 따로 둔다.
- **ASK**: ASK는 `requiresHumanInput`과 action ask gap만 근거다. missing-intent는 ask가 된 적이 없어(C97) 빼도 ASK 집합은 같다. D case: B 적용 뒤에도 ASK(verdictBasis.ask 그대로). explicit ambiguity, unresolved ID, 명시적 연결의 pending Decision, direct declared UNKNOWN 모두 불변(정지 조건 4 해당 없음).
- **BLOCK·WARN claim**: claim 집합과 blockEligible은 gap과 무관하다. C·C2는 BLOCK 그대로, C2의 WARN 근거 claim 3개도 그대로다. verdictBasis.warn에서 gap ID만 빠진다.
- **Claim**: missing-intent는 Knowledge Gap으로 남는다. claim 추가, `unlinked-addition` 변환, synthetic Requirement claim, fake evidence 없음.
- **다른 surface gap**(검색으로만 닿은 pending Decision, related declared UNKNOWN)은 이번 결정 범위가 아니며 WARN을 유지한다. 이들은 이 변경이 닿은 Truth에 실제 미결 질문이 있다는 신호이고, intent가 없다는 부재 신호와 성격이 다르다. noise가 관찰되면 별도로 판단한다.

B를 적용한 mapping으로 §1 결과를 다시 계산하면(gap action은 그대로, verdictBasis.warn에서 missing-intent ID만 제외): A PASS, B PASS, C BLOCK, C2 BLOCK, D ASK, E PASS.

## 8. 호환성과 기록

- **schema**: `duo.review/1` 유지. ReviewResult 형식, `gaps`, verdict enum, claim schema, verdictBasis 형식 모두 불변이다. verdictBasis.warn의 의미("WARN을 만든 ID")도 같고 들어가는 ID 집합만 줄어든다. compatibility.md의 선례(0.2.0·0.2.2 "Behavior correction", H-72의 새 BLOCK 조건)처럼 같은 `/1`의 동작 변경으로 분류하고 release notes·compatibility에 적는다. 정지 조건 3(schema major bump) 해당 없음.
- **Review Record**: body에 `review.verdict`, `review.verdictBasis`, gap 요약이 들어가고 ID는 body의 sha256이다(C118). B 적용 뒤에는 missing-intent가 있는 **모든** review의 Record body가 달라진다. WARN→PASS인 경우(A·B)는 verdict와 verdictBasis가, verdict가 그대로인 경우(C·C2·D)도 verdictBasis.warn이 바뀌므로 Record ID가 새로 난다. gap 요약은 같다. 이전 Record는 다시 쓰지 않고 읽기 전용으로 남으며(compatibility 정책), 새 ID라 integrity 충돌도 없다. `duo.review-record/1` 형식은 그대로다.
- **metrics**: review 실행의 verdict 분포가 바뀐다(`duo.metric/1`은 공개 계약 아님). gap 수(`surface` count)는 그대로 남아 coverage를 계속 볼 수 있다.

## 9. Adoption과 onboarding

adoption 직후 Truth는 `project.yaml`과 몇 개의 Decision 정도다. Requirement가 없으면 거의 모든 변경의 review packet에 Requirement·Decision tier item이 없어 정상 변경마다 WARN이 난다. 측정된 결과는 T31·T32 정상 변경 20/20 WARN, claim 0이다. 영향은 세 가지다. `--strict`·`--fail-on warn`을 쓰는 팀은 첫날부터 정상 PR이 실패해 strict를 끄게 된다. 끄지 않는 팀은 WARN을 무시하는 습관이 생겨 adoption baseline이 만든 의미 있는 WARN(pre-existing-touched)과 drift WARN이 묻힌다. gap을 없애려고 사람이 확정하지 않은 형식적 Truth를 쓰게 만드는 유인이 생겨 Human이 확인한 것만 Truth라는 원칙(ADR-014)과 T34의 Truth 유지 비용 감소 목표와 반대로 간다. C239는 benchmark 표시 문제가 아니라 첫 사용 경험의 기본 신호 품질 문제다.

B 아래에서는 "확정 intent 연결 없음"이 계속 보이므로 사용자는 어디에 Truth가 비어 있는지 알 수 있고, WARN은 실제로 볼 것이 있을 때만 남는다.

## 11. H-80 초안

> H-80 — Runtime Knowledge Gap `missing-intent`(`no-seed`, `no-confirmed-intent`)는 Review coverage·explainability signal이며 단독으로 verdict를 WARN으로 올리지 않는다(C239, C110 수정).
>
> 1. 뜻: 이번 review 맥락에서 확정 Requirement·Decision 연결을 찾지 못했다. policy conflict, code defect, 해결되지 않은 explicit instruction, 즉시 필요한 Human 선택이 아니다.
> 2. gap은 그대로 만든다. `ReviewResult.gaps`, CLI·MCP structuredContent·UI, Review Record gap 요약, metrics에 남는다. action은 surface 그대로이고 ask가 되지 않는다(C97).
> 3. `reviewVerdict`는 missing-intent gap을 `verdictBasis.warn`에 넣지 않는다. 다른 claim·gap이 없으면 PASS다. PASS는 계속 "현재 Evidence 범위에서 방향 위반을 찾지 못함"이며 coverage를 보증하지 않는다.
> 4. 불변: ambiguous-target, unresolved ID, 명시적 연결의 pending Decision, direct declared UNKNOWN의 ASK. 검색으로만 닿은 pending Decision과 related declared UNKNOWN의 surface → WARN. 모든 claim(BLOCK, non-blocking CONFLICT·PARTIAL·UNKNOWN drift의 WARN, provenance 정책).
> 5. claim을 만들지 않는다(synthetic claim, `unlinked-addition` 변환, fake evidence 금지). LLM으로 보완하거나 LLM이 verdict를 정하지 않는다.
> 6. task 유무로 missing-intent의 severity를 바꾸지 않는다(H-31).
> 7. `--strict`는 계속 `--fail-on warn`이다. coverage gate가 필요하면 별도 결정.
> 8. `duo.review/1`, `duo.review-record/1` 형식 유지. 동작 변경으로 compatibility·release notes에 적는다. missing-intent가 있는 review의 Record ID는 새로 나며 이전 Record는 다시 쓰지 않는다.
> 9. 구현은 `next`에만. main과 npm `latest`는 그대로, External Validation 01은 0.2.1 그대로.
