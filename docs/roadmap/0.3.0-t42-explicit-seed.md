# T42 — F-23 Explicit Seed Preservation

branch `next`, H-76. T41의 유일한 RC P1(F-23)만 닫는다. version은 `0.3.0-rc.1` 그대로이며 publish·tag·release는 하지 않는다.

## 1. 원인

`packContext`(director `context/pack.ts`)는 seed를 `mandatory`로 L1(제목)까지만 보장했다. 그 위 승격은 일반 규칙을 따랐다. tier 순서가 requirement > decision > pending > code-direct > test > issue이고, tier마다 남은 승격 예산의 몫이 정해져 있다. 그래서 seed가 Issue이면 같은 Requirement에 `VALIDATED_BY`로 매달린 다른 Issue의 테스트가 test tier에서 먼저 예산을 쓰고, seed Issue는 issue tier 차례에 남은 몫만 받았다. OpenHub TASK-010은 예산 12,000에서 omit된 후보가 하나도 없는데도 seed만 L1이었다.

## 2. 변경

- explicit primary seed: seed resolution에서 `match: "id"`인 Requirement 또는 Issue(깊이 0). candidates가 `primary` 표시를 붙인다. keyword·path·symbol·symbol-name seed, Review의 `explicitSeeds`(match `diff`), traversal 항목은 해당하지 않는다. Review의 diff seed와 task 문자열이 같은 ID를 가리키면 seed는 `diff`로 남는다(먼저 추가되고 strength가 같음).
- packer 순서: frame → 필수 항목 L1(기존과 같음, active Decision·confirmed Constraint 보존) → explicit primary seed를 한 단계씩 들어가는 가장 높은 표현까지 → 기존 capped·uncapped 승격 → exact check. exact check는 log를 역순으로 되돌리므로 일반 승격이 먼저 되돌려진다. 지시의 그림은 primary를 필수 L1보다 앞에 두었으나, 예산이 매우 작을 때 active Decision이 빠지지 않도록 필수 L1을 먼저 두었다(K 테스트).
- 여러 seed: plan 순서(tier, 순서값, 깊이, ID)로 처리한다. task에 적은 순서나 Map 순회와 무관하다.
- full 표현이 들어가지 않으면: 들어가는 가장 높은 기존 단계(L1·L2·L3 중 하나)를 넣고 limitation `explicit-seed-truncated`를 붙인다. 예(fixture의 큰 Issue): "Explicit seed <ID> could not fit its full specification within the 2500-token budget (N tokens); the highest fitting representation (L1) is shown." 들어가지 못하면 "… it is not shown." frame 예약은 이 줄을 최악의 길이로 포함한다. AC를 일부만 자른 새 표현은 없다.
- `CONTEXT_POLICY_VERSION` 2 → 3(선택이 바뀌므로 예전 cache Packet이 맞지 않게 한다).
- docs/05 packing 절, conflicts C246.
