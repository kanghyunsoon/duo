## 2. Core user story

후보 문장: "Keep coding agents from violating human-confirmed engineering decisions." 실제 동작은 "agent가 어긴 변경을 review가 찾아 BLOCK하고 근거를 보인다"이다. agent가 코드를 쓰는 것 자체를 막지는 않는다. canonical demo에서도 Codex는 시킨 대로 위반 코드를 썼고, DUO는 그 뒤 review에서 BLOCK했다. 따라서 "keep from violating"은 CI의 `--fail-on block`과 함께일 때 맞는 말이다. README headline은 §9에서 다룬다.

## 9. README positioning

현재 첫 화면: headline "Decision compliance for coding agents." 다음 문장 "Keep coding agents aligned with human-confirmed engineering decisions…DUO does not write code." 5초 안에 "무엇을 하나"에 답이 된다. 바로 아래 "Why not just AGENTS.md…"가 있고 데모, Quick start, How it works 순서다. Project Graph, Context Compiler, Evidence Engine, Knowledge Gap은 첫 화면에 없고 How·Core concepts에 있다. Adoption Baseline은 "Why not" bullet 하나로 나온다.

권장 후보 "Stop coding agents from breaking human-confirmed engineering decisions."는 더 직접적이지만 실제 동작보다 강하다. DUO는 agent가 쓰는 것을 막지 않고, review와 CI의 `--fail-on block`에서 막는다(§2). 기존 headline이 더 정확하므로 유지를 권한다. 0.3 README에 필요한 것은 문구보다 다음이다. (1) RC build로 데모 재녹화(N5). (2) Decision이 막을 수 있는 것(paths, symbols, dependencies, imported paths)과 막지 못하는 것(호출, 범위 지정 import, Java·C# import)을 한 줄로 밝힌다. (3) "Why not a linter?"에 dependency-cruiser·ESLint와의 관계를 정직하게 적는다(§10). 이번에는 사실 오류 세 건만 고쳤다.

## 10. 대체재 비교

| | A AGENTS.md + Codex review | B 50~100줄 script | C ESLint `no-restricted-imports` / dependency-cruiser | D DUO next |
|---|---|---|---|---|
| 금지 import 탐지 | 대체로 가능(이번 Codex도 규칙을 이해), 비결정적 | TS 상대 경로는 쉬움, alias·export-from·dynamic import 해석은 추가 작업 | 강함: 전체 파일, from→to 범위 지정, 성숙한 CI 통합. dependency-cruiser는 known-violations baseline도 있음 | 바뀐 줄만, 해석된 repository 파일, 범위 지정 없음 |
| 기존 위반 처리 | 사람이 판단 | state 파일로 가능(T32 DIY) | eslint-disable 또는 baseline | Adoption Baseline provenance |
| 규칙의 출처와 승인 | 문서 편집, 승인 기록 없음 | 코드 | 설정 파일 PR | agent proposal → preview → digest-bound confirm → lock |
| 여러 agent가 같은 규칙을 읽음 | 파일로 가능 | 아니요 | 아니요(규칙은 lint 설정) | MCP로 같은 Truth |
| 결정적 근거 | 아니요 | 예 | 예 | 예(Decision·줄·hunk) |

대체 가능한 것: 탐지(T31·T32에서 이미 확인), 기존 위반 구분(DIY 재현됨). `imported_paths`만 놓고 보면 dependency-cruiser보다 약하다(범위 지정, 전체 그래프 검사가 없음). DUO에만 남는 것: 하나의 Truth 저장소에서 agent가 제안하고 사람이 본 그대로 확정하며 lock되는 Decision lifecycle, 그리고 그 Decision과 코드 줄을 잇는 결정적 claim. Informed Confirm은 의미 있다. 0.2.1에서는 사람이 forbids·enforcement를 보지 않고 확정할 수 있었고, 이것은 실제 권한 구멍이었다. Adoption provenance는 기존 저장소에서 쓸모 있지만 재현 가능하다. Decision lifecycle이 실제로 추가 가치를 주는지는 External Validation 결과 전까지 미증명이다(H-66).

## 11. 0.3.0의 사용자에게 보이는 변화(3개)

1. Agent가 강제 가능한 Decision 전체(forbids, enforcement, supersedes)를 제안한다.
2. 사람은 본 내용 그대로를 확정한다(전체 preview, digest-bound confirm, stale 표시).
3. 확정된 Decision이 금지된 repository import를 바뀐 줄에서 BLOCK한다(provenance 표시는 baseline 기준 용어).

minor release 가치: 셋 모두 추가 field·추가 입력이라 semver minor에 맞고, 2는 0.2.1의 실제 권한 구멍을 닫는다. 다만 3은 기존 linter보다 약하고 제품 가치 자체는 미증명이다. 그래서 `latest`가 아닌 prerelease(RC)로 내는 것이 맞다. stable 승격은 External Validation과 별도 결정에 둔다.

## 16. 권고: B. CONDITIONAL GO

0.3 방향의 핵심 workflow는 동작하고 데이터·계약·성능·설치에 막힘이 없다. 그러나 RC 전에 다음을 별도 task(T40 제안)로 처리해야 한다.

1. **N1(P0)**: 읽을 수 없는 Truth 파일을 사람 출력(status, doctor, review)과 review JSON에 진단·limitation으로 보이게 한다. verdict를 바꿀지(예: ASK)는 의미 변경이라 Human Decision이 필요하다.
2. **N3(P1)**: preview와 MCP 설명, docs에 "forbids는 저장소 전체에 적용되고 governs로 좁혀지지 않는다"를 명시한다. importer 범위 field는 0.3 이후 Human Decision 후보다.
3. **N2(P1)**: release note에 하위 버전 비호환과 rollback 절차를 적는다. RC는 dist-tag `next`로만 publish한다.
4. **N4·N5(P1)**: version `0.3.0-rc.1`, RC build로 README 데모 재녹화.
