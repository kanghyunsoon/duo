# T24.5 Truth qualifiedName references to proven C++ declaration groups (C231)

0.2.0 Milestone C의 마지막 task다. 결정: H-55. C++ 공개 level은 L1 그대로다.

## 1. 결과

Truth의 qualifiedName 참조(`governs.symbols`, `implements.symbols`)가 persisted Symbol 여럿과 일치해도, 그 일치 전체가 T24.3이 증명한 C++ 선언·정의 쌍 정확히 하나이면 그 참조를 해석한다. 기존 edge type 그대로 header 선언 Symbol과 `.cpp` 정의 Symbol 둘 다에 edge를 만든다. 일치가 하나인 참조, paths로 좁혀지는 참조, overload 그룹, 쌍 + 다른 Symbol, link 없는 같은 이름, 다른 언어는 이전과 같다.

해석 조건을 정확히 쓰면: "Truth qualified-name references that match multiple persisted C++ Symbols may resolve only when all matches form exactly one proven declaration-definition group." DUO가 C++ 선언 일반을 이해한다는 뜻이 아니다.

함께 찾은 문제(C233): builder 규칙만 바뀌는 수정은 analyzer identity나 resolver version이 그대로라 기존 index가 `current`로 남아 반영되지 않았다. index state에 `relationRulesVersion`을 기록해 DUO를 올린 뒤 첫 확인에서 stale이 되고, `duoctl index` 한 번(analysis cache 재사용)으로 회복된다.

## 2. Truth resolution lifecycle 감사

| 단계 | 위치 | 동작(T24.5 이전) |
|---|---|---|
| 이름 참조 필드 | Requirement `implements.symbols`, Decision `governs.symbols` | qualifiedName 문자열. Symbol ID 직접 참조 문법은 없다 |
| 패턴 필드(해석 없음) | Decision `forbids.symbols`, Constraint `match.symbols` | wildcard로 seed의 qualifiedName과 비교. header·cpp 둘 다 이미 맞는다(C231 대상 아님) |
| qualifiedName lookup | builder `symbolsNamed(name, paths)` | 분석된 모든 파일의 Symbol 중 qualifiedName이 같은 것 |
| path narrowing | Requirement는 `implements.paths`로 먼저 좁힘, Decision `governs.symbols`는 paths 없음 | 좁힌 뒤 개수를 센다 |
| 일치 1개 | `declaredSymbol` | 그 Symbol에 edge(`IMPLEMENTS` Symbol → Requirement, `GOVERNS` Decision → Symbol), metadata `{provenance: declared, basis: [필드]}` |
| 일치 0개·2개 이상 | `declaredSymbol` | `DECLARED_SYMBOL_UNRESOLVED`(warning, "matches N symbols; no edge"), edge 없음. paths가 L0 파일만 가리키면 `DECLARED_SYMBOL_UNVERIFIABLE`. 별도 ambiguous code는 없다 |
| 저장 | index state `diagnostics`(persistent, canonical 정렬) | Review와 adoption이 다시 계산하지 않고 읽는다 |
| Review | `declared-reference` rule: state diagnostic → PARTIAL claim(Decision이 Packet에 있거나 Truth 파일이 바뀐 경우) | `decision-governance`·`requirement-implementation`은 seed의 GOVERNS·IMPLEMENTS edge를 Decision·Requirement별로 모아 claim 하나 |
| adoption baseline | init 때 그 시점 diagnostic으로 `declared-reference` finding(violation key = rule + 정의 + 참조, 줄 없음) | Review claim의 provenance(기존·새 위반) 분류에만 쓰고, finding 자체를 다시 보고하지 않는다 |
| trace, impact | Graph edge | edge가 없으면 연결 없음 |
| Context | Decision seed → GOVERNS → Symbol(T24.3 그룹 item 하나로 합침) | edge가 없으면 Decision에서 code로 가지 않음 |
| UI, MCP | Decision 화면은 Truth 문자열, entity·graph 화면은 trace edge, `duo_search`는 baseline finding도 찾음 | edge 그대로 표시 |

질문에 대한 답:

1. **일치가 하나인 참조.** 그 Symbol 하나에 edge. 바뀌지 않았다.
2. **ambiguous가 finding이 되는 단계.** builder가 `DECLARED_SYMBOL_UNRESOLVED`를 만들고 index state에 저장한다. Review는 그것을 `declared-reference` claim으로, adoption은 init 때 baseline finding으로 옮긴다.
3. **path.** Requirement는 paths로 먼저 좁힌 뒤 센다. 그룹 해석은 그 뒤에 남은 일치에만 적용한다.
4. **baseline이 현재 상태를 다시 계산하는가.** 아니다. baseline은 adoption 시점 기록이고, Review의 claim은 현재 index의 diagnostic에서 나온다.
5. **기존 unresolved가 사라지는가.** 다음 index에서 diagnostic이 없어지므로 Review claim도 없어진다. baseline 파일의 finding 기록은 남지만(adoption 당시 사실) 새 claim을 만들지 않는다.
6. **re-init, re-adoption, migration.** 필요 없다. `duoctl index` 한 번이면 된다(§5).
7. **declaration links와의 순서.** 이전에는 Truth 해석이 module resolution보다 먼저였고 links는 build 끝에서 계산됐다. 이제 일치가 둘 이상인 참조만 보류하고, module resolution 뒤 **같은 run의** links를 계산한 다음 결정한다. 이전 index의 `declaration_links` metadata는 읽지 않는다. 기존 edge의 merge 순서는 그대로다(module·call 단계는 IMPORTS, CALLS, Symbol → Test VALIDATED_BY만 만들고, 보류 해석은 annotation 단계보다 앞).

## 3. Edge projection 비교

| 기준 | A. 두 Symbol 모두 GOVERNS·IMPLEMENTS | B. 대표 Symbol 하나 | C. edge 하나 + query/Review에서 그룹 확장 | D. resolver가 그룹 결과를 내고 소비자가 투영 |
|---|---|---|---|---|
| header 수정 governance | 있음(edge) | 대표가 cpp면 없음 | 확장하는 소비자만 | 소비자 구현에 따름 |
| cpp 수정 governance | 있음 | 대표가 header면 없음 | 같음 | 같음 |
| Review | 기존 rule 그대로(Decision별 claim 하나) | 한쪽 수정 누락 | rule마다 links 읽기 추가 | 같음 |
| Context | T24.3 그룹 item 하나 | 한쪽만 seed, 그룹 item | 같음 | 같음 |
| trace | 두 Symbol 각각 edge(persisted 사실) | 하나 | 하나(나머지 숨음) | 소비자마다 |
| impact | header·cpp 어느 쪽에서도 Decision 도달 | 한쪽에서만 | 확장 필요 | 확장 필요 |
| UI, MCP | edge 2개 표시 | 1개 | 1개 | 새 응답 형태 위험 |
| Graph hash | 이전에 unresolved였던 참조에만 edge 2개 추가 | 1개 추가 | 1개 추가 | 구현에 따름 |
| 중복 claim | 없음(rule이 Decision·Requirement별로 묶음) | 없음 | 없음 | 소비자마다 |
| Decision Lock | 변화 없음(lock은 Truth 내용) | 같음 | 같음 | 같음 |
| adoption baseline | finding이 더 생기지 않음 | 같음 | 같음 | 같음 |
| future C++ L2 | 그대로 쓸 수 있음 | 대표 선택이 L2와 충돌 | L2에서 다시 설계 | 새 모델 |
| migration, public schema | 없음 | 없음 | 없음 | 응답 형태 변경 가능 |

A를 골랐다. 대표 하나(B)는 다른 쪽 수정이 governance에서 빠진다. C와 D는 edge를 읽는 모든 소비자(Review rule, impact, trace, Context)에 links 해석을 더해야 한다. A는 소비자를 바꾸지 않고, 사용자에게 보이는 중복이 없음을 아래에서 확인했다.

- Review: `decisionGovernance`와 `requirementImplementation`은 seed를 Decision·Requirement별로 모아 claim 하나를 만든다. header와 cpp를 함께 고치면 claim 하나에 두 Symbol이 나열된다(§7).
- Context: Decision에서 두 Symbol에 닿아도 T24.3 `dedupeGroups`가 item 하나로 합친다.
- trace·UI entity 화면: GOVERNS edge 2개(header Symbol, cpp Symbol)가 보인다. 각각 실제 persisted Symbol이라 과장이 아니다. Decision 화면은 Truth 문자열 하나를 보인다.
- impact: 한 seed에서 Decision에 한 번 도달한다(node별 best path). 두 Symbol을 seed로 주면 Decision item은 여전히 하나다.

## 4. 해석 조건

builder `declarationGroup`. 다음을 모두 만족할 때만 해석한다.

1. 기존 lookup(Requirement는 paths 적용 뒤) 결과가 정확히 2개
2. 둘 다 C++ 파일(analysis language `cpp`)의 Symbol
3. 각 Symbol이 선언 하나뿐(`additionalLocations` 없음, callable 하나): overload set이 아님
4. 이번 run의 declaration links 중 두 Symbol 중 하나에 닿는 link가 정확히 하나이고, 그 link의 선언 쪽과 정의 쪽이 두 Symbol

쌍 판정(qualified name, signature, 유일성, include 증거, H-54 suffix 범위)은 T24.3 link를 그대로 쓰고 여기서 다시 계산하지 않는다. 조건이 하나라도 맞지 않으면 이전과 같은 `DECLARED_SYMBOL_UNRESOLVED`다.

- overload(`void Foo(); void Foo(int);`가 각각 쌍): header Symbol 하나와 cpp Symbol 하나지만 link가 둘이고 callable도 둘이다 → unresolved
- 쌍 + 같은 qualifiedName의 다른 Symbol: 일치 3개 → unresolved
- link 없는 같은 이름(include 없음, signature 차이, template): unresolved
- 다른 언어의 같은 qualifiedName: unresolved
- 일치 1개(paths로 header만 또는 cpp만): 이전처럼 그 Symbol 하나

Symbol을 고르는 tie-break, 이름만으로 묶기, first match는 없다. Truth 문법은 바뀌지 않았다(C224 signature 문법 없음).

## 5. Freshness: relation rules version (C233)

Context, Review, MCP는 read-only `inspectIndex`가 `current`면 다시 index하지 않는다. stale 판정 입력은 fingerprint, analyzer identity, module·call resolution version, config, Git, Truth 변경이었고 builder의 Truth·annotation 규칙은 없었다. 그래서 T24.5만 설치하면 기존 index가 `current`로 남고, 저장된 `DECLARED_SYMBOL_UNRESOLVED` 때문에 Review가 계속 unresolved를 보고한다. T24.4의 annotation 후보 변경도 Python 외 언어에서 같은 문제가 있었다.

수정: builder `RELATION_RULES_VERSION`(1)을 index state의 optional `relationRulesVersion`에 기록한다. 이전 state(필드 없음)나 다른 값이면 inspect가 `stale`, `wouldRebuild.projectTruth: true`(parse 0)를 보고한다. Indexer는 원래 매번 전체 plan을 다시 만들므로 한 번의 incremental index로 규칙이 적용된다. `INDEX_STATE_VERSION`은 4 그대로라 전체 재구축이나 `INDEX_STATE_INVALID` 경고가 없다. 이전 DUO가 새 state를 읽으면 strict schema 때문에 한 번 전체 재구축한다(regenerable runtime 파일). 이후 builder의 관계 규칙을 바꿀 때 이 값을 올린다.

## 6. Graph·migration

- Symbol node ID 변화 0, node 변화 0.
- edge 변화: 이전에 unresolved였던 참조에만 기존 type edge 2개(`GOVERNS` 또는 `IMPLEMENTS`)가 생긴다. 다른 edge와 metadata는 그대로다.
- Truth schema, Graph schema, payload, edge type, CLI/MCP/UI 응답 형태 불변. index state에 optional 필드 하나.
- migration, re-init, re-adoption 불필요.

## 8. Milestone C

C231 Resolved. 남은 항목은 모두 Milestone C를 막지 않는다.

| 항목 | 상태 |
|---|---|
| C224 overload member identity | Deferred(H-52): member identity를 쓰는 첫 기능과 함께 |
| C229 polyglot Context ranking | 별도 Context milestone |
| C232 C++ IMPORTS include path | 문서화된 C++ L1 limitation(`imports: partial`) |

새 correctness blocker는 없다. C233은 찾은 즉시 고쳤다(§5). **Milestone C L1 Correctness를 완료한다.** 다음은 Milestone B Freshness다.

### 8.1 Milestone B 첫 task 제안: T25.1 analysis cache 확인 async·parallel (구현하지 않음)

0.2.0 audit §4.3 후보 1과 2. 먼저 Milestone C 뒤 build로 5개 저장소 noop·incremental freshness를 같은 세션 A/B로 다시 잰다(T24.3·T24.4·T24.5가 analyzer identity와 state를 바꿨다). 그다음 cache 확인을 비동기·제한 동시성으로 바꾸고, 한 freshness 호출 안의 `rev-parse --show-prefix` 중복을 없앤다. 조건: inspect와 index가 같은 판정 함수, 0.2.0 audit §4.3의 9개 시나리오를 regression test로, fuzz와 clean full equivalence, `relationRulesVersion`을 포함한 모든 stale 입력 유지, TTL·mtime-only·stale Graph 허용 금지, 3 OS before/after에서 개선 확인. 이득 상한이 작다는 점(ActionRoguelike 72 ms, ECS 401 ms)을 목표에 그대로 둔다.
