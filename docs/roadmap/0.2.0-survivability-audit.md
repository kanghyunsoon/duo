# T27.5 DUO Survivability / Positioning Audit

0.2.0 기능 동결 상태에서 수행한 전략 감사다. 구현 task가 아니며 production code, version(0.1.2), dependency를 바꾸지 않았다. 결정: H-61. 질문은 하나다. 경쟁 제품과 DIY 조합이 이미 있는 상황에서 DUO가 설치·유지 비용을 정당화할 만큼 다르게 동작하는가.

판정 어휘: **Yes**(공식 자료로 확인), **Partial**(일부 또는 다른 형태로 확인), **No**(공식 자료나 DUO 자신의 코드로 부재를 확인), **Unverified**(확인하지 못함). 공식 자료에서 찾지 못한 것은 No가 아니라 Unverified로 둔다. vendor 주장과 독립 성능 근거를 구분하며, 경쟁 제품의 품질·정확도 순위는 매기지 않는다.

## 1. Executive Summary

| 질문 | 판정 |
|---|---|
| Copy인가 | **No**. 독립 설계다. 이것이 독창성을 증명하지는 않는다 |
| Category가 유일한가 | **No**. rules-aware·requirements-aware·governance review는 Qodo, Cursor Bugbot, GitHub Copilot에 이미 있다 |
| Distinct product thesis | **Partial**. 개별 요소는 모두 어딘가에 있거나 DIY로 만들 수 있다. 남는 것은 조합(사람이 확정한 Decision lifecycle + repository 소유 상태 + agent 중립 + LLM 없는 재현 가능한 Evidence→Verdict + adoption baseline provenance)뿐이다 |
| 방어 가능한 차별점 | **Partial / 미증명**. 조합에 해당하는 동작은 경쟁 제품에서 Unverified이지만, 사용자가 그 차이에 비용을 지불할 가치가 있다는 근거는 없다 |
| Moat | **No**(현재) |
| 가장 큰 위험 | DIY 조합(docs + AGENTS.md/CLAUDE.md + custom linter + structural test + CI + hook)과 native review의 "good enough", 그리고 사람이 확정하는 Truth의 유지 비용 |
| 0.2.0 blocker | **No**. 새로 발견된 security·correctness·compatibility·packaging 문제가 없다 |
| T28 | 진행 가능. 이 감사에서는 시작하지 않는다 |

현재 product thesis는 **Weak / Unproven**으로 기록한다. 약하다는 뜻은 차이가 없다는 것이 아니라, 차이가 사용자 가치로 이어진다는 근거가 아직 없다는 뜻이다. 다음에 증명해야 할 것은 기능이 아니라 §11의 두 benchmark다.

## 2. What DUO Actually Is

0.1.2 + 0.2.0 main(`dd5c998`) 기준, 코드로 확인되는 동작만 적는다.

| 구성 | 실제 동작 |
|---|---|
| Truth | `.duo-project/`의 Requirement, Decision. 사람이 TTY(ID 재입력) 또는 local UI에서만 confirm·reject한다. agent는 MCP로 proposal만 만든다. Decision Lock, supersede가 있다 |
| Project Graph | tree-sitter 기반, 모든 Git 저장소 L0, Java/C#/C++/Python L1, TypeScript/JavaScript L2 |
| Index | `duoctl index`는 수동이다. MCP tool은 index하지 않고, freshness가 어긋나면 그렇게 보고한다 |
| Context Compiler | Truth + Graph에서 작업 context와 Knowledge Gap을 만든다 |
| Review | Claim → Evidence → Verdict(PASS/WARN/BLOCK/ASK). LLM 없이 결정적으로 동작한다. 선택적 semantic assist는 PASS를 최대 WARN으로만 올리고 BLOCK을 만들지 않는다 |
| Adoption Baseline | introduced 위반 → BLOCK, pre-existing → 집계 제외, pre-existing-touched → WARN |
| Integration | MCP server(9 tools), Codex·Claude Code install, Doctor, local UI |
| LLM | 선택. `openai-responses`(공식 endpoint 전용) 또는 `openai-compatible`(명시 endpoint) |
| 없는 것 | PR review, SCM merge gate, RBAC·SSO, 중앙 정책, cross-repo, auto-fix |

### 4.5 Claude Code

## 6. Distinct Product Thesis

검증 대상 문장: DUO는 사람이 확정한 engineering Decision의 lifecycle을 repository 소유 상태로 유지하고, agent·model·vendor와 독립적으로 repository 변경이 그 Decision과 일치하는지를 LLM 없이 재현 가능한 graph·evidence pipeline으로 검증하며, adoption 이전 부채와 이후 drift를 provenance로 구분하는 layer다.

| 요소 | 경쟁 제품·DIY에 있는가 | 판정 |
|---|---|---|
| A. 사람이 확정한 authority | Copilot·Bugbot의 지시 파일, Claude managed CLAUDE.md, Qodo rules도 사람이 쓰고 관리한다. 자동 학습 쪽으로 가는 흐름(Learned Rules, auto memory, rule discovery)과는 대비된다 | 단독으로는 unique 아님 |
| B. Repository 소유 상태 | AGENTS.md, CLAUDE.md, BUGBOT.md, Harness의 docs/ 모두 repository 안에 있다 | 단독으로는 unique 아님 |
| C. Decision lifecycle(confirm·lock·supersede) | decision log 관행(Codex Harness)은 있다. 상태 전이가 있는 entity는 어디서도 확인하지 못했다 | 경쟁 제품에서 Unverified |
| D. Agent·vendor 중립 | AGENTS.md 관행, Claude의 AGENTS.md 연동, Qodo의 "사람·AI agent 같은 기준" 주장이 일부 겹친다 | Partial |
| E. LLM 없는 review | linter·structural test·hook이 LLM 없이 rule을 강제한다 | 단독으로는 unique 아님 |
| F. 재현 가능한 Evidence | linter 결과도 재현 가능하다. Decision에 묶인 Evidence pointer(commit, path, symbol, range, hash, Decision ID)는 확인하지 못했다 | Partial |
| G. Adoption baseline | 확인하지 못했다. 많은 linter가 baseline 파일 관행을 갖지만 Decision 단위는 확인하지 못했다 | 경쟁 제품에서 Unverified |
| H. Introduced·pre-existing provenance | diff 기반 review가 일부 대체한다 | 경쟁 제품에서 Unverified |

결론: 각 요소가 독립적으로 unique하다고 주장하지 않는다. 남는 차별화 후보는 A~H의 **조합**이며, 특히 C·G·H가 Decision 단위로 묶인다는 점이다. 이 조합이 Truth 유지 비용을 지불할 만큼 사용자에게 가치 있다는 것은 **검증되지 않았다**. 판정: Distinct product thesis **Partial**, 강도 **Weak / Unproven**.

## 7. Defensible Differentiation

현재 경쟁 제품과 다르게 동작하는 것(공식 자료에서 같은 동작을 확인하지 못한 것):

- Decision이 상태 전이(proposal → confirm → lock → supersede)를 가진 entity이고, 전이는 사람만 일으킨다.
- 같은 repository 상태에서 Truth → Graph → Evidence → Verdict가 LLM 없이 같은 결과로 재현된다.
- 위반을 adoption baseline과 비교해 introduced, pre-existing, pre-existing-touched로 나누고 Verdict를 다르게 준다.
- 위 상태가 agent 설정이 아니라 repository에 있어 Codex와 Claude Code가 같은 MCP를 쓴다.

방어 가능성은 **Partial / 미증명**이다. 기술적으로 복제가 어렵지 않다. Qodo는 rules system에 lifecycle을 더할 수 있고, DIY 조합은 linter baseline 파일과 ADR status 필드로 상당 부분을 흉내 낼 수 있다. 방어력은 사용자가 이 차이를 실제로 원한다는 증거가 생긴 뒤에야 판단할 수 있다.

## 8. What Is Not a Moat

Differentiation(지금 다르게 동작하는 것)과 moat(복제가 어렵거나 시간이 지날수록 방어력이 커지는 것)를 분리한다. **현재 moat는 없다.**

moat가 아닌 것: code 양, test 수, CLI, MCP, tree-sitter, UI, 지원 provider, analyzer 구현량, 문서 양.

앞으로 생길 수 있는 moat 후보(지금은 없음):

- 신뢰가 쌓인 Decision 이력: 프로젝트에 확정된 Decision이 쌓일수록 다른 도구로 옮기는 비용이 커진다. 사용자가 실제로 Decision을 유지할 때만 생긴다.
- Workflow 내장: 여러 agent가 같은 Truth를 매일 참조하는 상태.
- 표준: Decision·Evidence 형식이 다른 도구에서도 읽히는 형식이 되는 경우.
- Benchmark 신뢰: §11 benchmark가 공개되고 재현되어 기준으로 쓰이는 경우.

## 9. Truth Authority Tradeoff

이 감사의 핵심 위험이다.

| 제품 | 규칙·지식이 생기는 방식 |
|---|---|
| Cursor | Learned Rules(PR feedback에서 학습) |
| Qodo | rule discovery(vendor claim) |
| Claude Code | auto memory(correction·pattern 자동 저장) |
| Codex(Harness 사례) | agent가 관리하고 갱신하는 repository docs |
| DUO | 사람의 confirm만 |

| 강점 | 약점 |
|---|---|
| 명시적 authority: 무엇이 기준인지 분명하다 | 초기 작성 비용 |
| 의도된 결정: 우연히 학습된 규칙이 아니다 | 유지 비용 |
| 재현성: 같은 Truth면 같은 Verdict | Truth가 비어 있으면(sparse) Review가 할 일이 적다 |
| 감사 가능한 이력: 언제 누가 무엇을 확정·대체했는가 | confirm 절차의 마찰 |

수동 Truth는 DUO authority의 근거이면서 동시에 가장 약한 가정(사용자가 Truth를 계속 유지한다)이다. 이를 줄이는 방향은 §19 Bet 2(후보 제안 → 사람 확정)이며, AI가 Truth를 자동 확정하는 방향은 thesis를 없애므로 택하지 않는다.

Claude memory와 DUO Truth의 차이 후보: Claude memory는 agent 효율을 위한 기억된 context이고, DUO Truth는 사람이 확정한 project authority다. 이 차이에 시장 가치가 있다는 근거는 없다.

## 10. Killer Use Cases

실제 가치가 생긴다면 여기서 생겨야 한다(검증 전 가설).

1. **기존 저장소 도입**: 이미 위반이 많은 저장소에 Decision을 확정해도 기존 부채로 막히지 않고, 새로 들어온 위반만 BLOCK한다.
2. **Agent 교체·병행**: Codex에서 Claude Code로 바꾸거나 둘을 같이 써도 같은 Decision과 같은 Verdict를 받는다.
3. **Decision 변경**: architecture 결정을 바꿀 때 이전 결정을 supersede로 남기고, 이후 위반이 현재 Decision에 묶인다.
4. **계정·network 없는 검증**: 외부 SaaS로 code나 context를 보내지 않고 core review를 돌린다.

## 11. Killer Benchmarks

설계만 한다. 이번 task에서 실행하지 않으며, DUO가 이긴다고 가정하지 않는다.

### Benchmark 1 — Legacy + New Violation

- 초기 상태: 확정된 architecture Decision 1개, 같은 Decision의 legacy 위반 1개.
- 변경: 같은 Decision을 위반하는 새 위반 1개를 추가하는 PR·변경.
- 비교 대상: A instructions-only, B Copilot review, C Cursor Bugbot, D Qodo, E Codex review, F Claude Code 설정·hooks(비교 가능한 범위), G DUO.
- 측정: (1) 새 위반 탐지, (2) legacy 위반 처리, (3) introduced·pre-existing 구분, (4) Evidence 구체성, (5) 정책·Decision provenance, (6) 반복 실행 일관성, (7) false positive, (8) setup 시간, (9) 유지 시간, (10) model·network 의존, (11) 계정 의존, (12) agent 교체 시 동작.
- 공정성: 각 도구는 공식 문서대로 가장 잘 설정한다. DIY 조합(linter baseline + CI)도 F 또는 별도 항목으로 포함한다. 결과는 원자료와 함께 공개한다.

### Benchmark 2 — Decision History(Longitudinal)

- Day 1 Decision 확정 → Day 30 coding agent 교체 → Day 60 architecture Decision 변경(supersede) → Day 90 새 위반.
- 측정: 원래 Decision 이력 보존, supersede의 명시성, 현재 authority 식별, 위반이 올바른 현재 Decision에 묶이는지, provenance, 재현성, agent·vendor 교체가 정책 상태에 주는 영향.
- 이 benchmark는 Decision Lock·supersede thesis를 직접 반증할 수 있다. ADR 문서 + git history로 같은 답을 같은 비용에 얻으면 thesis가 약해진다.

## 12. Adoption Friction

순서 없이 상위 3개.

- **초기·sparse Truth**: Truth가 비어 있으면 Review와 Context의 가치가 작다. `duoctl init` 초안이 있지만 사람이 confirm해야 한다.
- **수동 `duoctl index`**: 변경 후 index를 직접 돌려야 한다. MCP는 freshness 불일치를 보고만 한다.
- **사람만 할 수 있는 Decision confirm**: 의도된 설계이지만 마찰이다.

CI, pre-push, hook 연동은 분석만 했고 0.2.0 범위 밖이다.

## 13. Language Scalability

기존 결론을 유지한다.

- universal L2를 추구하지 않는다.
- 모든 Git 저장소 L0, Java/C#/C++/Python L1의 정확성을 넓게 유지한다.
- 깊은 semantic은 선택한 언어(현재 TypeScript/JavaScript)에만 둔다.
- SCIP·LSP·compiler index ingest는 미래 연구다. 외부 semantic index를 쓰더라도 결정적, 버전 고정, 재현 가능, local provenance 조건을 지켜야 한다. 이 조건을 못 지키면 "LLM 없이 재현 가능한 Evidence" thesis와 충돌한다.
- killer use case(§10)의 대부분은 의존 방향·경계 같은 L1 수준 관계로 탐지할 수 있다는 것이 가설이며, Benchmark 1로 확인한다.

## 14. Local-First Analysis

"local"을 다섯 의미로 나눈다.

| 의미 | DUO | Copilot | Cursor/Bugbot | Qodo | Codex | Claude Code |
|---|---|---|---|---|---|---|
| Code 실행이 local | Yes | Unverified | Unverified | Partial | Partial(local CLI·sandbox) | Yes(local agent) |
| Inference가 local | Partial(LLM 끄면 inference 없음, 켜면 provider로 나감) | Unverified | Unverified | Partial(on-prem) | Unverified | Unverified |
| Review logic이 local | Yes | Unverified | Unverified | Partial(local Pre-PR, login 필요) | Unverified | Partial(local hooks) |
| Project authority·state가 local | Yes(repository) | Partial(지시 파일) | Partial(BUGBOT.md, Team·Learned Rules는 서비스) | Partial | Partial(repository docs) | Partial(CLAUDE.md는 repository, auto memory는 사용자 홈) |
| 계정·network 불필요 | Yes(core) | Unverified | Unverified | No(login 필요 확인) | Unverified | Unverified |

DUO가 주장할 수 있는 최종 표현: "DUO core는 review logic과 project Truth·state를 local에 두고, core review에 계정과 network가 필요 없으며, LLM은 선택이다. semantic assist를 켜면 inference는 설정한 provider로 나갈 수 있다."

Qodo는 Codex plugin 사용에 login이 필요하다고 공식 자료에 적혀 있어 해당 칸만 No로 둔다.

## 15. Enterprise Readiness

현재 enterprise governance 시장을 주 target으로 **추천하지 않는다**. evidence와 일치한다.

- DUO에 RBAC, SSO, 중앙 정책, merge gate가 없다.
- Qodo가 중앙 rules, RBAC, on-prem으로 이 영역과 직접 겹친다.
- Codex는 managed configuration, managed network, telemetry, Compliance Platform을 제공한다.
- Claude Code는 최상위 managed settings, managed hooks only, inference hooks(beta)를 제공한다.

enterprise 미래를 부정하지 않지만 현재 wedge(§19 Bet 3)와 분리한다. 다만 구분은 기록한다. Codex·Claude의 governance는 "agent가 무엇을 할 수 있는가"(실행·정책), DUO는 "repository 변경이 사람이 확정한 engineering Decision과 일치하는가"(Decision compliance)다. 두 layer는 hook이나 CI에서 DUO를 실행하는 식으로 겹칠 수 있지만 같은 abstraction은 아니다.

## 16. Native Good-Enough Risk

Native substitute: Cursor Bugbot, GitHub Copilot review, OpenAI Codex review. 사용자는 이미 쓰는 platform에서 지시 파일만 추가하면 된다. 추가 설치가 없고 PR 흐름에 바로 붙는다. diff 기반이라 새 코드에 집중하므로 introduced·pre-existing 구분의 상당 부분을 자연스럽게 대체할 수 있다.

DUO가 다른 점은 PR 단계 이전·외부에서 Decision 단위 Verdict를 재현 가능하게 주는 것과 baseline 분류다. 이 차이가 "good enough"를 넘는지는 Benchmark 1로만 판단할 수 있다. 위험도: **높음**.

## 17. Direct Competitive Risk

Direct product overlap: **Qodo**. 중앙 rules, requirements context, pre-PR review, Codex plugin, RBAC, on-prem. Qodo가 rule lifecycle과 baseline을 추가하면 DUO의 조합 차이 대부분이 사라진다. DUO가 남기는 것은 계정·network 없는 core와 repository 소유 상태 정도다. 위험도: **높음**. 순위는 매기지 않는다.

Claude Code 전체를 단순 DIY로 보지 않는다. Claude Code는 coding agent이자 managed policy 제품이며, 그 hooks가 DIY guardrail의 재료가 된다.

## 18. DIY Substitute Risk

가장 강한 DIY: 구조화된 docs + AGENTS.md / CLAUDE.md + custom linter / structural test + CI + 결정적 hooks. OpenAI Harness Engineering이 이 방식이 실제 운영 가능함을 공개했고, Claude Code hooks가 agent lifecycle에서 같은 검사를 결정적으로 실행하게 해준다. 위험도: **강함**.

**"그냥 docs + instructions + linter + CI + hooks면 되지 않나?"** 현재 코드로 낼 수 있는 가장 강한 답:

1. Decision이 상태(confirm·lock·supersede)를 가진 entity라서, 현재 무엇이 유효한 결정이고 무엇이 대체됐는지를 문서 해석 없이 알 수 있다.
2. Adoption baseline이 Decision 단위로 위반을 introduced·pre-existing·pre-existing-touched로 나눠, 기존 저장소에 규칙을 들이는 비용을 낮춘다.
3. 위반이 Evidence pointer(commit, path, symbol, range, hash, Decision ID)로 특정 Decision에 묶인다.
4. 이 모든 것이 agent 설정이 아니라 repository에 있고 MCP 하나로 여러 agent에 같은 답을 준다.
5. 이를 위해 rule마다 linter를 새로 짤 필요가 없다. Decision을 Graph 관계로 표현한다.

이 답은 아직 **약하다**. DIY 조합에도 linter baseline 파일, ADR status 필드, git history가 있고, 이 다섯 가지가 그것보다 유지 비용 대비 낫다는 증거가 없다. 따라서 **Weak / Unproven Product Thesis**로 명시한다.

## 19. 12-Month Strategic Bets

최대 3개. 0.2.0 범위를 다시 열지 않으며 0.2.x 이후 검토 대상이다.

### Bet 1 — 공개·재현 가능한 decision-compliance benchmark

- Why: 차별점이 주장 수준이다. 증명하지 못하면 다른 모든 투자가 근거를 잃는다.
- Evidence: §6·§7의 조합 차이는 경쟁 제품에서 Unverified일 뿐, 우위가 확인된 것이 아니다.
- 만들지 않을 것: DUO에 유리하게 짠 시나리오, 경쟁 제품 품질 순위표, benchmark를 위한 새 기능.
- Success signal: 외부인이 재현하고, 최소 한 도구 조합 대비 DUO가 provenance·재현성에서 측정 가능한 차이를 보인다.
- Failure signal: native·Qodo·DIY가 같은 결과를 더 적은 setup·유지 비용으로 낸다(§21 Kill 1).

### Bet 2 — Truth 후보 제안 → 사람 확정

- Why: 가장 약한 가정(Truth 유지)을 직접 공략한다.
- Evidence: 경쟁 제품은 모두 자동 학습 쪽으로 간다(§9). DUO는 그 입력(architecture docs, AGENTS.md, CLAUDE.md, Cursor rules, PR review comment, issue·spec, 기존 DUO Review)을 후보 Requirement·Decision으로 바꾸고 사람이 confirm하게 할 수 있다.
- 만들지 않을 것: AI가 Truth를 자동 확정하는 경로. 그렇게 하면 human-authority thesis가 사라진다.
- Success signal: init에서 첫 유용한 Review까지 시간이 줄고, 제안 후보의 confirm 비율이 의미 있게 유지된다.
- Failure signal: 후보 대부분이 reject되거나, confirm 마찰이 줄지 않는다.

### Bet 3 — Local·agent 중립·Decision 이력 wedge의 실사용 검증

- Why: 현재 최적 사용자(§23)에게 실제 가치가 있는지 먼저 알아야 한다.
- Evidence: 계정·network 없는 core, repository 소유 Truth, 여러 agent 공용 MCP는 이미 동작한다. 사용 증거는 없다.
- 만들지 않을 것: enterprise dashboard, universal L2, auto-fix, 경쟁 기능 복제.
- Success signal: §20 신호(반복 사용, 참조되는 Decision, 수용된 drift finding)가 실제 저장소에서 관측된다.
- Failure signal: 설치 후 반복 사용이 없거나 Decision이 갱신되지 않는다.

## 20. Success Signals

telemetry를 넣지 않는다. 사용자가 선택해 공유하는 local report로만 수집한다.

- init → 첫 유용한 Review 완료
- 주간 반복 사용
- Review·Context에서 참조되는 확정 Decision 수
- 수용된 drift finding
- false positive reject 비율
- agent의 context tool 호출
- 여러 agent를 쓰는 프로젝트 수

## 21. Kill Criteria

다음 중 하나가 benchmark나 실사용으로 확인되면 thesis를 접거나 크게 줄인다.

1. Native·Qodo·DIY 조합이 Benchmark 1에서 같은 provenance와 재현성을 더 낮은 유지 비용으로 제공한다.
2. Adoption baseline이나 Decision lifecycle이 일반 docs·ADR·git history보다 실질적인 이득을 주지 않는다(Benchmark 2, 사용자 피드백).
3. Deterministic Review가 다른 도구가 놓친 actionable finding을 거의 추가하지 못한다.
4. Truth 유지 비용이 막은 drift의 가치보다 크다(Truth가 갱신되지 않고 방치됨).
5. 언어 한계(L0/L1) 때문에 killer use case의 핵심 위반 탐지 자체가 약하다.

## 22. 0.2.0 Impact

- 전략적 약점은 release blocker가 아니다. blocker는 security, correctness, compatibility, packaging만 인정한다.
- 이번 감사에서 새 blocker는 발견되지 않았다.
- 0.2.0 기능 범위는 다시 열지 않는다. benchmark·Truth 후보 제안은 0.2.x 이후 검토한다.
- **T28 Release Hardening은 진행할 수 있다.** 이 감사에서는 시작하지 않는다.
