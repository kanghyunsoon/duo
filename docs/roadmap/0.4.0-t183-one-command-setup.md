# One-command setup (T183)

Related: [#3](https://github.com/kanghyunsoon/duo/issues/3), Jira S15P31A106-318 (this work), -319 (AI-2, agents),
-320 (FE, wording), -252 (investigation, [report](https://github.com/kanghyunsoon/duo/issues/3#issuecomment-6431885164)).
Decision: [H-102](../conflicts.md).

`duoctl setup` runs the first-time setup of an existing Git repository as one flow. It reuses the
services that `init`, `install` and `doctor` already call, and adds no new domain contract. The `init`
and `install` commands keep their behavior, options and exit codes for scripts and advanced use.

## Flow

1. **Preflight (read-only).** `planInit`, `getAdoptionBaselineStatus` and every agent step's `plan()`.
2. **Human choices.** The dirty-tree baseline policy (when a baseline is still needed), then the Truth
   questions. `--yes` answers neither; `--answers -` and `--baseline-policy` work as in `init`.
3. **One plan, one confirmation.** Setup lists the Truth files it will create with these answers, the
   index and baseline actions, and every agent step's files, then asks once (`Apply this setup? [y/N]`).
   Non-interactive runs need `--yes`; without it setup exits 6 with `status: "confirmation-required"`.
4. **Apply.** `applyInitPlan` → `indexRepository` (skipped when current) → `captureAdoptionBaseline`
   (HEAD_BASELINE when the tree is dirty) → each agent step's `apply()`.
5. **Summary.** The read-only `projectDoctor` result, what is left outside DUO (from the agent steps),
   and a reminder that DUO does not commit.

Nothing is written before the confirmation. When nothing needs to be written (Truth and baseline exist and
every agent step is a no-op), setup asks nothing; it only updates a stale index, which is regenerable
state, as `duoctl index` does. Metrics are appended only once `project.yaml` exists, so a refusal or a
cancellation in a new repository leaves no file behind.

## Refusals and recovery

| Case | Setup | Exit | Writes |
|---|---|---|---|
| Not a Git repository | `GIT_REPOSITORY_REQUIRED`, `status: "blocked"` | 1 | 0 |
| No initial commit while a baseline is needed (C214) | `ADOPTION_HEAD_REQUIRED` before any question | 6 | 0 |
| `.duo-project` without `project.yaml` | `INIT_REPAIR_REQUIRED`; `duoctl setup --repair` adds only missing files | 6 | 0 |
| Conflicting `.duo-project` (file, symlink, unreadable Truth) | the `planInit` blockers, `blocked` | 1 | 0 |
| Unreadable adoption baseline | `ADOPTION_BASELINE_EXISTS`; setup never replaces it | 1 | 0 |
| Agent step blocker (conflict, launcher) | the step's diagnostics, `blocked`, before any question | 6 | 0 |
| Dirty tree, no policy / `abort` | `ADOPTION_DIRTY_POLICY_REQUIRED` / `aborted` | 6 | 0 |
| Non-interactive without `--yes` | `confirmation-required` | 6 | 0 |
| The person declines | `cancelled` | 1 | 0 |
| A step fails after the confirmation | stops; keeps everything before it; `resume: "duoctl setup"` | 1 | kept |

After the confirmation, a failure never deletes Project Truth (#3 F6). `applyInitPlan` itself removes what
it created when it fails (`INIT_APPLY_FAILED`); index and baseline are regenerable or explicit; an agent
step must undo its own partial writes (H-94). Running setup again continues from the first unfinished
step: existing Truth and baseline are kept, a current index is skipped, a connected agent is a no-op.

## Agent step interface (for -319)

`apps/cli/src/commands/setup.ts` exports `SetupAgentStep`:

```ts
interface SetupAgentStep {
  readonly id: string;                                    // "codex", "claude-code"
  plan(context: SetupStepContext): Promise<SetupStepPlan>; // read-only; before the confirmation
  apply(context: SetupStepContext, plan: SetupStepPlan): Promise<SetupStepResult>; // after Truth, index, baseline
}
interface SetupStepContext { readonly env: Env; readonly truthPlanned: boolean }
interface SetupStepPlan { willCreate; willModify; blockers: Diagnostic[]; noop: boolean; lines: string[]; detail?: unknown }
interface SetupStepResult { ok: boolean; diagnostics; lines: string[]; remaining: string[]; detail?: unknown }
```

`setupCommand(env, options, agentSteps)` takes the steps; `cli.ts` passes none today, so setup does not
connect an agent yet and `doctor`'s next action names `duoctl install codex` / `claude-code`. To connect
agents, -319:

- builds one step per selected or detected agent around `planAgentIntegration` /
  `applyAgentIntegration` / `verifyAgentIntegration`, and passes them from the `setup` case in `cli.ts`;
- when `truthPlanned` is true, plans as if initialized (the -252 `assumeInitialized` planning option, an
  integration-package change owned by -319) so that conflicts and launcher problems become `blockers`
  before the confirmation instead of `AGENT_NOT_INITIALIZED`;
- puts the plan lines (`renderPlan` of `install`) in `lines`, the AgentIntegrationPlan in `detail`;
- returns the trust and approval step (Codex project trust, Claude Code `duo-director` approval) in
  `remaining`; setup prints it under "Left for you outside DUO" and never performs it;
- maps a failed verification to `ok: false`. Setup then stops with the resume command; the agent files
  stay as `applyAgentIntegration` left them (H-94).

## Wording (for -320)

Human output uses the `setup.*` keys in `apps/cli/src/messages.ts` (en, ko) and reuses `init.*`
(questions, dirty-tree choice, step labels) and `doctor.*` (summary). Step lines use the same
`<label> <status> · <detail>` format as `init`. Prompts go to stderr, so `--json` stdout stays one
envelope. -320 can change wording, order of the plan lines and the confirmation text without changing
the `--json` result.

## JSON result

`duo.cli.setup/1` envelope; `result` is `{ status, steps: { repository, truth, index, baseline, agents },
plan?, apply?, index?, baseline?, agents?, resume?, remaining, doctor? }`. `status` is one of `set-up`,
`unchanged`, `blocked`, `action-required`, `confirmation-required`, `cancelled`, `failed`. `plan` holds
the init plan fields that `init --json` shows, plus `baseline: { required, policy }` and the agent steps'
plans. Exit 0 after a successful setup unless the closing doctor reports an error check (6).

## Verification

`apps/cli/src/commands/setup.test.ts` (in-process, scripted terminal; every refusal compares a hash
snapshot of the whole repository outside `.git`): outside Git, unborn HEAD before any prompt, dirty
tree (missing policy, abort, prompt choice, head), partial and conflicting `.duo-project`, non-interactive
without `--yes`, questions then exactly one confirmation, cancel, apply with planned file count equal to
created files, rerun with no prompt and unchanged Truth and user files (including an existing
`.codex/config.toml` and `AGENTS.md`), resume after an `init` stopped at the baseline (C214), agent step
blocker before any prompt, agent step failure after the confirmation keeping Truth with the resume
command, and the rerun completing with one confirmation. Existing `init`, `install` and `doctor`
suites run unchanged.
