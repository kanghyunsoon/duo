## 3. Graph의 CALLS·IMPORTS 계약

공통: CALLS는 Symbol(호출을 감싼 가장 안쪽 symbol) → Symbol, **resolution이 `exact`일 때만** edge. module 수준 호출(감싼 symbol 없음)은 edge 없음(`exactWithoutSourceSymbol`). edge metadata는 `{provenance: "static", resolution: "exact", callSites: <개수>, declarationOnly}`이고 **호출 위치는 edge에 없다.** IMPORTS는 File → File, 해석된 repository 파일일 때만 edge, metadata `{resolution, kinds, typeOnly, declarationOnly, extensionSubstituted}`, **import 문 위치는 edge에 없다.** ambiguous·unresolved·external은 edge 없음(진단 `CALL_AMBIGUOUS`, `MODULE_UNRESOLVED`, `MODULE_AMBIGUOUS`).

위치가 남는 곳: 파일별 `SourceAnalysis`(analysis cache, `moduleReferences[].location`, `callSites[].location`, `calleeText`, `calleePath`, `enclosingSymbol`)와 index state의 `FileResolution`(`modules[]`, `calls[]`: `SourceAnalysis`의 같은 순서, 각 `status`·`reason`·`target`). 둘을 순서대로 맞추면 "현재 내용의 이 call site·import 문 → 이 대상"을 위치와 함께 복원할 수 있다. Graph store(`graph_edges`)에는 없다.

| Language | CALLS (`callResolution`) | 언제 exact | IMPORTS | 해석 기준 |
|---|---|---|---|---|
| TypeScript / JavaScript | partial(`module-bindings`) | import binding(alias 포함), re-export chain(깊이 제한), `this.method()`(instance member), 정적 `Class.method()`, `new Class()`. 인스턴스 변수의 method(`db.run()`)는 `receiver-type-unknown`으로 edge 없음. type-only binding은 `type-only-binding` | resolved(TypeScript Compiler API: tsconfig/jsconfig, paths, exports) | `typeOnly`·`kinds`(import, export-from, dynamic-import, require) 기록. external package는 edge 없음 |
| Python | partial(`same-file-functions`) | 같은 module의 유일한 top-level 함수에 대한 bare call만. 다른 module 함수 호출은 edge 없음 | partial: 상대 import, 발견된 source root 아래 absolute module. 여러 root면 ambiguous | stdlib·설치 package는 external |
| C++ | partial(`same-file-functions`) | 자유 함수 안의 bare call이 같은 파일의 유일한 함수일 때만. member·overload·template·macro는 추측 안 함 | partial: `#include "…"`가 옆 파일일 때만 | `<…>`는 system, include path(-I) 해석 없음 |
| Java | 없음(`none`, syntactic call site만) | 없음 | syntactic(쓰인 그대로, 파일 edge 없음) | package 이름이며 파일 경로가 아님 |
| C# | 없음(`none`) | 없음 | syntactic(`using`, 파일 edge 없음) | namespace 이름 |
| 그 밖 | 없음 | 없음 | 없음 | L0 |

실측(TS fixture, 2026-10-06): `new LegacyDb()`를 담은 `ReportService.build`, alias import(`import { LegacyDb as L }`), barrel re-export(`import { LegacyDb } from "../db"`, `db/index.ts`가 `export { LegacyDb } from "./legacy-db"`)가 모두 `LegacyDb`로 가는 exact CALLS를 만들었다. `.run()` 인스턴스 호출과 type-only import는 CALLS가 없다. IMPORTS는 `legacy-db.ts`로 `report-service.ts`, `alias-service.ts`, `type-only.ts`(`typeOnly: true`), `db/index.ts`(`export-from`)가 들어오고, barrel 경유 파일은 `db/index.ts`로만 간다. `duoctl impact LegacyDb.run`은 호출자가 없다고만 보이고 "instance call은 해석하지 않음" limitation을 붙이지 않았다(§14 위험).

## 4. "현재 관계"와 "새 관계"

| evidence 후보 | 있나 | 무엇을 증명하나 |
|---|---|---|
| Git hunk(review는 `-U0`, `-M`) | 있음 | new-side의 바뀐 줄 범위. 줄이 "추가됐다"와 "고쳐졌다"를 구분하지 않는다(new-side range) |
| 현재 `SourceAnalysis`의 call site·import 문 위치 | 있음(analysis cache, 또는 바뀐 파일을 review 때 다시 분석) | 지금 그 줄에 그 call·import가 있다 |
| 현재 exact CALLS·IMPORTS(`FileResolution` + Graph) | 있음(index가 WORKTREE와 같을 때) | 지금 그 call·import가 이 대상으로 정확히 해석된다 |
| HEAD 쪽 source 분석 | 일부: adoption의 HEAD 평가기가 바뀐 파일의 HEAD blob을 analyzer로 다시 분석하지만 **symbol만** 쓰고 module·call resolution은 하지 않는다 | 이전에 그 이름의 symbol이 있었다 |
| HEAD 쪽 관계(이전 exact CALLS·IMPORTS) | **없음**. 이전 Graph·이전 resolution을 보관하지 않고, 다시 계산하려면 HEAD tree 기준 module resolution(tsconfig, 파일 집합)과 export chain을 다시 돌려야 한다 | — |
| Adoption Baseline | 있음(violation key 집합). 지금은 relation rule이 없다 | adoption 시점에 그 위반이 있었는지 |

결론: **"이번 변경이 이 관계를 새로 만들었다"는 지금 evidence로 결정적으로 증명할 수 없다.** 증명할 수 있는 것은 "이번 diff가 바꾼 줄에 있는 call site·import 문이 지금 금지 대상으로 정확히 해석된다"이다. 이 둘을 같은 것으로 부르지 않는다. 예를 들어 기존 `legacy.run(a)`를 `legacy.run(b)`로 고친 줄은 바뀐 줄이지만 관계는 새것이 아니다.

## 8. Adoption provenance

- violation key 후보(줄 번호 없음, 위치 이동에 안정): `violationKey("decision-forbids-import", D-id, "import:" + fromFileNodeId + "->" + toFileNodeId)`, `violationKey("decision-forbids-call", D-id, "call:" + sourceSymbolNodeId + "->" + targetSymbolNodeId)`. 같은 쌍의 여러 call site·import 문은 한 위반이다.
- adoption 이전부터 있던 관계: baseline에 key가 있으면 `pre-existing`·`pre-existing-touched`, BLOCK 안 함.
- adoption 이후 생긴 관계: baseline에 없으므로 `introduced`. 이번 diff가 만들지 않았어도 그 줄을 바꾸면 그렇게 표시된다. 이것이 C240 용어 문제와 같은 종류다. claim 문구는 "introduced"가 아니라 "바뀐 줄의 금지 관계(adoption baseline에 없음)"로 쓴다.
- baseline 계산: HEAD가 깨끗하면 현재 Graph의 IMPORTS·CALLS가 곧 HEAD의 관계다. 바뀐 파일이 있는 adoption은 그 파일의 HEAD 관계를 다시 해석하지 않으므로 limitation(`head-relations-approximated`)을 남긴다(declared reference와 같은 방식).
- **기존 baseline(T36 이전)**: relation rule을 평가하지 않았으므로 relation 위반이 "baseline에 없다"는 것이 "adoption 이후 생겼다"는 뜻이 아니다. 이 경우 `unverified-at-adoption`(경고, BLOCK 아님)으로 둬야 한다. baseline에 평가한 rule 목록(또는 format version)을 기록해 구분한다.

## 11. 제품 가치

기술적 가능성과 제품 가치를 나눈다.

- **기술적으로**: A′ IMPORTS는 지금 데이터로 결정적으로 구현 가능하다. CALLS는 TS의 일부 호출만 exact다.
- **대체재**: TS의 import 금지는 ESLint `no-restricted-imports`·dependency-cruiser, Python은 import-linter, Java는 ArchUnit이 더 깊게 한다. 작은 grep·script도 대부분의 경우를 덮는다(T31·T32 결론과 같은 구조).
- **DUO만의 이점**: (1) 규칙이 사람이 확정한 Decision으로 Truth에 있고 agent가 H-71로 제안·사람이 Informed Confirm으로 확정한다(T35 흐름과 직접 연결, YAML·lint 설정 작성 없음). (2) tsconfig paths·alias·re-export를 resolver가 이미 해석한다. (3) adoption provenance로 기존 위반을 면책. (4) 언어가 섞인 저장소에서 같은 Decision 형식.
- **기대 위험**: 언어별 exact 범위가 좁다. Java·C#에서는 UNKNOWN만, TS calls는 인스턴스 호출을 못 잡는다. "사용 금지"라는 이름이 주는 기대와 실제 보장이 다르면 S1과 같은 실망이 반복된다.
- **판단**: IMPORTS(S1-C)는 T35의 "agent가 architecture Decision을 제안하고 사람이 확정" 흐름을 실제로 완성하는 가장 작은 조각이라 가치가 있다. CALLS(S1-B)는 범위가 좁아 기대를 깨기 쉽고, imports로 대부분 대신할 수 있으므로 지금은 보류한다. External Validation이 진행 중이므로 이 판단은 그 evidence로 다시 볼 수 있다.

## 12. H-72 초안 (권장: IMPORTS만, 승인 전 main에 기록하지 않음)

> 승인된 최종 H-72(2026-10-06, `docs/conflicts.md`)는 이 초안과 다르다: type-only import도 대상이고, 해석되지 않은 import에 텍스트 유사성으로 UNKNOWN·WARN을 만들지 않고 limitation만 보이며, 어떤 파일과도 맞지 않는 패턴은 아무것도 보고하지 않는다. 기존 baseline은 `evaluatedRules`와 Decision `confirmed_at`으로 판정한다. 아래는 T36 당시 기록이다.

> | H-72 | (승인일) | T36 Forbidden relation(imports) on `next`. T35 S1의 capability gap("다른 코드가 대상을 새로 사용하는 변경 금지")에서 import 부분만 결정적으로 표현한다. "새 관계"는 지금 evidence로 증명할 수 없으므로 주장하지 않는다. 결정: (1) Decision `forbids`에 `imported_paths`(repository path pattern, `compileRepoPattern`)를 추가한다. 기존 `forbids.symbols`의 의미(바뀐 symbol의 qualified name)는 바꾸지 않고 "사용 금지"로 재해석하지 않는다. `called_symbols`는 이번 범위가 아니다. (2) 새 review rule: diff가 바꾼 new-side 줄에 있는 import 문(TS·JS import·export-from·require·dynamic import, Python import, C++ quoted include)이 지금 index에서 금지 경로의 repository 파일로 해석되면 CONFLICT `forbidden-import`, `enforcement: block`이면 BLOCK 후보. 근거는 Git hunk, 현재 `SourceAnalysis`의 import 위치, index의 module resolution이며 claim은 "바뀐 줄의 금지 import"로 말하고 "새로 추가됨"이라 주장하지 않는다. type-only import는 conflict가 아니다. (3) 해석되지 않거나(unresolved·ambiguous·syntactic) 분석할 수 없는 언어의 바뀐 import 중 쓰인 이름이 금지 경로와 그럴듯하게 맞는 것은 UNKNOWN drift(WARN)이며 BLOCK하지 않는다. 텍스트·LLM은 BLOCK 근거가 아니다(ADR-007). 분석할 수 없음을 위반 없음으로 보고하지 않고 limitation을 함께 보인다. (4) 패턴이 현재 어떤 파일과도 맞지 않으면 진단과 UNKNOWN(WARN)으로 알린다. (5) violation key는 `decision-forbids-import` + Decision + `import:<from file>-><to file>`이다. adoption 시점에 있던 관계는 BLOCK하지 않고, relation rule을 평가하지 않은 기존 Adoption Baseline에서는 `unverified-at-adoption`(BLOCK 아님)이다. (6) 새 field는 값이 있을 때만 lock digest에 들어가 기존 Decision의 lock을 바꾸지 않는다. (7) MCP `duo_propose_decision`에 `forbids.imported_paths`를 추가한다(H-71 확장, tool 수 9개 그대로). Informed Confirm이 그대로 보인다. (8) 언어 지원: TS·JS resolved, Python·C++ partial, Java·C#·그 밖은 UNKNOWN 또는 limitation. (9) `next`에만 적용, main·npm·External Validation 영향 없음, promotion은 별도 결정 | core schema·digest, director review·adoption, integration MCP, docs |

## 14. 남은 위험

- A′는 "새 관계"가 아니라 "바뀐 줄의 관계"다. 기존 import 줄을 고치기만 해도(예: binding 추가) adoption 이후 관계면 BLOCK된다.
- barrel·re-export 경유 import는 barrel 경로를 따로 금지하지 않으면 놓친다.
- `duoctl impact`·Context가 "인스턴스 호출은 해석하지 않음"을 해당 symbol 조회에 limitation으로 붙이지 않는다(실측). 관계 부재가 "관계 없음"으로 읽힐 수 있다(기존 동작, 이번 범위 밖).
- 기존 baseline 구분(평가 rule 목록)이 없으면 모든 기존 저장소에서 relation 위반이 `introduced`로 BLOCK될 수 있다. 구현 시 필수.
- lock digest 호환을 놓치면 모든 confirmed Decision이 lock mismatch가 된다. 구현 시 필수 test.
