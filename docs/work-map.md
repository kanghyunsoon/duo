# Work map

`duoctl ui --open` serves `/work` from the existing local UI server. It draws work items beside the Project Graph with React Flow. People can add an item in the UI; a successful `duo_get_context` call also records the agent name and the first line of the task in local runtime state. A `duo_review_changes` call updates that activity when its `task` argument is present. No extra MCP call or LLM call is made for the map. Completion is explicit in the UI; elapsed time alone does not mark work complete.

Task names and agent labels pass through the same secret redaction as Context Packets before they are stored (#84): known credential formats such as `sk-…`, `ghp_…`, AWS access keys, JWTs and PEM private keys become `[REDACTED]`. An MCP task's first line is redacted in full before it is cut to 200 characters. The task key still hashes the unredacted task text, so session matching is unchanged. When the map reads a task file written before this change, it rewrites it under the task lock with redacted labels, keeping IDs, task keys and status; `cache/work-map.json` is regenerated from the redacted tasks on the next map load. Redaction covers the listed formats only. Other secret-like text in a task line is stored as written.

The source of truth stays with DUO. The UI reads existing Issue, Requirement, Decision, File, Symbol and Test nodes and existing graph edges. It creates only a task-to-seed link: `TARGETS` for an explicit Issue ID or `RELATED` for a Context seed. A Context result is a candidate, not proof that the agent changed or owns a file. In a shared checkout, Git changes cannot be assigned to an agent by this map.

`.duo-project/runtime/work-tasks.json` is a compact v2 object containing task records. Existing v1 arrays are migrated on read under a short cross-process lock, retaining their UUIDs and marking their identity as legacy. All task writes use that lock so parallel MCP connections cannot overwrite each other's records. New MCP connections receive a DUO session UUID. An MCP task key is the SHA-256 of its session UUID and full task text after converting CRLF/CR to LF and trimming only the outer whitespace; internal whitespace is preserved. An active call with the same key updates its existing UUID, while a completed task restarted with the same text receives a new UUID. Resolving a target later adds target metadata to the matching active task; target equality alone never merges tasks. Calls without a DUO session do not record activity. Old records without a task key keep their IDs and are never merged by display name. Activity write failures are logged without changing the MCP response, and MCP activity lock waits are limited to 100 ms per write. Malformed task data is left intact for diagnosis. Connection close marks its active tasks disconnected; only an explicit UI action marks a task complete. The task file is bounded by 128 KiB: old completed records, then disconnected records, are removed as needed; active records are never silently discarded. `.duo-project/cache/work-map.json` is a regenerable compact projection with node IDs, short labels, edges, index status and graph revision. It contains no SDD text, source code or diff. The initial map is bounded to 120 nodes, including at most 60 task nodes so the selected task has room for DUO relations; expansion to depth 1–3 is fetched separately and held only in browser memory. Shared DUO nodes appear once. Both JSON files are local runtime/cache data, not Project Truth.

`duo_get_context` and `duo_review_changes` advertise `readOnlyHint: false` because each appends a record to `.duo-project/runtime/metrics.jsonl`, and with a DUO session they also write regenerable activity to `.duo-project/runtime/work-tasks.json`. These writes do not change Project Truth, source code or the index. Their `idempotentHint` is false because repeated calls can append metrics and update activity. Their `destructiveHint` is true because the bounded task file can prune old completed or disconnected activity records when full; neither tool changes project sources or confirmed direction. Under lock contention, `withTaskLock` uses synchronous `Atomics.wait`, which temporarily blocks the server event loop; MCP activity writes limit lock waiting to 100 ms per write, and a lock timeout leaves the successful MCP result intact.

The map identifies the current Git worktree by a hash of its canonical root and labels it with the branch name. Changed files attach to the worktree, not an agent task. A review call can attach a small digest, verdict and claim count to the exact active task ID in its DUO session, including an unresolved free-form task. This is an observed activity summary, not a persisted formal Review Record. The UI currently shows one worktree per local server.

Without an explicit selection, the map focuses the most recently updated active task. Large trees open at a readable zoom around that task; the minimap provides an overview. Browser pan and zoom are retained across live map refreshes. Index status is reused when only task runtime data changes, and recalculated when source, Project Truth or the indexed graph changes.

The server watches the repository and sends small SSE notifications from `/api/work-events`. It also checks the task file's metadata every two seconds to catch atomic replacements missed by the Windows watcher. On reconnect, page visibility restoration and every 60 seconds while visible, the browser checks `/api/work-revision`; event-driven checks are coalesced to at most one per 1.5 seconds. It reloads the full map only when its revision differs, with one map request in flight at a time. The existing graph remains visible while a new map loads. The revision covers task data, the indexed graph and Git working-tree metadata, so it can recover a missed file event without repeatedly transferring the graph. A file change can make the index stale; the page labels that state and keeps the last indexed relations until `duoctl index` runs. The server and watcher run only while `duoctl ui` is open.

The map does not infer an agent's coding phase or assign edits to a task. Its DUO session identifies an MCP connection rather than the host application's conversation; restarting the connection creates a new session. UI-created work keeps its own manual UUID.
