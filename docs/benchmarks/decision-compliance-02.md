# Decision Compliance Benchmark 2: Adoption Provenance + Supersession

Date: 2026-10-04 · DUO under test: published `@duo-director/cli@0.2.0` · Fixture: `decision-compliance-02/1` (TypeScript) · Method: [H-64](../conflicts.md#human-결정-기록), same as [Benchmark 1](decision-compliance-01.md)

A fixed timeline with raw evidence. No overall score or winner; this is not a performance benchmark.

## 1. Question

When the timeline gets longer, does a workflow keep two meanings?

- **Adoption provenance**: a violation that entered after adoption is not legacy debt, even when a later diff base already contains it.
- **Decision authority**: after a person supersedes D-001 with D-002, only the current decision applies, and the history stays traceable.

## 2. Why Benchmark 1 was insufficient

[Benchmark 1](decision-compliance-01.md) showed that DUO, a 57-line DIY gate and Codex review all classified the fixed violation the same way. Detection of one fixed rule is therefore not evidence for DUO. In Benchmark 1 the adoption baseline and the diff base were the same commit, so "existed at adoption" and "existed before this change" could not be told apart. Benchmark 2 tests the remaining longitudinal claims, not detection.

## 3. What this benchmark does NOT prove

One small fixture, one language, one rule per decision and one machine do not show overall code quality, general accuracy, behavior across languages, repositories or models, overall superiority of any tool, or enterprise suitability. Every count is "in this fixture". TypeScript is DUO's deepest analysis level and was chosen so analyzer limits do not mix with the thesis.

| Step | Branch | SHA | Change |

| T1 | `t1-late-violation` | `a1f5892` | `LateSessionStore` added; in the story it was merged without a decision review |

Full SHAs are in the manifest. The policy texts (same intent for every workflow):

> **D-001** (T0): authentication must keep no server-side session state. Code must not add or change any class, function or other symbol whose name contains `SessionStore`. Session stores that already existed when this decision was adopted are known legacy debt: when a change touches one, report it, but do not block the change for it. A change that adds a new symbol whose name contains `SessionStore` violates the decision and must be blocked.
>
> **D-002** (T3) supersedes D-001: session stores are no longer the forbidden pattern. Code must not add or change any class, function or other symbol whose name contains `GlobalAuthCache`. There was no GlobalAuthCache code when D-002 was adopted, so every GlobalAuthCache symbol is a violation: a change that adds one must be blocked.

## 5. Scenario A: post-adoption debt

Review range T1..T2. `LateSessionStore` exists at the diff base (T1) but did not exist at adoption (T0). A diff-base view sees touched legacy; an adoption view sees a violation that is not legacy debt. The intent says only debt known at adoption is exempt.

## 6. Scenario B: supersession

Review range T3..T4, after D-002 became current. Touching `MemorySessionStore` is no longer a violation (D-001 is superseded); the new `GlobalAuthCache` violates D-002 and must be blocked.

Both decisions were confirmed with the published CLI's interactive `duoctl decision confirm` (Git user `benchmark-maintainer`). For D-002 the person wrote a proposed YAML Decision with `supersedes: D-001` and confirmed it; DUO then set D-001 to `state: superseded`, `superseded_by: D-002` (D-001's lock digest did not change, since those two fields are outside it). The generator replays both resulting files byte for byte. The public lifecycle covered the scenario; nothing had to be reduced.

## 7. DUO method

[run.mjs](../../bench/decision-compliance-02/run.mjs) installs the registry package into a temporary prefix with an empty npm config, generates the timeline, runs `duoctl init` once at T0, then for each range checks out the head branch, runs `duoctl index` and `duoctl review --from <base> --to <head> --json` 10 times, plus `--fail-on block` once and `duoctl trace D-001/D-002 --json` at T4. Repeatability uses Benchmark 1's [canonical projection](../../bench/decision-compliance/canonical.mjs) unchanged: an audit of the Scenario B output found no lifecycle field beyond what the projection already keeps (claims with their Decision, Evidence records with Decision file ranges and hashes).

## 9. Codex method (reviewer with native docs)

The fixture also holds the decision docs a team could keep for an AI reviewer: `AGENTS.md` (and `CLAUDE.md`) as the current policy map, `docs/decisions/D-001.md` and `D-002.md` as history, and `docs/adoption.md` with the adoption commit and the known legacy debt. These files are inert; the results below are the reviewer's. [external.mjs](../../bench/decision-compliance-02/external.mjs) checks out the reviewed commit (as in a pull-request review) and runs `codex review --commit <SHA> -c model=gpt-5.5` (OpenAI Codex v0.147.0, read-only sandbox, ChatGPT sign-in, through a local OpenCodex proxy; the client reported `model: gpt-5.5`, `provider: openai`, and the serving model was not independently verified). `codex review --commit` takes no custom instructions.

Harness correction: the first four Scenario A runs had `main` (T4) checked out while reviewing T2, so the working tree held the later D-002 docs; two of them applied D-002 to T2. They were stopped, kept in [codex-invalid-harness/](../../bench/decision-compliance-02/evidence/codex-invalid-harness/) and excluded, and every Codex run was repeated with the reviewed commit checked out. The same mistake affected Benchmark 1's control-only Codex runs; that document now says so.

Other tools: Claude Code NOT RUN (not signed in; the proxy launch failed with "OAuth session expired", see [Benchmark 1 evidence](../../bench/decision-compliance/evidence/claude-code/not-run.json)). GitHub Copilot code review, Cursor Bugbot, Qodo: NOT RUN (no account or client on the benchmark machine).

## 10. Metrics

## 16. Limitations

- One rule per decision, one supersession, one language, one machine; Codex runs were 5 and 3 per range.
- The DIY gates and the decision docs were written knowing the fixture, so they are a lower bound on bespoke cost, not a general tool. Cost at many decisions, many rule kinds (paths, dependencies), several languages or several teams was not measured.
- The Codex docs were written once, correctly. The benchmark did not test docs that drift from reality, which hand-kept records can do and which DUO's generated adoption record and lock avoid by construction; that is a hypothesis here, not a result.
- Codex went through a local proxy; the serving model was not independently verified.
- DUO's `introduced` label for post-adoption debt that a change touched (Scenario A) is accurate to DUO's definition (not in the adoption baseline) but reads as "this change added it"; the output does not say the violation entered at T1.

## 17. Interpretation

- **Adoption baseline vs diff base.** The difference is real: the diff-base gate (DIY-0) exempted `LateSessionStore`, and DUO did not. But a persisted adoption list closes the gap with 54 lines of code and a 7-line generated state file (DIY-1), and Codex closed it 5/5 when a person had written the adoption record.
- **Supersession.** DUO applied only the current decision, kept the history and exposed the link through `trace`, all deterministically. A 73-line gate with a 16-line hand-edited registry did the same, and its output names the current decision more directly than DUO's review output. Codex with hand-kept docs applied the current decision 5/5.
- **Controls.** Every DIY level and Codex passed both valid changes; DUO returned WARN on both because of the `missing-intent` gap (C239), with exit 0 under `--fail-on block`.
- **What only DUO did here:** enforced human-only confirmation of each decision, wrote the supersession edit and the adoption record itself, attached content hashes to every piece of evidence, and needed no account, network, model or custom code. Whether these outweigh its setup and the WARN friction was not measured.

## 18. Falsification outcome (criteria fixed before the runs)

| Criterion | Outcome |
|---|---|
| A. A simple diff-base DIY handles post-adoption provenance | Not met: DIY-0 exempted the post-adoption debt |
| B. A persistent-baseline DIY matches DUO with little code and state | **Met**: DIY-1, 54 code lines + 7-line state, same Scenario A result |
| C. A supersession DIY stays small and clear | **Met**: DIY-2, 73 code lines + 16-line registry, same Scenario A and B results, with validation |
| D. Codex with versioned docs judges post-adoption debt and the current decision correctly, repeatedly | **Met**: 5/5 in A, 5/5 in B, 0 false findings in 6 control runs (with hand-kept docs) |
| E. DUO exempts the post-adoption violation as pre-existing | Not met |
| F. DUO applies the superseded D-001 as current | Not met |
| G. DUO's lifecycle and evidence add little to interpreting the result | Partially met: the review never mentions the superseded decision and labels post-adoption debt `introduced`; current authority is read from the cited D-002 file or from `trace` |

## 19. Product-thesis checkpoint

**C. Thesis materially weakened.** In this fixture, bespoke code (54–73 lines plus small JSON state) and a native AI reviewer with hand-kept docs both reproduced DUO's longitudinal results: adoption provenance across a later diff base and current-versus-superseded authority. DUO's results were correct and repeatable, and it was the only workflow that enforced human confirmation, generated its own adoption and supersession records and hashed its evidence, but none of these produced a different decision in this benchmark. The claims that could still separate DUO (many decisions and rule kinds, several languages, records that drift when kept by hand, cost of maintaining bespoke gates over time) are untested. Under the T32 rule, the next step is a product thesis review before new features, contributor work or distribution.
