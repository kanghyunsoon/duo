# Decision Compliance Benchmark 1: Legacy + New Violation

Date: 2026-10-04 · DUO under test: published `@duo-director/cli@0.2.0` · Fixture: `decision-compliance-01/1` (TypeScript)

This is a fixed, reproducible fixture with raw evidence. It is not a performance benchmark (speed, resources and Context size are in [performance-benchmark.md](../performance-benchmark.md)), and it has no overall score or winner.

## 1. Question

A repository already has architectural debt, and a coding-agent change adds another violation of the same engineering decision. Can a workflow tell apart:

- a violation that was already there and is not touched,
- a violation that was already there and is touched,
- a violation the change introduces,
- a valid change that has nothing to do with the decision,

and tie the actionable result back to the decision and to code locations?

## 2. Why this benchmark exists

DUO's thesis is that a human-confirmed Decision lifecycle, an adoption baseline and deterministic evidence add value over instruction files, native AI review and purpose-built checks. The [survivability audit](../roadmap/0.2.0-survivability-audit.md) rated that thesis as unproven. This benchmark tests one part of it on purpose so that it can fail: it includes a bespoke deterministic script and a native AI review as controls.

## 3. What it does NOT prove

One fixture with one rule does not prove or measure:

- overall code quality or general bug-detection accuracy,
- every architecture rule, language, repository or model,
- that any tool is better or worse overall,
- enterprise suitability,
- false-positive rates: every count below is "in this fixture".

TypeScript was chosen because it is DUO's deepest analysis level (L2), so analyzer limits do not mix with the thesis. It does not mean DUO behaves the same in other languages.

## 4. Fixed policy

Every workflow received the same human intent, each in its own native form:

> Decision D-001, stateless authentication: authentication must keep no server-side session state. Code must not add or change any class, function or other symbol whose name contains `SessionStore`. Session stores that already existed when this decision was adopted are known legacy debt: when a change touches one, report it, but do not block the change for it. A change that adds a new symbol whose name contains `SessionStore` violates the decision and must be blocked.

| Workflow | Native form of the same intent |
|---|---|
| DUO | Decision `.duo-project/decisions/D-001.yaml`: `forbids.symbols: ["*SessionStore*"]`, `enforcement: block`, confirmed by a person |
| Instruction files (AI review) | the sentence above in `AGENTS.md` and `CLAUDE.md` |
| DIY gate | the rule hard-coded in a script |

| change (branch `main`) | `f062976dc4a4edbe89a9de372bdd44a38120b54e` | D, E, F |
| control-only (branch `control-only`) | `b9beaa78b5d0171cdc09de4c123b9364a8120fa4` | F only |

| Role | Id | File and symbol |
|---|---|---|
| legacy, untouched | A | `src/legacy/memory-session-store.ts` `MemorySessionStore` |
| legacy, touched | B (baseline) / E (change: one line inside `save`) | `src/legacy/cookie-session-store.ts` `CookieSessionStore` |
| introduced | D | `src/auth/redis-session-store.ts` `RedisSessionStore` (new file) |

Expected: A is known debt with nothing to block; B/E is reported but does not block; D blocks; C/F is no violation.

The 4-class fixture works with DUO 0.2.0 as published; no reduction was needed.

## 6. Method

- **DUO**: [run.mjs](../../bench/decision-compliance/run.mjs) installs the registry package into a temporary prefix with an empty npm config (no workspace code), generates the fixture, and runs the public CLI. Each scenario is reviewed 10 times with `--json`.
- **DIY**: the same runner runs [session-store-gate.mjs](../../bench/decision-compliance/diy/session-store-gate.mjs) 10 times per scenario.
- **External AI review**: [external.mjs](../../bench/decision-compliance/external.mjs), run by hand outside CI.
- **Repeatability**: DUO results are compared through a canonical projection ([canonical.mjs](../../bench/decision-compliance/canonical.mjs)). It keeps the verdict and its basis, every claim (Decision, rule, provenance, blocking meaning, expected and observed text, claim ID) with every cited Evidence record (kind, path, symbol, lines, diff change, commit, content hash, Evidence ID), the gap assessment, limitations and the baseline reference. It drops only `meta.performance` timings, metrics and diagnostics. Comparing raw files showed that the five `meta.performance` timings were the only fields that differed between runs.

## 7. DUO setup (the real public flow)

1. `npm install -g @duo-director/cli@0.2.0`
2. A person confirms D-001 with `duoctl decision confirm D-001` in an interactive terminal, typing the ID again. This step was done once with the published CLI (Git user `benchmark-maintainer`); the generator replays the resulting file, including its `lock.digest`. No internal API was used.
3. With D-001 in the baseline commit: `duoctl init --non-interactive --answers -` (adoption baseline at `baseline`).
4. `git checkout main`, `duoctl index`, `duoctl review --from <baseline> --to <change> --json` (and the same for `control-only`).

The adoption record stays an untracked file in the working tree, so the change commit is identical for every workflow. A Decision affects the adoption baseline only if it is already in Truth when `duoctl init` runs; confirmed later, existing violations are not in the baseline (seen while preparing the README example).

## 8. DIY baseline

A bespoke gate for this one rule, written the way a competent developer might for a single fixed rule: Git plus the Node standard library, no DUO code, no network, no LLM, no dependencies. It finds declarations whose name contains `SessionStore` at the base and head commits, computes their line ranges by brace matching, and compares them with a zero-context diff:

- not present at the base → introduced, blocking (exit 1),
- present at the base and inside a changed range → pre-existing-touched,
- present at the base and not changed → pre-existing (listed).

Size: 1 file, 70 lines, 57 code lines. It is not a general rule engine, has no Decision lifecycle, and "pre-existing" means "present at the diff base", which in this fixture is the same commit as DUO's adoption baseline.

## 9. External tool protocol

Each tool gets the policy only through its native instruction file in the fixture and is run on the change commit. A cell is filled only from a real run on a real account, with date, client, model and raw output kept; otherwise it is NOT RUN. No account was created and nothing was paid for this benchmark.

- **Codex**: `codex review --commit <SHA> -c model=gpt-5.5`, client OpenAI Codex v0.147.0, sandbox read-only, ChatGPT sign-in. On this machine Codex reaches OpenAI through a local OpenCodex proxy; the client reported `model: gpt-5.5`, `provider: openai`, but the serving model was not independently verified. `codex review --commit` does not accept custom instructions, so Codex received only its built-in review prompt and `AGENTS.md`. One exploratory run (same command) came before the recorded runs and is not counted.
- **Claude Code**: NOT RUN. Claude Code 2.1.258 is installed but not signed in, and launching it through the same proxy failed with "OAuth session expired and could not be refreshed". No review prompt was sent ([evidence](../../bench/decision-compliance/evidence/claude-code/not-run.json)). A later run would use `CLAUDE.md` and the prompt in [review-prompt.txt](../../bench/decision-compliance/review-prompt.txt).
- **GitHub Copilot code review, Cursor Bugbot, Qodo**: NOT RUN, no account or installed client on the benchmark machine. Their documented capabilities ([survivability audit](../roadmap/0.2.0-survivability-audit.md)) are not benchmark results.

## 10. Metrics

Functional: the new violation, touched and untouched legacy, valid-control findings, explicit provenance, evidence specificity, overall action, repeatability. Operational: install and setup steps, human confirmation, files added to the repository, custom code, account, network and model. Functional and operational results are reported separately and never combined.

Cell states: **Observed**, **Not observed**, **Partial**, **NOT RUN**, **Not applicable**.

```bash

node bench/decision-compliance/run.mjs --runs 10                 # published DUO + DIY (needs the npm registry)
```

`pnpm test` checks the fixture SHAs, the DIY result and the stored DUO projections without running DUO or any external tool.

## 14. Limitations

- One rule, one language, one small fixture, one machine. AI runs were 5 and 3.
- The adoption baseline and the diff base are the same commit here. The fixture does not separate "existed at adoption" (DUO) from "existed before this change" (the DIY gate and the AI review). A violation added after adoption and touched by a later change would tell them apart; that case is not tested.
- The Codex runs went through a local proxy, and the serving model was not independently verified.
- The Codex review command cannot take extra instructions with `--commit`, so Codex and DUO got the intent through different channels (instruction file versus Decision file).
- The DIY gate was written knowing the fixture. It is meant as an upper bound on how little code one fixed rule needs, not as a general tool.
- Decision lifecycle, locks and supersession (DUO's other claims) are not exercised; a decision-history benchmark is the next step.

## 15. Interpretation

- **A. Does DUO 0.2.0 tell legacy from introduced?** Yes in this fixture: introduced D blocks, touched legacy E is reported without blocking, untouched legacy A is held in the adoption baseline and not reported as new.
- **B. Is it repeatable?** Yes: 10/10 identical projections per scenario, and the raw outputs differed only in timings.
- **C. Is the evidence traceable?** Yes: each claim names D-001 and cites the Decision file range, the symbol range and the diff hunk, each with a content hash.
- **D. How much code does a DIY gate need?** 57 code lines reproduced the same four-way classification and a blocking exit code for this one rule.
- **E. Is DUO's setup cost reasonable?** Not decided by one fixture. DUO needs one interactive confirmation and the Decision in Truth before adoption; in return it records a lock, an adoption-time baseline and hashed evidence that the other workflows here did not produce.

The same functional classification was produced by all three workflows that ran. On this fixture DUO does not show a detection advantage; what it adds is fixed machine fields, content hashes, a confirmed and locked Decision, an adoption-time reference, no model or account, and identical results across runs.

## 16. Falsification criteria (fixed before the runs)

| Criterion | Result in this benchmark |
|---|---|
| DUO misses the new violation | Not met: 10/10 blocked |
| DUO's legacy / new classification is unstable | Not met: 10/10 identical |
| DUO's Decision and Evidence provenance is weaker than expected | Not met: Decision, ranges and hashes present. Untouched legacy appears only in the adoption record, not in the review |
| A valid control is flagged | **Partially met**: no violation claim, but the control-only change gets an overall **WARN** from a knowledge gap. A pipeline that fails on WARN (`--fail-on warn`, `--strict`) would reject this valid change; `--fail-on block` passes it |
| A tiny DIY script gives nearly the same provenance | **Met** for this one rule: same four-way classification and gate in 57 code lines, without hashes, lifecycle or an adoption-time baseline |
| DUO setup or confirmation cost is clearly larger | Partially met: DUO alone needs an interactive human confirmation and the Decision in place before adoption |
| A native AI review gives the same result with simpler setup, repeatedly | **Met** on the change commit: Codex gave the same classification 5/5 with only an `AGENTS.md` section. It needed an account, a hosted model and about a minute per review, gave prose without fixed fields or hashes, and was not a pass/fail gate; on the control-only commit 1/3 runs added an unrelated P1 finding |

These results weaken the claim that DUO is needed to detect and classify this kind of violation, and narrow its remaining case to what this fixture did not stress: Decision lifecycle and supersession, adoption-time provenance across later changes, model independence and gateable, hashed evidence.
